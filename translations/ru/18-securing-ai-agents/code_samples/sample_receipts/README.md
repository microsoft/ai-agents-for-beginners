# Примеры фикстур чеков

Три заранее сгенерированных файла чеков для просмотра без запуска ноутбука.

| Файл | Что это |
|---|---|
| `01_valid_receipt.json` | Валидный подписанный чек для вызова инструмента `lookup_flights`. Проверка возвращает True. |
| `02_tampered_receipt.json` | Тот же чек с одним измененным полем после подписи. Проверка возвращает False. |
| `03_chain_three_receipts.json` | Цепочка из трех валидных чеков (search, hold, book) с `previous_receipt_hash`, связывающим каждый с предыдущим. |

Фикстуры подписывают канонические JCS-байты полезной нагрузки напрямую с помощью Ed25519.
SHA-256 продолжает использоваться для дайджестов содержимого и ссылок в цепочке чеков, а не как
дополнительный пре-хэш перед подписью.

## Проверка примеров

В ноутбуке проверка разбита на четыре раздела. Чтобы проверить эти фикстуры
напрямую, не проходя через рассказ ноутбука:

```python
import json
from pathlib import Path

# Предполагается, что вы выполнили импорты и вспомогательные функции
# из разделов 1 и 2 файла 18-signed-receipts.ipynb.

valid = json.loads(Path("01_valid_receipt.json").read_text())
print(f"Valid receipt: {verify_receipt(valid)}")        # Истина

tampered = json.loads(Path("02_tampered_receipt.json").read_text())
print(f"Tampered receipt: {verify_receipt(tampered)}")  # Ложь

chain = json.loads(Path("03_chain_three_receipts.json").read_text())
for r in verify_chain(chain):
    print(f"  Receipt {r['index']} ({r['tool']}): {'VALID' if r['overall_valid'] else 'INVALID'}")
```

## Как они были сгенерированы

Фикстуры используют тот же код, что и ноутбук, с одним фиксированным ключом подписи
и фиксированными временными метками для воспроизводимости байтов. Чтобы пересоздать:

```bash
python3 generate_fixtures.py
```

(Скрипт находится в `generate_fixtures.py` в этой папке.)

## Что студенты узнают, изучая raw JSON

Чтение сырого формата чека формирует интуицию, которой иногда не хватает в ячейках ноутбука.
Студенты, которые пролистывают JSON, часто замечают:

1. Подпись — это непрозрачная строка base64url, но все остальные поля — простой
   читаемый JSON. Подпись не шифрует содержимое; она подтверждает его.
2. `public_key` встроен в чек. Аудитору больше ничего не нужно,
   чтобы проверить (при условии, что ключ действительно принадлежит заявленному
   издателю; смотрите README урока по инфраструктуре идентификации).
3. Изменение одного символа в любом поле и последующее сравнение с
   `02_tampered_receipt.json` делает механизм на уровне байтов понятным.
