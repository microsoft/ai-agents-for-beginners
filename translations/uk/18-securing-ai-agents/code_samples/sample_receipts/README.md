# Приклади квитанцій

Три попередньо згенеровані файли квитанцій для перегляду без запуску ноутбука.

| Файл | Що це таке |
|---|---|
| `01_valid_receipt.json` | Дійсна підписана квитанція для виклику інструменту `lookup_flights`. Перевірка повертає True. |
| `02_tampered_receipt.json` | Та сама квитанція з одним зміненим полем після підпису. Перевірка повертає False. |
| `03_chain_three_receipts.json` | Ланцюжок із трьох дійсних квитанцій (пошук, утримання, бронювання) з `previous_receipt_hash`, що пов’язує кожну з попередньою. |

Приклади підписують канонічні JCS байти корисного навантаження безпосередньо за допомогою Ed25519.
SHA-256 залишається вжитку для дайджестів вмісту та посилань у ланцюгу квитанцій, але не як
додаткове передхешування перед підписом.

## Перевірка прикладів

У ноутбуці проходять перевірку у чотирьох розділах. Щоб перевірити ці приклади
безпосередньо, не виконуючи ноутбук:

```python
import json
from pathlib import Path

# Припускає, що ви завершили імпорти та допоміжні функції
# з розділів 1 та 2 файлу 18-signed-receipts.ipynb.

valid = json.loads(Path("01_valid_receipt.json").read_text())
print(f"Valid receipt: {verify_receipt(valid)}")        # Істина

tampered = json.loads(Path("02_tampered_receipt.json").read_text())
print(f"Tampered receipt: {verify_receipt(tampered)}")  # Хибність

chain = json.loads(Path("03_chain_three_receipts.json").read_text())
for r in verify_chain(chain):
    print(f"  Receipt {r['index']} ({r['tool']}): {'VALID' if r['overall_valid'] else 'INVALID'}")
```

## Як вони були згенеровані

Приклади використовують той самий кодовий шлях, що й ноутбук, з одним фіксованим ключем підпису
і фіксованими часовими позначками для відтворюваності байтів. Щоб згенерувати знову:

```bash
python3 generate_fixtures.py
```

(Скрипт знаходиться у `generate_fixtures.py` в цій директорії.)

## Що студенти дізнаються, переглядаючи сирий JSON

Ознайомлення з сирим форматом квитанцій допомагає сформувати інтуїцію, яку не завжди дають комірки в ноутбуці.
Студенти, які переглядають JSON поверхнево, часто помічають:

1. Підпис — це непрозорий рядок base64url, але всі інші поля — простий
   читабельний JSON. Підпис не шифрує вміст; він засвідчує його.
2. `public_key` вбудований у квитанцію. Аудитор не потребує нічого іншого,
   щоб перевірити її (за умови довіри, що ключ належить заявленому
   видавцю; див. README до уроку про інфраструктуру ідентичності).
3. Зміна одного символу будь-якого поля, а потім повторне порівняння цього файлу з
   `02_tampered_receipt.json` робить механізм на рівні байтів наочним.
