# Використання агентських протоколів (MCP, A2A та NLWeb)

[![Agentic Protocols](../../../translated_images/uk/lesson-11-thumbnail.b6c742949cf1ce2a.webp)](https://youtu.be/X-Dh9R3Opn8)

> _(Натисніть на зображення вище, щоб переглянути відео цього уроку)_

Зі зростанням використання AI-агентів з'являється й потреба в протоколах, які забезпечують стандартизацію, безпеку та підтримку відкритих інновацій. У цьому уроці ми розглянемо 3 протоколи, які відповідають на цю потребу — Model Context Protocol (MCP), Agent to Agent (A2A) та Natural Language Web (NLWeb).

## Вступ

У цьому уроці ми розглянемо:

• Як **MCP** дозволяє AI-агентам отримувати доступ до зовнішніх інструментів і даних для виконання завдань користувача.

• Як **A2A** забезпечує комунікацію та співпрацю між різними AI-агентами.

• Як **NLWeb** приносить інтерфейси природної мови на будь-який вебсайт, дозволяючи AI-агентам знаходити та взаємодіяти з контентом.

## Цілі навчання

• **Визначити** основне призначення та переваги MCP, A2A та NLWeb у контексті AI-агентів.

• **Пояснити**, як кожен протокол полегшує спілкування і взаємодію між LLM, інструментами та іншими агентами.

• **Розпізнати** окремі ролі, які кожен протокол виконує у побудові складних агентських систем.

## Протокол контексту моделей

**Model Context Protocol (MCP)** — це відкритий стандарт, який забезпечує стандартизований спосіб для додатків надавати контекст і інструменти LLM. Це дозволяє мати "універсальний адаптер" до різних джерел даних та інструментів, до яких AI-агенти можуть підключатися послідовним способом.

Розглянемо компоненти MCP, переваги порівняно з безпосереднім використанням API та приклад того, як AI-агенти можуть використовувати MCP-сервер.

### Основні компоненти MCP

MCP працює на основі **клієнт-серверної архітектури**, а основними компонентами є:

• **Ведучі (Hosts)** — це застосунки LLM (наприклад, редактор коду, як VSCode), які ініціюють з'єднання з MCP-сервером.

• **Клієнти (Clients)** — це компоненти всередині ведучого застосунку, які підтримують один-на-один з'єднання з серверами.

• **Сервери (Servers)** — це легковагові програми, що надають певні можливості.

Протокол охоплює три основні примітиви, які є можливостями MCP-сервера:

• **Інструменти (Tools)**: Це окремі дії або функції, які AI-агент може викликати для виконання завдання. Наприклад, сервіс погоди може мати інструмент "отримати погоду", або сервер електронної комерції інструмент "купити продукт". MCP-сервери рекламують ім'я інструменту, опис і схему вхідних/вихідних даних у своєму списку можливостей.

• **Ресурси (Resources)**: Це дані або документи лише для читання, які MCP-сервер може надати, і клієнти можуть запитувати їх за потреби. Приклади включають вміст файлів, записи бази даних або лог-файли. Ресурси можуть бути текстовими (наприклад, код або JSON) або бінарними (зображення чи PDF).

• **Шаблони (Prompts)**: Це заздалегідь визначені шаблони, які пропонують рекомендовані запити, що дозволяє створювати більш складні робочі процеси.

### Переваги MCP

MCP пропонує суттєві переваги для AI-агентів:

• **Динамічне виявлення інструментів**: Агенти можуть динамічно отримувати список доступних інструментів від сервера разом із описами їхньої функції. На відміну від традиційних API, які часто потребують статичного кодування інтеграцій, що призводить до необхідності оновлення коду при зміні API. MCP пропонує підхід "інтегрувати один раз", що забезпечує більшу адаптивність.

• **Інтероперабельність між різними LLM**: MCP працює з різними LLM, надаючи гнучкість у виборі основних моделей для кращої продуктивності.

• **Стандартизована безпека**: MCP включає стандартний метод аутентифікації, що полегшує масштабування при додаванні доступу до інших MCP-серверів. Це простіше, ніж керувати різними ключами та типами аутентифікації для різних традиційних API.

### Приклад MCP

![MCP Diagram](../../../translated_images/uk/mcp-diagram.e4ca1cbd551444a1.webp)

Уявімо користувача, що хоче забронювати авіарейс за допомогою AI-помічника, який працює на базі MCP.

1. **З'єднання**: AI-помічник (MCP-клієнт) підключається до MCP-сервера, що належить авіакомпанії.

2. **Виявлення інструментів**: Клієнт питає MCP-сервер авіакомпанії: "Які інструменти у вас доступні?" Сервер відповідає інструментами, такими як "пошук рейсів" і "бронювання рейсів".

3. **Виклик інструменту**: Користувач говорить AI-помічнику: "Будь ласка, знайди рейс з Портленда до Гонолулу." AI-помічник, використовуючи свій LLM, визначає, що потрібно викликати інструмент "пошук рейсів" і передає відповідні параметри (початок, пункт призначення) MCP-серверу.

4. **Виконання та відповідь**: MCP-сервер, виконуючи роль обгортки, робить фактичний виклик внутрішнього API бронювання авіакомпанії. Потім він отримує інформацію про рейс (наприклад, у форматі JSON) і надсилає її назад AI-помічнику.

5. **Подальша взаємодія**: AI-помічник показує варіанти рейсів. Після вибору рейсу помічник може викликати інструмент "бронювання рейсу" на тому ж MCP-сервері, завершуючи бронювання.

## Протокол Agent-to-Agent (A2A)

Якщо MCP зосереджується на підключенні LLM до інструментів, то **протокол Agent-to-Agent (A2A)** йде далі, дозволяючи комунікацію та співпрацю між різними AI-агентами. A2A з'єднує AI-агентів із різних організацій, середовищ та технологічних стеків для виконання спільного завдання.

Розглянемо компоненти й переваги A2A, а також приклад його застосування в нашому додатку для подорожей.

### Основні компоненти A2A

A2A спрямований на забезпечення спілкування між агентами і їх спільну роботу над підзавданням користувача. Кожен компонент протоколу сприяє цьому:

#### Карта агента (Agent Card)

Подібно до того, як MCP-сервер надає список інструментів, карта агента містить:
- Назву агента.
- **Опис загальних завдань**, які він виконує.
- **Список конкретних навичок** із описами, що допомагають іншим агентам (або навіть користувачам) розуміти, коли й чому варто звертатися до цього агента.
- **Поточну URL-адресу кінцевої точки (Endpoint)** агента.
- **Версію** та **можливості** агента, такі як потокові відповіді та push-повідомлення.

#### Виконавець агента (Agent Executor)

Виконавець агента відповідає за **передачу контексту користувацького чату віддаленому агенту**; віддаленому агенту це необхідно для розуміння завдання. В A2A-сервері агент використовує власний великий мовний модель (LLM) для обробки запитів і виконання завдань із використанням внутрішніх інструментів.

#### Артефакт (Artifact)

Коли віддалений агент завершує поставлене завдання, його результат створюється у вигляді артефакту. Артефакт **містить результат роботи агента**, **опис того, що було виконано**, та **текстовий контекст**, що передається через протокол. Після надсилання артефакту з'єднання з віддаленим агентом закривається до наступного виклику.

#### Черга подій (Event Queue)

Цей компонент використовується для **обробки оновлень і передачі повідомлень**. Особливо важливо в продуктивних агентських системах, щоб не допустити закриття зв’язку між агентами до завершення завдання, особливо коли виконання може займати тривалий час.

### Переваги A2A

• **Покращена співпраця**: Дозволяє агентам від різних постачальників і платформ взаємодіяти, обмінюватися контекстом і працювати разом, спрощуючи автоматизацію між раніше відокремленими системами.

• **Гнучкість вибору моделі**: Кожен A2A-агент може визначити, яку LLM він використовує для обробки своїх запитів, що дозволяє оптимізувати або налаштовувати моделі для кожного агента окремо, на відміну від єдиного зв’язку з LLM у деяких сценаріях MCP.

• **Вбудована аутентифікація**: Аутентифікація інтегрована безпосередньо в протокол A2A, забезпечуючи надійну безпеку взаємодії агентів.

### Приклад A2A

![A2A Diagram](../../../translated_images/uk/A2A-Diagram.8666928d648acc26.webp)

Розглянемо нашу ситуацію з бронюванням подорожі, але цього разу з використанням A2A.

1. **Запит користувача до мультиагента**: Користувач взаємодіє з клієнтом/агентом A2A "Туристичний агент", наприклад, каже: "Забронь, будь ласка, повністю поїздку до Гонолулу на наступний тиждень, включно з авіарейсами, готелем і орендою авто".

2. **Організація з боку туристичного агента**: Туристичний агент отримує це складне завдання. Він використовує свій LLM для аналізу завдання і визначення, що потрібно взаємодіяти з іншими спеціалізованими агентами.

3. **Комунікація між агентами**: Туристичний агент використовує протокол A2A для підключення до підпорядкованих агентів, наприклад, "Агент авіакомпанії", "Агент готелю" та "Агент оренди авто", які створені різними компаніями.

4. **Виконання делегованих завдань**: Туристичний агент відсилає конкретні завдання цим спеціалізованим агентам (наприклад, "Знайти рейси до Гонолулу", "Забронювати готель", "Орендувати авто"). Кожен із цих агентів, який працює на власному LLM і використовує внутрішні інструменти (що можуть бути MCP-серверами), виконує свою частину бронювання.

5. **Об’єднана відповідь**: Коли всі підлеглі агенти завершують свої завдання, Туристичний агент компілює результати (дані про рейси, підтвердження готелю, бронювання авто) і надсилає повну, у стилі чату, відповідь користувачу.

## Natural Language Web (NLWeb)

Вебсайти давно є основним способом доступу користувачів до інформації та даних в Інтернеті.

Розглянемо різні компоненти NLWeb, переваги NLWeb та приклад роботи NLWeb на прикладі нашого додатку для подорожей.

### Компоненти NLWeb

- **Застосунок NLWeb (Основний код сервісу)**: Система, що обробляє запити природною мовою. Вона пов’язує різні частини платформи для створення відповідей. Ви можете уявити її як **двигун, що забезпечує функції природної мови** на сайті.

- **Протокол NLWeb**: Це **базовий набір правил для взаємодії природньою мовою** з вебсайтом. Він повертає відповіді в форматі JSON (часто з використанням Schema.org). Його мета — створити просту основу для "AI Web", так само, як HTML відкрив можливість обміну документами онлайн.

- **MCP-сервер (кінцева точка Model Context Protocol)**: Кожен NLWeb також працює як **MCP-сервер**. Це означає, що він може **надавати інструменти (наприклад, метод "ask") і дані** іншим AI-системам. Фактично це робить контент і можливості сайту доступними для AI-агентів, дозволяючи сайту стати частиною ширшої "екосистеми агентів".

- **Моделі вбудовування (Embedding Models)**: Ці моделі використовуються для **перетворення контенту сайту у числові представлення, звані векторами** (embedding). Ці вектори відображають значення так, щоб комп’ютери могли порівнювати і шукати. Вони зберігаються в спеціальній базі даних, і користувачі можуть обирати, яку модель embedding використовувати.

- **Векторна база даних (механізм пошуку)**: Ця база даних **зберігає embedding вебконтенту**. Коли хтось ставить запитання, NLWeb перевіряє цю базу, щоб швидко знайти найбільш релевантну інформацію. Вона видає швидкий список можливих відповідей, відсортованих за подібністю. NLWeb працює з різними системами зберігання векторів, такими як Qdrant, Snowflake, Milvus, Azure AI Search і Elasticsearch.

### NLWeb на прикладі

![NLWeb](../../../translated_images/uk/nlweb-diagram.c1e2390b310e5fe4.webp)

Знову розглянемо наш сайт для бронювання подорожей, але цього разу він працює на базі NLWeb.

1. **Завантаження даних**: Існуючі каталоги продуктів сайту (наприклад, списки рейсів, описи готелів, турпакети) форматуються за Schema.org або завантажуються через RSS. Інструменти NLWeb інтерпретують ці структуровані дані, створюють embedding і зберігають їх у локальній або віддаленій векторній базі.

2. **Запит природною мовою (користувач)**: Користувач заходить на сайт і замість навігації меню вводить у чат: "Знайди готель, дружній до сімей з басейном у Гонолулу на наступний тиждень".

3. **Обробка NLWeb**: Застосунок NLWeb отримує цей запит. Він надсилає його LLM для розуміння і одночасно проводить пошук у векторній базі для релевантних готелів.

4. **Точні результати**: LLM допомагає інтерпретувати пошукові результати, визначає найкращі збіги за критеріями "дружній до сімей", "басейн" і "Гонолулу", а потім формує відповідь природною мовою. Важливо, що відповідь посилається на реальні готелі з каталогу сайту, уникаючи вигаданих даних.

5. **Взаємодія AI-агента**: Оскільки NLWeb служить MCP-сервером, зовнішній AI-туристичний агент також може підключитися до екземпляра NLWeb цього сайту. AI-агент може використати метод `ask` MCP, щоб звернутися до сайту напряму: `ask("Чи є в районі Гонолулу веганські ресторани, рекомендовані готелем?")`. Екземпляр NLWeb обробить це, використовуючи базу даних інформації про ресторани (якщо вона була завантажена), й поверне структуровану відповідь у форматі JSON.
