# Примерни файлове с касови бележки

Три предварително генерирани файла с касови бележки за преглед без изпълнение на тетрадката.

| Файл | Какво представлява |
|---|---|
| `01_valid_receipt.json` | Валидна подписана касова бележка за извикване на инструмента `lookup_flights`. Проверката връща True. |
| `02_tampered_receipt.json` | Същата бележка с една променена стойност след подписване. Проверката връща False. |
| `03_chain_three_receipts.json` | Верига от три валидни касови бележки (търсене, задържане, резервация) с `previous_receipt_hash`, която свързва всяка с предходната. |

Фикстурите подписват директно каноничните байтове на JCS на полезния товар с Ed25519.
SHA-256 все още се използва за дайджести на съдържанието и връзки в веригата от касови бележки, не като
допълнително предварително хеширане преди подписване.

## Проверка на примерите

Тетрадката разглежда проверката в четири раздела. За да се проверят тези фикстури
директно, без да се изпълнява разказът в тетрадката:

```python
import json
from pathlib import Path

# Предполага се, че сте завършили импортите и помощните функции
# от секции 1 и 2 на 18-signed-receipts.ipynb.

valid = json.loads(Path("01_valid_receipt.json").read_text())
print(f"Valid receipt: {verify_receipt(valid)}")        # Вярно

tampered = json.loads(Path("02_tampered_receipt.json").read_text())
print(f"Tampered receipt: {verify_receipt(tampered)}")  # Грешно

chain = json.loads(Path("03_chain_three_receipts.json").read_text())
for r in verify_chain(chain):
    print(f"  Receipt {r['index']} ({r['tool']}): {'VALID' if r['overall_valid'] else 'INVALID'}")
```

## Как са генерирани тези

Фикстурите използват същия кодов път като тетрадката, с един фиксиран подписващ ключ
и фиксирани времеви печати за възпроизвеждане на байтовете. За повторно генериране:

```bash
python3 generate_fixtures.py
```

(Скриптът е в `generate_fixtures.py` в тази директория.)

## Какво учащите научават от прегледа на суров JSON

Четенето на суровия формат на касовата бележка изгражда интуиция, която клетките в тетрадката
не винаги предоставят. Учениците, които разглеждат JSON, често забелязват:

1. Подписът е непрозрачен base64url низ, но всяко друго поле е обикновен
   четим JSON. Подписът не криптира съдържанието; той го удостоверява.
2. `public_key` е вграден в касовата бележка. Одиторът не се нуждае от нищо друго,
   за да провери (при условие че се доверява, че ключът наистина принадлежи на посочения
   издател; вижте урока README за инфраструктурата на идентичността).
3. Промяната на един символ в което и да е поле, след това повторното сравняване на този файл с
   `02_tampered_receipt.json`, прави механизма на байтово ниво осезаем.
