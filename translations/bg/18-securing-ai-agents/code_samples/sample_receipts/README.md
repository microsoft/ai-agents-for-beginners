# Примерни фиксирани файлове за квитанции

Три предварително генерирани файла с квитанции за преглед без да се стартира тетрадката.

| Файл | Какво представлява |
|---|---|
| `01_valid_receipt.json` | Валидна подписана квитанция за повикване на инструмента `lookup_flights`. Проверката връща True. |
| `02_tampered_receipt.json` | Същата квитанция със променено едно поле след подписването. Проверката връща False. |
| `03_chain_three_receipts.json` | Верига от три валидни квитанции (търсене, задържане, резервация) с `previous_receipt_hash`, свързващ всяка една с предходната. |

Фиксите подписват каноничните байтове на полезния товар (payload) директно с Ed25519.
SHA-256 продължава да се използва за дайджести на съдържанието и връзките в веригата на квитанциите, но не като
допълнителна предварителна хеш-функция преди подписването.

## Проверка на примерите

Тетрадката разглежда проверката в четири части. За да проверите тези фиксирани файлове
директно без да преминавате през историята в тетрадката:

```python
import json
from pathlib import Path

# Предполага, че сте завършили импортите и помощните функции
# от секциите 1 и 2 на 18-signed-receipts.ipynb.

valid = json.loads(Path("01_valid_receipt.json").read_text())
print(f"Valid receipt: {verify_receipt(valid)}")        # Вярно

tampered = json.loads(Path("02_tampered_receipt.json").read_text())
print(f"Tampered receipt: {verify_receipt(tampered)}")  # Грешно

chain = json.loads(Path("03_chain_three_receipts.json").read_text())
for r in verify_chain(chain):
    print(f"  Receipt {r['index']} ({r['tool']}): {'VALID' if r['overall_valid'] else 'INVALID'}")
```

## Как са генерирани тези файлове

Фиксите използват същия път за код, както тетрадката, с един фиксиран ключ за подписване
и фиксирани времеви отпечатъци за повторяемост на байтовете. За да ги прегенерирате:

```bash
python3 generate_fixtures.py
```

(Скриптът е в `generate_fixtures.py` в тази директория.)

## Какво учат студентите, когато разглеждат суровия JSON

Прочитането на суровия формат на квитанциите изгражда интуиция, която клетките в тетрадката
не винаги предоставят. Студентите, които разглеждат JSON, често забелязват:

1. Подписът е непрозрачен низ в base64url, но всяко друго поле е обикновен
   четим JSON. Подписът не криптира съдържанието; той го удостоверява.
2. `public_key` е вграден в квитанцията. Аудиторът не се нуждае от нищо друго
   за проверка (с изключение на доверие, че ключът действително принадлежи на твърдения
   издател; виж урока README за инфраструктурата за идентичност).
3. Промяната на един символ в някое поле и след това сравняването на този файл с
   `02_tampered_receipt.json` прави байтовия механизъм конкретен.
