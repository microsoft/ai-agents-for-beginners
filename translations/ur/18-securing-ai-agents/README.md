# کرپٹو گرافک رسیدوں کے ساتھ AI ایجنٹس کو محفوظ کرنا

## تعارف

یہ سبق مندرجہ ذیل کو شامل کرے گا:

- AI ایجنٹس کے لیے آڈٹ ٹریلز کی اہمیت برائے تعمیل، ڈی بگنگ، اور اعتماد۔
- کرپٹو گرافک رسید کیا ہے اور یہ بغیر دستخط کے لاگ لائن سے کس طرح مختلف ہے۔
- ایک ایجنٹ کے ٹول کال کے لیے سادہ Python میں دستخط شدہ رسید کیسے بنائیں۔
- رسید کو آف لائن کیسے ویریفائی کریں اور چھیڑ چھاڑ کا پتہ لگائیں۔
- رسیدوں کو چین کیسے کریں تاکہ ایک کو ہٹانے یا ترتیب بدلنے سے چین ٹوٹ جائے۔
- رسید کیا ثابت کرتے ہیں اور کیا واضح طور پر ثابت نہیں کرتے۔

## سیکھنے کے مقاصد

اس سبق کو مکمل کرنے کے بعد، آپ جان پائیں گے کہ کیسے:

- ان ناکامی کے طریقوں کی شناخت کرنا جو ایجنٹ کے عمل کے لئے کرپٹو گرافک ماخذ کا محرک بنتے ہیں۔
- ایک کینونیکل JSON پے لوڈ پر Ed25519 دستخط شدہ رسید تیار کرنا۔
- رسید کو صرف دستخط کنندہ کی عوامی کنجی سے آزادانہ طور پر ویریفائی کرنا۔
- ترمیم کا پتہ لگانا، ایک بدلی ہوئی رسید پر دوبارہ ویریفکیشن کرنا۔
- رسیدوں کی ہیش چین کے سلسلے کی تعمیر کرنا اور وضاحت کرنا کہ یہ چین کیوں اہم ہے۔
- اس حد کو پہچاننا کہ رسیدیں کیا ثابت کرتی ہیں (اسناد، سالمیت، ترتیب) اور کیا نہیں (عمل کی درستگی، پالیسی کی معقولیت)۔

## مسئلہ: آپ کے ایجنٹ کا آڈٹ ٹریل

تصور کریں کہ آپ نے Contoso Travel کے لیے ایک AI ایجنٹ تعینات کیا ہے۔ ایجنٹ کسٹمر کے درخواستیں پڑھتا ہے، فلائٹس API کو کال کر کے آپشنز دیکھتا ہے، اور کسٹمر کی جانب سے سیٹ بک کرتا ہے۔ پچھلے سہ ماہی میں، ایجنٹ نے 50,000 بکنگز کیں۔

آج ایک آڈیٹر آتا ہے۔ وہ ایک سادہ سوال کرتا ہے: "مجھے دکھائیں کہ آپ کے ایجنٹ نے کیا کیا۔"

آپ لاگ فائلز حوالے کرتے ہیں۔ آڈیٹر انہیں دیکھتا ہے اور مشکل سوال پوچھتا ہے: "میں کیسے جانوں کہ یہ لاگز ایڈیٹ نہیں کیے گئے؟"

یہ آڈٹ ٹریل کا مسئلہ ہے۔ آج کل اکثر ایجنٹ تعیناتیاں ان پر انحصار کرتی ہیں:

- **ایپلیکیشن لاگز**: جو ایجنٹ خود لکھتا ہے، فائل سسٹم تک رسائی رکھنے والا کوئی بھی اسے ایڈیٹ کر سکتا ہے۔
- **کلاؤڈ لاگنگ سروسز**: پلیٹ فارم کی سطح پر چھیڑ چھاڑ سے محفوظ لیکن صرف اگر آڈیٹر پلیٹ فارم آپریٹر پر اعتماد کرے۔
- **ڈیٹا بیس ٹرانزیکشن لاگز**: ڈیٹا بیس کی تبدیلیوں کے لیے مفید لیکن بے ترتیب ٹول کالز کے لیے نہیں۔

ان میں سے کوئی بھی آڈیٹر کے سوال کا جواب نہیں دے سکتا بغیر آڈیٹر کے کسی پر اعتماد کے (آپ، آپ کا کلاؤڈ فراہم کنندہ، آپ کے ڈیٹا بیس فروشندہ)۔ داخلی استعمال کے لیے یہ اعتماد اکثر قابل قبول ہوتا ہے۔ مالیات، صحت کی دیکھ بھال، EU AI ایکٹ کے تحت کاموں کے لیے ایسا نہیں۔

کرپٹو گرافک رسیدیں اس مسئلے کو اس طرح حل کرتی ہیں کہ ہر ایجنٹ کی کارروائی آزادانہ طور پر تصدیق کی جا سکتی ہے۔ آڈیٹر کو آپ پر اعتماد کرنے کی ضرورت نہیں۔ انہیں صرف آپ کی عوامی کلید اور رسید خود چاہیے۔

## کرپٹو گرافک رسید کیا ہے؟

رسید ایک JSON آبجیکٹ ہے جو ریکارڈ کرتا ہے کہ ایجنٹ نے کیا کیا، اور اسے ڈیجیٹل دستخط کے ساتھ دستخط کیا گیا ہے۔

```mermaid
flowchart LR
    A[ایجنٹ ایک آلہ چلاتا ہے] --> B[رسید کا مواد تیار کریں]
    B --> C[جے ایس او این آر ایف سی 8785 کو معیاری بنائیں]
    C --> E[ایڈ25519 سے معیاری بائٹس پر دستخط کریں]
    E --> F[دستخط کے ساتھ رسید]
    F --> G[آڈیٹر آف لائن تصدیق کرتا ہے]
    G --> H{دستخط درست ہے؟}
    H -- yes --> I[چھیڑ چھاڑ کی ثبوت]
    H -- no --> J[رسید مسترد ہو گئی]
```

ایک کم از کم رسید اس طرح دکھائی دیتی ہے:

```json
{
  "type": "agent.tool_call.v1",
  "agent_id": "contoso-travel-bot",
  "tool_name": "lookup_flights",
  "tool_args_hash": "sha256:a3f9c1...",
  "result_hash": "sha256:7b2e1d...",
  "policy_id": "contoso-travel-policy-v3",
  "timestamp": "2026-04-25T14:30:00Z",
  "sequence": 47,
  "previous_receipt_hash": "sha256:9d4e6a...",
  "signature": {
    "alg": "EdDSA",
    "sig": "c5af83...",
    "public_key": "8f3b2c..."
  }
}
```

تین خصوصیات کام کر رہی ہیں:

1. **دستخط**۔ رسید ایجنٹ کے گیٹ وے کے ذریعے Ed25519 پرائیویٹ کی سے دستخط کی جاتی ہے۔ جس کے پاس متعلقہ عوامی کلید ہو، وہ اس دستخط کو آف لائن ویریفائی کر سکتا ہے۔ کسی بھی فیلڈ میں چھیڑچھاڑ دستخط کو غیر معتبر بنا دیتی ہے۔

2. **کینونیکل انکوڈنگ**۔ دستخط کرنے سے پہلے، رسید کو JSON Canonicalization Scheme (JCS, RFC 8785) استعمال کرتے ہوئے سیریلائز کیا جاتا ہے۔ یہ یقینی بناتا ہے کہ دو الگ الگ امپلیمنٹیشنز جو ایک ہی منطقی رسید پیدا کرتے ہیں، ایک جیسا بائٹ-شناسا نتیجہ پیدا کریں۔ بغیر کینونیکلائزیشن کے، مختلف JSON سیریلائزرز ایک ہی مواد کے لیے مختلف دستخط پیدا کریں گے۔

3. **ہیش چیننگ**۔ `previous_receipt_hash` فیلڈ ہر رسید کو اس سے پہلے والی رسید سے جوڑتا ہے۔ ایک رسید کو ہٹانے یا ترتیب بدلنے سے ہر بعد کی رسید خراب ہو جاتی ہے۔ چھیڑ چھاڑ چین کی سطح پر بھی نظر آتی ہے چاہے انفرادی دستخط چوری کر لیے جائیں۔

یہ خصوصیات مل کر تین ضمانتیں فراہم کرتی ہیں:

- **اثبات**: اس کلید نے یہ مواد دستخط کیا۔
- **سالميت**: دستخط کے بعد مواد تبدیل نہیں ہوا۔
- **ترتیب**: یہ رسید اس چین میں اس رسید کے بعد آئی۔

## Python میں رسید بنانا

رسید بنانے کے لیے آپ کو کوئی خاص لائبریری درکار نہیں۔ کرپٹو گرافک پرائمیٹوز عام دستیاب ہیں اور منطق چند درجن Python لائنز ہے۔

`code_samples/18-signed-receipts.ipynb` میں ہاتھ سے کرنے کی مشقیں پورے عمل کو قدم بہ قدم دکھاتی ہیں۔ خلاصے کا ورژن:

```python
import json
import hashlib
import base64
from nacl import signing
from jcs import canonicalize  # آر ایف سی ۸۷۸۵ کینونیکل جے ایس او این

def b64url_nopad(data: bytes) -> str:
    return base64.urlsafe_b64encode(data).decode("ascii").rstrip("=")

def sha256_canonical(obj) -> str:
    """SHA-256 of a Python object's JCS-canonical JSON form."""
    return f"sha256:{hashlib.sha256(canonicalize(obj)).hexdigest()}"

# ایک دستخطی کلید پیدا کریں یا لوڈ کریں (پیداوار میں، کلید کے خزانے میں محفوظ کریں)
signing_key = signing.SigningKey.generate()
verify_key = signing_key.verify_key

# رسید کا مواد تیار کریں (ابھی کوئی دستخط نہیں)
tool_args = {"origin": "SYD", "destination": "LAX"}
tool_result = [{"flight": "QF11", "price": 1850, "stops": 0}]

payload = {
    "type": "agent.tool_call.v1",
    "agent_id": "contoso-travel-bot",
    "tool_name": "lookup_flights",
    "tool_args_hash": sha256_canonical(tool_args),
    "result_hash": sha256_canonical(tool_result),
    "policy_id": "contoso-travel-policy-v3",
    "timestamp": "2026-04-25T14:30:00Z",
    "sequence": 0,
    "previous_receipt_hash": None,
}

# جے سی ایس بائٹس کو براہ راست معیاری بنائیں اور دستخط کریں۔ پیور ایڈ ڈی ایس اے اندرونی طور پر ہیشز کرتا ہے۔
canonical_bytes = canonicalize(payload)
signature_bytes = signing_key.sign(canonical_bytes).signature

# ایک منظم دستخطی آبجیکٹ منسلک کریں۔
receipt = {
    **payload,
    "signature": {
        "alg": "EdDSA",
        "sig": b64url_nopad(signature_bytes),
        "public_key": b64url_nopad(bytes(verify_key)),
    },
}
```

یہی مکمل دستخط کا عمل ہے۔ نوٹ بک میں مشقیں ہر قدم کی وضاحت کرتی ہیں۔

## رسید کی تصدیق اور چھیڑچھاڑ کا پتہ لگانا

تصدیق الٹی کارروائی ہے:

```python
import base64
import hashlib
from nacl import signing
from nacl.exceptions import BadSignatureError
from jcs import canonicalize

def b64url_decode(s: str) -> bytes:
    padding = "=" * ((4 - len(s) % 4) % 4)
    return base64.urlsafe_b64decode(s + padding)

def verify_receipt(receipt: dict) -> bool:
    # دستخط ایک منظم شے ہے: {"alg", "sig", "public_key"}۔
    sig_obj = receipt.get("signature")
    if not sig_obj or sig_obj.get("alg") != "EdDSA":
        return False

    # اصل میں دستخط کیے گئے پے لوڈ کو پھر سے تعمیر کریں (دستخط کو چھوڑ کر سب کچھ)۔
    payload = {k: v for k, v in receipt.items() if k != "signature"}

    canonical_bytes = canonicalize(payload)

    try:
        verify_key = signing.VerifyKey(b64url_decode(sig_obj["public_key"]))
        verify_key.verify(canonical_bytes, b64url_decode(sig_obj["sig"]))
        return True
    except BadSignatureError:
        return False
```

یہ فنکشن ایک رسید لیتا ہے اور `True` واپس کرتا ہے اگر دستخط درست ہو، ورنہ `False`۔ نہ کوئی نیٹ ورک کال، نہ کوئی سروس انحصار، نہ کسی تیسرے فریق پر اعتماد۔  

چھیڑچھاڑ کے پتہ چلانے کے لیے نوٹ بک یہ دیکھاتی ہے:

1. ایک درست رسید بنانا اور تصدیق کی یقین دہانی کرنا۔
2. `tool_args_hash` فیلڈ کے ایک بائٹ میں ترمیم کرنا۔
3. دوبارہ تصدیق کرنا اور ناکامی دیکھنا۔

یہ عملی مظاہرہ ہے کہ رسیدیں چھیڑچھاڑ کا پتہ دیتی ہیں: کوئی بھی معمولی ترمیم دستخط کو ناکام کر دیتی ہے۔

## ملٹی-اسٹیپ ایجنٹس کے لئے رسیدوں کی چیننگ

ایک دستخط شدہ رسید ایک عمل کی حفاظت کرتی ہے۔ رسیدوں کی چین ایک سلسلے کی حفاظت کرتی ہے۔

```mermaid
flowchart LR
    R0[رسید 0<br/>ابتدائیہ] --> R1[رسید 1]
    R1 --> R2[رسید 2]
    R2 --> R3[رسید 3]
    R1 -. previous_receipt_hash .-> R0
    R2 -. previous_receipt_hash .-> R1
    R3 -. previous_receipt_hash .-> R2
```

ہر رسید اپنی سے پہلے والی رسید کے ہیش کو ریکارڈ کرتی ہے۔ رسید 2 کو چپکے سے ہٹانے کے لئے حملہ آور کو چاہیئے کہ یا:

- رسید 3 کے `previous_receipt_hash` فیلڈ میں ترمیم کرے (رسید 3 کا دستخط خراب ہو جائے)، یا
- رسید 3 کی ایک بدلی ہوئی رسید پر نئی دستخط بنائے (ایجنٹ کی پرائیویٹ کلید درکار)۔

اگر پرائیویٹ کی ہارڈویئر کلید والیٹ میں ہو اور آپ ہر رسید کے ساتھ عوامی کلید شائع کریں، تو کوئی بھی حملہ بغیر پتا چلائے ممکن نہیں۔

نوٹ بک میں:

1. تین رسیدوں کی ایک چین بنانا۔
2. تصدیق کرنا کہ ہر رسید کا `previous_receipt_hash` سابقہ رسید کے اصل ہیش سے ملتا ہے۔
3. درمیان میں ایک رسید کے ساتھ چھیڑچھاڑ کرنا اور دیکھنا کہ چین اسی مقام پر ٹوٹتی ہے۔

یہ ہے کہ آپ ایسا آڈٹ ٹریل بناتے ہیں جسے بیرونی آڈیٹر آپ پر اعتماد کیے بغیر ویریفائی کر سکتا ہے۔

## رسیدیں کیا ثابت کرتی ہیں (اور کیا نہیں)

یہ سبق کا سب سے اہم حصہ ہے۔ رسیدیں طاقتور ہیں لیکن ان کی طاقت محدود ہے۔

**رسیدیں تین چیزیں ثابت کرتی ہیں:**

1. **اثبات**: ایک مخصوص کلید نے مخصوص پے لوڈ پر دستخط کیا۔
2. **سالميت**: پے لوڈ دستخط کے بعد تبدیل نہیں ہوا۔
3. **ترتیب**: یہ رسید ہیش چین میں اس رسید کے بعد آئی۔

**رسیدیں یہ ثابت نہیں کرتیں:**

1. **درستگی**: کہ ایجنٹ کی کارروائی صحیح تھی۔ رسید غلط جواب پر بھی اتنی ہی صاف دستخط ہو سکتی ہے جتنی صحیح جواب پر۔
2. **پالیسی کی تعمیل**: کہ `policy_id` میں حوالہ دی گئی پالیسی کا اصل میں جائزہ لیا گیا، یا اگر چیک کی گئی تو یہ کارروائی قابلِ اجازت تھی۔ رسید صرف دعوی ثبت کرتی ہے، نفاذ نہیں۔
3. **کلید سے آگے شناخت**: رسید کہتی ہے "یہ کلید یہ مواد دستخط کر چکی ہے۔" یہ نہیں کہتی "یہ انسان نے اجازت دی۔" ایک کلید کو کسی شخص یا ادارے سے جوڑنے کے لیے علیحدہ شناختی انفراسٹرکچر درکار ہے۔
4. **ان پٹ کی صداقت**: اگر ایجنٹ کو چالاکی سے بدلا ہوا پرامپٹ ملے اور وہ اس پر عمل کرے، تو رسید عمل کو وفاداری سے ریکارڈ کرتی ہے۔ رسید ان پٹ کی تصدیق کا نعم البدل نہیں بلکہ اس کے بعد کا عمل ہے۔

یہ حد دو وجوہات کی بنا پر اہم ہے:

- یہ آپ کو بتاتی ہے کہ رسیدیں کس لیے مفید ہیں: ایجنٹ کے رویے کو آڈٹ ایبل اور چھیڑچھاڑ سے محفوظ بنانے کے لیے، چاہے تنظیمی سرحدوں کے پار بھی ہو۔
- یہ آپ کو بتاتی ہے کہ آپ کو کن اضافی پرتوں کی ضرورت ہے: ان پٹ کی تصدیق (سبق 6)، پالیسی نفاذ (ذیل میں مختصر)، اور شناختی انفراسٹرکچر (اس سبق سے باہر)۔

ایک عام غلط فہمی یہ ہے کہ "ہمارے پاس رسیدیں ہیں" کا مطلب "ہم حکومت کرتے ہیں" ہے۔ ایسا نہیں ہے۔ رسید ایک بنیاد ہے۔ حکمرانی وہ نظام ہے جو آپ اس کے اوپر بناتے ہیں۔

## انسانی منظوری کے عین عمل کو ثابت کرنا

اوپر کی اشیاء میں سے نمبر 3 اپنی ایک علیحدہ سیکشن کے لائق ہے: ایک کارروائی کی رسید کہتی ہے "اس کلید نے یہ مواد دستخط کیا،" کبھی "یہ انسان نے اجازت دی" نہیں۔ اعلیٰ خطرے کی کارروائیوں (رقم کی واپسی، حذف کرنا، وائر ٹرانسفرز) کے لیے حکومتی فریم ورک ایسے بیان کی تقاضا بڑھ رہے ہیں، اور یہ وہی ابتدائیات ہیں جو آپ نے اس سبق میں بنائی ہیں۔

اگلی کتابچہ `code_samples/human-authorization-receipts.ipynb` ایک دوسرا رسید قسم شامل کرتا ہے، `human.approval.v1`، جو سبق کی رسیدوں کی ہی شکل میں ہوتا ہے (Ed25519 سے دستخط شدہ ٹائپ کیا گیا پے لوڈ، اس کے کینونیکل JCS بائٹس پر، دستخطی آبجیکٹ دستخط شدہ بائٹس کے باہر ہوتا ہے)۔ نامزد منظور کنندہ **مکمل کینونیکل عمل اور اس کی ڈائجسٹ** پر دستخط کرتا ہے قبل از عمل؛ ایجنٹ کی کارروائی کی رسید میں وہی **عمل کی ڈائجسٹ** شامل ہوتی ہے اور `parent_approval_ref`، منظور کی رسید کے `receipt_hash` جو آپ نے اوپر چین میں `previous_receipt_hash` کے طور پر استعمال کیا۔ ایک `verify_chain` الگ الگ کلید رجسٹریوں کے تحت دونوں اشیاء کو چیک کرتا ہے (منظور کنندگان کی چابیاں بمقابلہ ایجنٹ کی چابیاں)، لہٰذا کوڈ راستہ مشترکہ ہے مگر اتھارٹیز کبھی نہیں۔

یہ خصوصیت مہیا کی گئی ہے، محتاط انداز میں کہی گئی: *انسان نے اسی خاص عمل کی منظوری دی، اور ایجنٹ نے بالکل وہی منظور شدہ عمل انجام دیا۔* نوٹ بک کی انکار کی خصوصیات ہی اسے محض دعویٰ کے بجائے حقیقت بناتی ہیں:

- کلاسیکی مجموعہ: چھیڑچھاڑ، الجھن کی صورتحال، ری پلے، دونوں طرف جعلی چابیاں، نامناسب ان پٹ؛
- **پرانی اتھارٹی**: دستخط جو اب بھی تصدیق ہوتی ہے، لیکن قطعی انکار کی جاتی ہے کیونکہ پالیسی ورژن بدل گیا، منظور کنندہ کی کلید رجسٹری سے ہٹا دی گئی، یا منظور کی میعاد ختم ہو گئی؛
- **ڈائجسٹ کی تبدیلی**: ایک درست دستخط شدہ عمل رسید جو کسی *حقیقی* منظوری کی طرف اشارہ کرتی ہے جو *مختلف* کینونیکل عمل سے بندھی ہوئی ہے۔

ہر ناکامی مختلف وجہ سے انکار کرتی ہے، تاکہ آڈیٹر انکار پڑھ کر بتا سکے کہ آیا اتھارٹی پرانی ہوئی یا انجام دی گئی کارروائی بدلی۔ نوٹ بک کی ہدایت: دستخط شدہ منظوری خود میں اتھارٹی نہیں ہے۔ اتھارٹی اس وقت موجود ہوتی ہے جب دونوں رسیدیں ابھی بھی ایک ہی کینونیکل عمل سے پابند ہوں۔ انسانی منظوری کی رسید ایک تعلیمی مجموعہ ہے جو اس سبق نے بیان کیا ہے، نہ کہ `draft-farley-acta-signed-receipts` کی جانب سے مقرر شدہ رسید کی قسم۔

## پیداوار کے لئے حوالہ جات

اس سبق کا Python کوڈ جان بوجھ کر مختصر رکھا گیا ہے تاکہ آپ ہر لائن پڑھ سکیں اور جان سکیں کہ کیا ہو رہا ہے۔ پیداوار میں آپ کے پاس دو اختیارات ہیں:

1. **کرپٹو گرافک پرائمیٹوز پر براہ راست تعمیر کریں۔** اوپر دکھائی گئی 50 لائنز کئی استعمال کے لیے کافی ہیں۔ PyNaCl (Ed25519) اور `jcs` پیکیج (کینونیکل JSON) اچھی طرح سے برقرار اور آڈٹ شدہ لائبریریاں ہیں۔

2. **پیداواری رسید لائبریری استعمال کریں۔** متعدد اوپن سورس پراجیکٹس وہی نمونہ اضافی خصوصیات کے ساتھ نافذ کرتے ہیں (کی کلید کی گردش، بیچ کی تصدیق، JWK سیٹ کی تقسیم، پالیسی انجن کے ساتھ انضمام):
   - دستخطی سلسلہ ایک خود مختار IETF انٹرنیٹ ڈرافٹ ([`draft-farley-acta-signed-receipts`](https://datatracker.ietf.org/doc/draft-farley-acta-signed-receipts/), نظرثانی 02) میں JCS اور دستخط کے دائرہ کار کے روایات استعمال کرتا ہے۔ اس سبق کی سادہ تعلیمی رسید ڈرافٹ کے `{payload, signature}` لفافے سے مختلف ہے اور اسے مطابقتی نفاذ کے طور پر پیش نہیں کیا گیا۔ ڈرافٹ ایک مشترکہ کنفارمنس سویٹ ([agent-governance-testvectors](https://github.com/ScopeBlind/agent-governance-testvectors)) شائع کرتا ہے جو اس کے وائر فارمیٹ ہدف بناتی ہے۔
   - Microsoft Agent Governance Toolkit رسیدوں کو Cedar-بنیاد پالیسی فیصلوں کے ساتھ جوڑتا ہے؛ اس ذخیرے میں ٹیوٹوریل 33 میں مکمل مثال دیکھیں۔
   - `protect-mcp` (npm) اور `@veritasacta/verify` (npm) پیکیجز Node پر مبنی رسید کی دستخط اور آف لائن تصدیق فراہم کرتے ہیں، جس کا مقصد کسی بھی MCP سرور کو چھیڑچھاڑ سے محفوظ آڈٹ ٹریل کے ساتھ لپیٹنا ہے، جس میں ایک held-for-co-sign فلو شامل ہے جہاں روک دی گئی کارروائی ایک منظوری رسید جاری کرتی ہے جو عمل کی ڈائجسٹ سے بندھی ہو (ڈیسک ٹاپ فلو میں WebAuthn کی حمایت کے ساتھ)، وہی منظوری-رسید نمونہ جو انسانی اجازت والی نوٹ بک میں ہے۔
   - **[nobulex](https://github.com/arian-gogani/nobulex)** Python SDK (`pip install nobulex`) وہی Ed25519 + JCS دستخطی نمونہ Python میں LangChain اور CrewAI انضمام کے ساتھ فراہم کرتا ہے، شائع شدہ کراس ویلیڈیشن ٹیسٹ ویکٹرز اور OWASP PR #2210 کے ذریعے تعاون یافتہ کمپلائنس میپنگ سمیت۔

اپنا خود کا حل بنانے اور لائبریری استعمال کرنے کا فیصلہ JWT لائبریری لکھنے اور آزمودہ لائبریری استعمال کرنے کے فیصلے سے مماثل ہے: دونوں معقول ہیں؛ لائبریری وقت بچاتی ہے اور آڈٹ کی سطح کم کرتی ہے؛ خود سے آغاز کا مطلب ہر پرائمیٹیو کو سمجھنا ہے۔ یہ سبق آپ کو خود سے سکھاتا ہے تاکہ آپ کے پاس دونوں اختیارات کا بنیاد ہو۔

## عملی مشق

`code_samples/18-signed-receipts.ipynb` کھولیں اور تمام چار حصے مکمل کریں:

1۔ **حصہ 1**: اپنی پہلی رسید پر دستخط کریں اور اس کی تصدیق کریں۔
2۔ **حصہ 2**: رسید میں چھیڑ چھاڑ کریں اور تصدیق کی ناکامی دیکھیں۔
3۔ **حصہ 3**: تین رسیدوں کی زنجیر بنائیں اور زنجیر کی سالمیت کی تصدیق کریں۔
4۔ **حصہ 4**: مائیکروسافٹ ایجنٹ فریم ورک کے ساتھ بنائے گئے ایجنٹ پر اس نمونے کو لاگو کریں: ایک ٹول کال کو رسید دستخط کرنے میں لپیٹیں، پھر رسید کی آزادانہ تصدیق کریں۔

**اضافی چیلنج 1:** رسید کے اسکیمے میں اپنی پسند کا ایک اضافی فیلڈ شامل کریں (مثلاً، ٹریسنگ کے لیے درخواست کی شناخت)، کینونیکل دستخط کے منطقی عمل کو اس میں شامل کریں، اور تصدیق کریں کہ رسید اب بھی درست طور پر گزر جاتی ہے۔ پھر دستخط کے بعد فیلڈ میں ترمیم کریں اور تصدیق کی ناکامی یقینی بنائیں۔ یہ آپ کو سمجھنے پر مجبور کرے گا کہ کینونیکل انکوڈنگ کے ہر بائٹ کا دستخط پر کیا اثر ہوتا ہے۔

**اضافی چیلنج 2:** اپنی دو رسیدوں کے کینونیکل بائٹس کو ایک مقررہ ترتیب میں concatinate کر کے SHA-256 ہیش بنائیں اور نتیجے کو تیسرے رسید کے ایک نئے فیلڈ میں دستخط سے پہلے شامل کریں۔ تصدیق کریں کہ تمام تین رسیدیں اب بھی درست طریقے سے گزر جاتی ہیں۔ آپ نے اب صرف ایک قدم کا شمولیتی ثبوت بنایا ہے: جو بھی تیسرے رسید کا حامل ہو، ثابت کر سکتا ہے کہ پہلے دو رسیدیں دستخط کے وقت موجود تھیں بغیر ان کے مواد ظاہر کیے۔ یہی نمونہ وسیع پیمانے پر استعمال ہونے والے انتخابی افشاء رسیدوں میں ہوتا ہے (Merkle commitments, RFC 6962)۔

## خلاصہ

کرپٹوگرافک رسیدیں AI ایجنٹس کو ایک آڈٹ ٹریل دیتی ہیں جو:

- **خود مختار تصدیق کے قابل**: کوئی بھی عوامی کلید رکھنے والا پارٹی تصدیق کر سکتا ہے، کوئی سروس انحصار نہیں۔
- **چھیڑ چھاڑ کا ثبوت دیتی ہیں**: کوئی بھی ترمیم دستخط کو غیر معتبر بنا دیتی ہے۔
- **قابلِ حمل**: رسید ایک چھوٹا JSON فائل ہے؛ اسے کہیں بھی ذخیرہ، منتقل، اور تصدیق کیا جا سکتا ہے۔
- **معیاری تقاضوں کے مطابق**: Ed25519 (RFC 8032)، JCS (RFC 8785)، اور SHA-256 پر مبنی، جو تمام عام استعمال شدہ بنیادی اجزاء ہیں۔

یہ ان پٹ کی تصدیق، پالیسی نفاذ، یا شناخت کے انفراسٹرکچر کا متبادل نہیں ہیں۔ یہ ان تہوں کی بنیاد ہیں۔ جب آپ ایجنٹس کو منظم شدہ کاموں، کثیر تنظیمی ورک فلو، یا ایسے ماحول میں تعینات کر رہے ہوں جہاں مستقبل کا آڈیٹر آپ پر اعتماد کرنے کا مفروضہ نہیں رکھتا، تو رسیدیں ہی آڈٹ ٹریل کو ایماندار بناتی ہیں۔

سب سے اہم بات: رسیدیں یہ ثابت کرتی ہیں کہ کس نے کیا کہا اور کب کہا۔ یہ ثابت نہیں کرتی کہ جو کہا گیا وہ سچ یا درست تھا۔ اس فرق کو مضبوطی سے پکڑ کر رکھیں۔ یہ ایماندار ماخذ نظام اور گمراہ کن نظام کے درمیان فرق ہے۔

## پیداواری چیکلسٹ

جب آپ اس سبق کو مکمل کر کے حقیقی ماحول میں رسید دستخط والے ایجنٹس تعینات کرنے کے لیے تیار ہوں:

- [ ] **دستخط کی کلید کو ڈیولپر کے لیپ ٹاپ سے ہٹا دیں۔** Azure Key Vault، AWS KMS، یا ہارڈویئر سیکیورٹی ماڈیول استعمال کریں۔ ذاتی کلید جو آپ کی رسیدوں پر دستخط کرتی ہے، اسے کبھی سورس کنٹرول یا ایپلیکیشن مشینوں پر سادہ متن میں مت رکھیں۔
- [ ] **تصدیق کی عوامی کلید شائع کریں۔** آڈیٹرز کو آف لائن تصدیق کے لیے یہ درکار ہوتی ہے۔ معیاری طریقہ JWK Set کو کسی معروف URL پر رکھنا ہے (RFC 7517)، جیسے `https://your-org.example.com/.well-known/agent-keys.json`۔
- [ ] **زنجیر کو بیرونی طور پر انکر کریں۔** وقفے وقفے سے تازہ ترین زنجیر کے سر کے ہیش کو ایک شفافیت لاگ میں لکھیں (Sigstore Rekor، RFC 3161 ٹائم اسٹیمپ اتھارٹی، یا دوسرا داخلی نظام) تاکہ کوئی بیرونی پارٹی تصدیق کر سکے "یہ زنجیر اس وقت موجود تھی۔"
- [ ] **رسیدوں کو ناقابلِ تغییر ذخیرہ کریں۔** صرف جمع ہونے والا بلیب اسٹوریج (Azure Storage کے ساتھ ناقابلِ تبدیلی پالیسیاں، AWS S3 Object Lock) اندرونی افراد کو ذخیرہ کی تاریخ کو دوبارہ لکھنے سے روکتا ہے۔
- [ ] **محفوظ رکھنے کا فیصلہ کریں۔** بہت سے تعمیل کے قواعد طویل المدتی محفوظ رکھنے کا تقاضا کرتے ہیں۔ رسید کی تعداد میں اضافے کا منصوبہ بنائیں (ہر رسید تقریباً 500 بائٹس کی ہوتی ہے؛ ایک ایجنٹ جو روزانہ 10 ہزار کالز کرتا ہے سالانہ تقریباً 1.8 جی بی پیدا کرتا ہے)۔
- [ ] **دستاویز کریں کہ رسید کیا نہیں کرتی۔** رسیدیں نسبت، سالمیت، اور ترتیب ثابت کرتی ہیں۔ آپ کی رن بک میں واضح لکھنا چاہیے کہ کون سے اضافی کنٹرولز (ان پٹ کی تصدیق، پالیسی نفاذ، ریٹ لمٹنگ، شناخت کا انفراسٹرکچر) آپ کی نگرانی کی پالیسی میں رسیدوں کے ساتھ شامل ہیں۔

### AI ایجنٹس کو محفوظ بنانے کے بارے میں مزید سوالات ہیں؟

[Microsoft Foundry Discord](https://aka.ms/ai-agents/discord) میں شامل ہوں تاکہ دوسرے سیکھنے والوں سے مل سکیں، آفیس آورز میں شرکت کریں، اور اپنے AI ایجنٹس کے سوالات کے جواب حاصل کریں۔

## اس سبق سے آگے

یہ سبق واحد رسید دستخط اور ہیش زنجیر شدہ تسلسل کو کور کرتا ہے۔ یہی بنیادی اجزاء کئی زیادہ جدید نمونوں میں مل کر کام کرتے ہیں جو آپ کی نگرانی کی پوزیشن کے بہتر ہونے کے ساتھ سامنے آ سکتے ہیں:

- **منتخب اظہار۔** جب رسید کے فیلڈز الگ الگ کمیٹ کیے جاتے ہیں (RFC 6962-طرز کا Merkle درخت)، تو آپ مخصوص فیلڈز کو مخصوص آڈیٹروں کو ظاہر کر سکتے ہیں اور باقی کو بغیر ظاہر کیے ہوئے ثابت کر سکتے ہیں کہ وہ بدلے نہیں گئے۔ مفید جب ایک ہی رسید کو جامع آڈٹ (جو مکمل ہونا چاہتا ہے) اور ڈیٹا کم سے کم کرنے والی پالیسیوں جیسے GDPR (جو کم سے کم دیکھنے کی اجازت دیتا ہے) دونوں کو پورا کرنا ہو۔
- **رسید منسوخی۔** اگر دستخط کرنے والی کلید متاثر ہو جائے، تو آپ کو ایک طریقہ چاہیے کہ تمام رسیدیں جو اس کلید سے دستخط شدہ ہوں ایک مخصوص وقت کے بعد غیر معتبر قرار دی جا سکیں۔ معیاری نمونے: مختصر عمر کی دستخط کی چابیاں اور شائع شدہ منسوخی فہرست، یا شفافیت لاگ جس میں منسوخی کی اندراجات ہوں۔
- **دو طرفہ / تقسیم دستخط والی رسیدیں۔** کچھ نفاذ شدہ طریقوں میں دستخط شدہ پیلوڈ کو عمل سے پہلے (`authorization_*`) اور عمل کے بعد (`result_*`) حصوں میں تقسیم کر کے الگ الگ دستخط کیے جاتے ہیں، یہ مفید ہوتا ہے جب اجازت کا فیصلہ اور مشاہدہ شدہ نتیجہ مختلف اہلکاروں یا وقتوں میں پیدا ہو۔ یہ سبق میں سکھائے جانے والے رسید فارمٹ پر اضافہ کرتا ہے۔
- **پیلوڈ کی ترکیب۔** رسید اس چیز کی مہریں لگا دیتی ہے جو آپ `result_hash` میں رکھتے ہیں۔ حقیقی دنیا کے پیلوڈز اکثر ایک ٹول کے نتیجے سے زیادہ جامع ہوتے ہیں: پہلے کے فیصلے کی وضاحت (ماڈل پیش گوئی، زیرِ غور اختیارات، شواہد اور اس کی تکمیل، خطرے کی پوزیشن، جوابدہی کی زنجیر، دروازے کے نتیجے) سب پیلوڈ میں شامل ہو سکتے ہیں اور ایک کا واحد رسید کے ذریعے مہریں لگا دی جاتی ہیں۔ اس طرح رسید کا نقشہ مختصر رہتا ہے جبکہ ڈومین کے لحاظ سے پیلوڈ اسکیمے ترقی کرتے رہتے ہیں۔
- **مختلف نفاذ کے ساتھ مطابقت۔** ایک ہی رسید فارمٹ کے متعدد آزاد نفاذ (Python, TypeScript, Rust, Go) مشترکہ ٹیسٹ ویکٹرز کے خلاف دو طرفہ تصدیق کرتے ہیں۔ اگر آپ اپنی نفاذ بناتے ہیں، تو شائع شدہ ویکٹرز کے خلاف تصدیق وائر مطابقت کی تصدیق کرتی ہے۔
- **بعد از کوانٹم منتقلی۔** Ed25519 آج کل وسیع پیمانے پر استعمال ہوتا ہے لیکن کوانٹم مزاحم نہیں ہے۔ رسید فارمیٹ لچکدار ہے: `signature.alg` فیلڈ میں `ML-DSA-65` (NIST کا بعد از کوانٹم دستخط معیار) شامل کیا جا سکتا ہے جب آپ کو منتقلی کی ضرورت ہو۔ منتقلی کے دوران رسیدیں دوہری دستخط والی ہو سکتی ہیں۔
