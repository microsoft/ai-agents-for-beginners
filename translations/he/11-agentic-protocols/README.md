# שימוש בפרוטוקולים אגנטיים (MCP, A2A ו-NLWeb)

[![Agentic Protocols](../../../translated_images/he/lesson-11-thumbnail.b6c742949cf1ce2a.webp)](https://youtu.be/X-Dh9R3Opn8)

> _(לחצו על התמונה למעלה לצפייה בסרטון על השיעור)_

ככל שהשימוש בסוכני AI גדל, כך גוברת גם הצורך בפרוטוקולים שמבטיחים סטנדרטיזציה, אבטחה ותמיכה בחדשנות פתוחה. בשיעור זה נסקור 3 פרוטוקולים שמטרתם לענות על צורך זה - Model Context Protocol (MCP), Agent to Agent (A2A) ו-Natural Language Web (NLWeb).

## מבוא

בשיעור זה נסקור:

• כיצד **MCP** מאפשר לסוכני AI גישה לכלים חיצוניים ולנתונים לביצוע משימות משתמש.

• כיצד **A2A** מאפשר תקשורת ושיתוף פעולה בין סוכנים שונים של AI.

• כיצד **NLWeb** מביא ממשקי שפה טבעית לכל אתר אינטרנט, ומאפשר לסוכני AI לגלות ולהתייחס לתוכן.

## מטרות למידה

• **זיהוי** המטרה המרכזית והיתרונות של MCP, A2A, ו-NLWeb בהקשר של סוכני AI.

• **הסבר** כיצד כל פרוטוקול מאפשר תקשורת ואינטראקציה בין LLMs, כלים וסוכנים אחרים.

• **הכרת** התפקידים השונים שכל פרוטוקול ממלא בבניית מערכות סוכנים מורכבות.

## פרוטוקול Model Context

ה-**Model Context Protocol (MCP)** הוא תקן פתוח המספק דרך סטנדרטית לאפליקציות להציע הקשר וכלים ל-LLMs. זה מאפשר "מתאם אוניברסלי" למקורות נתונים וכלים שונים שיכולים להתחבר אליהם סוכני AI באופן עקבי.

נבחן את רכיבי ה-MCP, היתרונות לעומת שימוש ישיר ב-API, ודוגמה לאופן שבו סוכני AI עשויים להשתמש בשרת MCP.

### רכיבי הליבה של MCP

MCP פועל על פי **ארכיטקטורת לקוח-שרת** והרכיבים המרכזיים הם:

• **Hosts** הם אפליקציות LLM (למשל עורך קוד כמו VSCode) שמתחילות את החיבורים לשרת MCP.

• **Clients** הן הרכיבים בתוך אפליקציית ה-host ששומרים על חיבורים אחד על אחד עם שרתים.

• **Servers** הם תוכניות קלות משקל שמציגות יכולות ספציפיות.

בפרוטוקול כלולות שלוש פרימיטיבות מרכזיות הנחשבות ליכולות של שרת MCP:

• **כלים**: פעולות או פונקציות נפרדות שסוכן AI יכול לקרוא כדי לבצע פעולה. לדוגמה, שירות מזג אוויר עשוי להציע כלי "קבל מזג אוויר", או שרת e-commerce עשוי להציע כלי "רכוש מוצר". שרתי MCP מפרסמים את שם הכלי, תיאורו, וסכמת הקלט/פלט ברשימת היכולות שלהם.

• **משאבים**: פריטי מידע או מסמכים לקריאה בלבד ששרת MCP יכול לספק, ולקוחות יכולים לשלוף אותם לפי דרישה. דוגמאות כוללות תוכן קבצים, רשומות מאגר מידע או קבצי לוג. המשאבים יכולים להיות טקסט (כמו קוד או JSON) או בינארי (כמו תמונות או PDFs).

• **הנחיות**: תבניות מוגדרות מראש שמספקות הנחיות מוצעות, ומאפשרות זרימות עבודה מורכבות יותר.

### יתרונות MCP

ל-MCP יתרונות משמעותיים עבור סוכני AI:

• **גילוי דינמי של כלים**: סוכנים יכולים לקבל דינמית רשימה של כלים זמינים משרת יחד עם תיאורים של פעולתם. זאת בניגוד ל-APIs מסורתיים שמחייבים קידוד סטטי לאינטגרציות, וכאשר API משתנה נדרש עדכון קוד. MCP מציע גישה של "אינטגרציה פעם אחת", המובילה להתאמה גבוהה יותר.

• **אינטרופרטביליות בין LLMs**: MCP עובד עם LLMs שונים ומעניק גמישות לשנות את המודלים המרכזיים כדי להעריך ביצועים טובים יותר.

• **אבטחה סטנדרטית**: MCP כולל שיטת אימות סטנדרטית, המשפרת מודולריות כשמוסיפים גישה לשרתי MCP נוספים. זה פשוט יותר מאשר לנהל מפתחות וסוגי אימות שונים עבור APIs מסורתיים.

### דוגמה ל-MCP

![MCP Diagram](../../../translated_images/he/mcp-diagram.e4ca1cbd551444a1.webp)

דמיינו שמשתמש רוצה להזמין טיסה באמצעות עוזר AI שמופעל על ידי MCP.

1. **חיבור**: העוזר AI (הלקוח של MCP) מתחבר לשרת MCP שמסופק על ידי חברת תעופה.

2. **גילוי כלים**: הלקוח שואל את שרת MCP של חברת התעופה, "אילו כלים יש לכם?" השרת משיב עם כלים כמו "חיפוש טיסות" ו-"הזמנת טיסות".

3. **קריאה לכלי**: אז אתה מבקש מהעוזר AI, "אנא חפש טיסה מפורטלנד להונולולו." העוזר AI, באמצעות ה-LLM שלו, מזהה כי עליו לקרוא לכלי "חיפוש טיסות" ומעביר את הפרמטרים הרלוונטיים (מקור, יעד) לשרת MCP.

4. **ביצוע ותגובה**: שרת MCP, שתפקידו לעטוף, מבצע את הקריאה ל-API הפנימי של חברת התעופה. לאחר מכן מקבל את פרטי הטיסה (למשל, נתוני JSON) ושולח אותם חזרה לעוזר AI.

5. **אינטראקציה נוספת**: העוזר AI מציג את אפשרויות הטיסה. ברגע שאתה בוחר טיסה, העוזר עשוי להפעיל את כלי "הזמן טיסה" באותו שרת MCP, ולסיים את ההזמנה.

## פרוטוקול סוכן לסוכן (A2A)

בעוד MCP מתמקד בחיבור בין LLMs לכלים, **פרוטוקול Agent-to-Agent (A2A)** לוקח את זה צעד קדימה על ידי מתן אפשרות לתקשורת ולשיתוף פעולה בין סוכני AI שונים. A2A מחבר סוכני AI מארגונים, סביבות וסטאקים טכנולוגיים שונים כדי להשלים משימה משותפת.

נבחן את הרכיבים והיתרונות של A2A, יחד עם דוגמה לאופן שבו ניתן ליישם אותו באפליקציית הנסיעות שלנו.

### רכיבי הליבה של A2A

A2A מתמקד במתן אפשרות לתקשורת בין סוכנים ובעבודה משותפת שלהם להספקת תת-משימה של המשתמש. כל רכיב בפרוטוקול תורם לכך:

#### כרטיס סוכן

בדומה לאופן שבו שרת MCP משתף רשימת כלים, לכרטיס סוכן יש:
- שם הסוכן.
- **תיאור המשימות הכלליות** שהוא מבצע.
- **רשימת כישורים ספציפיים** עם תיאורים שיעזרו לסוכנים אחרים (או אפילו למשתמשים אנושיים) להבין מתי ולמה להזמין את אותו סוכן.
- **כתובת Endpoint נוכחית** של הסוכן
- **גרסה** ו**יכולות** של הסוכן כמו תגובות בשידור וידיעות דחיפה.

#### מבצע הסוכן

מבצע הסוכן אחראי על **העבר הקשר השיח של המשתמש לסוכן מרוחק**. הסוכן המרוחק זקוק לכך כדי להבין את המשימה שעליו לבצע. בשרת A2A, סוכן משתמש ב-LLM משלו כדי לפרש בקשות נכנסות ולבצע משימות באמצעות הכלים הפנימיים שלו.

#### ארטיפקט

כאשר סוכן מרוחק משלים את המשימה המבוקשת, תוצר עבודתו נוצר כארטיפקט.  ארטיפקט **מכיל את תוצאת עבודת הסוכן**, **תיאור מה הושלם**, וה**הקשר הטקסטואלי** שנשלח דרך הפרוטוקול. לאחר שליחת הארטיפקט, נעשה ניתוק מהסוכן המרוחק עד שיידרש שוב.

#### תור אירועים

רכיב זה משמש ל**טיפול בעדכונים והעבר הודעות**. הוא חשוב במיוחד במערכות סוכנים בפרודקשן כדי למנוע סגירת החיבור בין סוכנים לפני השלמת משימה, במיוחד כשזמן לסיום משימה יכול להיות ארוך יותר.

### יתרונות A2A

• **שיתוף פעולה משופר**: מאפשר לסוכנים מספקים ופלטפורמות שונות לתקשר, לשתף הקשר ולעבוד יחד, מה שמקל על אוטומציה חלקה במערכות שהיו מנותקות בעבר.

• **גמישות בבחירת מודל**: כל סוכן A2A יכול לבחור איזה LLM הוא משתמש כדי לשרת את בקשותיו, ומאפשר אופטימיזציה או כוונון למודלים ספציפיים לסוכן, בניגוד לחיבור LLM יחיד במקרים מסוימים ב-MCP.

• **אימות מובנה**: אימות משולב ישירות בפרוטוקול A2A, ומעניק מסגרת אבטחה חזקה לאינטראקציות בין סוכנים.

### דוגמה ל-A2A

![A2A Diagram](../../../translated_images/he/A2A-Diagram.8666928d648acc26.webp)

נרחיב על תרחיש הזמנת הנסיעות שלנו, אך הפעם באמצעות A2A.

1. **בקשת משתמש לרב-סוכן**: משתמש מתקשר עם סוכן "סוכן נסיעות" בלקוח/סוכן A2A, אולי באומרו, "אנא הזמן טיול שלם להונולולו לשבוע הבא, כולל טיסות, מלון ורכב השכרה".

2. **תיאום על ידי סוכן הנסיעות**: סוכן הנסיעות מקבל את הבקשה המורכבת. הוא משתמש ב-LLM שלו כדי לנתח את המשימה ולקבוע שהוא צריך לתקשר עם סוכנים מתמחים נוספים.

3. **תקשורת בין סוכנים**: סוכן הנסיעות משתמש בפרוטוקול A2A כדי להתחבר לסוכנים משניים, כמו "סוכן חברת תעופה," "סוכן מלון," ו-"סוכן השכרת רכב" שנוצרו על ידי חברות שונות.

4. **ביצוע משימות מורשות**: סוכן הנסיעות שולח משימות ספציפיות לסוכנים המתמחים הללו (למשל, "מצא טיסות להונולולו," "הזמן מלון," "השכר רכב"). כל אחד מהסוכנים המתמחים, שרצים עם LLM משלו ומשתמשים בכלים משלהם (שיכולים להיות שרתי MCP בעצמם), מבצע את חלקו בהזמנה.

5. **תגובה מאוחדת**: לאחר שכל הסוכנים התת-משניים מסיימים את משימותיהם, סוכן הנסיעות מקבץ את התוצאות (פרטי טיסה, אישור מלון, הזמנת רכב) ושולח תשובה מקיפה בסגנון שיחה למשתמש.

## רשת שפה טבעית (NLWeb)

אתרי אינטרנט היו זמן רב הדרך הראשית שבה משתמשים ניגשים למידע ולנתונים ברחבי האינטרנט.

נבחן את רכיבי ה-NLWeb השונים, היתרונות של NLWeb ודוגמה לאופן בו NLWeb שלנו עובד דרך אפליקציית הנסיעות שלנו.

### רכיבי NLWeb

- **יישום NLWeb (קוד שירות ליבה)**: המערכת שמעבדת שאלות בשפה טבעית. היא מחברת את חלקי הפלטפורמה השונים ליצירת תגובות. ניתן לחשוב עליה כ**מנוע שמפעיל את תכונות השפה הטבעית** באתר אינטרנט.

- **פרוטוקול NLWeb**: זהו **מערך כללים בסיסי לאינטראקציה בשפה טבעית** עם אתר אינטרנט. הוא מחזיר תגובות בפורמט JSON (לעיתים בשימוש Schema.org). מטרתו ליצור בסיס פשוט עבור "האינטרנט עם בינה מלאכותית," באותו אופן ש-HTML איפשר שיתוף מסמכים באינטרנט.

- **שרת MCP (נקודת סיום של Model Context Protocol)**: כל התקנת NLWeb פועלת גם כ**שרת MCP**. משמעות הדבר היא שהוא יכול **לשתף כלים (כגון שיטת "ask") ונתונים** עם מערכות AI אחרות. למעשה, זה מאפשר לתוכן האתר וליכולותיו לשמש על ידי סוכני AI, וכך האתר הופך לחלק מ״אקוסיסטמת הסוכנים״ הרחבה יותר.

- **מודלי החדרה (Embedding Models)**: מודלים אלו משמשים ל**המרת תוכן האתר לייצוגים מספריים שנקראים וקטורים** (החדרות). וקטורים אלו לוכדים משמעות בצורה שמחשבים יכולים להשוות ולחפש. הם נשמרים במאגר מיוחד, והמשתמשים יכולים לבחור איזה מודל החדרה להשתמש.

- **מאגר וקטורים (מנגנון אחזור)**: מאגר זה **שומר את ההחדרות של תוכן האתר**. כאשר מישהו שואל שאלה, NLWeb בודק את מאגר הווקטורים כדי למצוא במהירות את המידע הרלוונטי ביותר. הוא מספק רשימה מהירה של תשובות אפשריות, מדורגות לפי דמיון. NLWeb עובד עם מערכות אחסון וקטורים שונות כמו Qdrant, Snowflake, Milvus, Azure AI Search ו-Elasticsearch.

### NLWeb בדוגמה

![NLWeb](../../../translated_images/he/nlweb-diagram.c1e2390b310e5fe4.webp)

נחשוב שוב על אתר הזמנת הנסיעות שלנו, אך הפעם הוא מופעל על ידי NLWeb.

1. **הזנת נתונים**: קטלוגי המוצרים הקיימים באתר הנסיעות (כגון רשימות טיסות, תיאורי מלונות, חבילות טיול) מעוצבים באמצעות Schema.org או נטענים דרך RSS. כלים של NLWeb מכניסים את הנתונים המבניים האלה, יוצרים ההחדרות, ושומרים אותם במאגר וקטורים מקומי או מרוחק.

2. **שאילתה בשפה טבעית (אנושי)**: משתמש מבקר באתר, ובמקום לגלוש בתפריטים, מקליד בממשק שיחה: "מצא לי מלון ידידותי למשפחות בהונולולו עם בריכה לשבוע הבא".

3. **עיבוד ב-NLWeb**: יישום NLWeb מקבל את השאילתה. הוא שולח את השאילתה ל-LLM כדי להבין אותה ומבצע במקביל חיפוש במאגר הווקטורים שלו לרשימות מלונות רלוונטיות.

4. **תוצאות מדויקות**: ה-LLM מסייע לפרש את תוצאות החיפוש מהמאגר, מזהה את ההתאמות הטובות ביותר על פי הקריטריונים "ידידותי למשפחות," "בריכה," ו"הונולולו," ומעצב תשובה בשפה טבעית. חשוב שהתגובה מתייחסת למלונות אמיתיים מתוך קטלוג האתר, ולא למידע מומצא.

5. **אינטראקציה עם סוכן AI**: מאחר ש-NLWeb משמש כשרת MCP, סוכן נסיעות AI חיצוני יכול גם להתחבר למופע NLWeb של אתר זה. סוכן ה-AI יכול להשתמש בשיטת `ask` בפרוטוקול MCP כדי לשאול ישירות את האתר: `ask("האם יש מסעדות טבעוניות באזור הונולולו שמומלצות על ידי המלון?")`. מופע NLWeb יעבד זאת, ישתמש במאגר המידע על מסעדות (אם נטען), ויחזיר תגובה בפורמט JSON מובנה.
