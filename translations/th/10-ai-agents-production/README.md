# ตัวแทน AI ในการผลิต: การสังเกตการณ์ & การประเมินผล

[![AI Agents in Production](../../../translated_images/th/lesson-10-thumbnail.2b79a30773db093e.webp)](https://youtu.be/l4TP6IyJxmQ?si=reGOyeqjxFevyDq9)

เมื่อผู้แทน AI ก้าวจากต้นแบบทดลองสู่การใช้งานในโลกจริง ความสามารถในการเข้าใจพฤติกรรม ตรวจสอบประสิทธิภาพ และประเมินผลลัพธ์อย่างเป็นระบบจึงมีความสำคัญ

## เป้าหมายการเรียนรู้

หลังจากเรียนบทนี้จบ คุณจะรู้วิธี/เข้าใจ:
- แนวคิดหลักของการสังเกตการณ์และการประเมินผลของตัวแทน
- เทคนิคในการปรับปรุงประสิทธิภาพ ค่าใช้จ่าย และความมีประสิทธิผลของตัวแทน
- สิ่งที่ควรประเมินและวิธีประเมินตัวแทน AI ของคุณอย่างเป็นระบบ
- วิธีควบคุมค่าใช้จ่ายเมื่อนำตัวแทน AI ไปใช้งานจริง
- วิธีติดตั้งเครื่องมือในตัวแทนที่สร้างด้วย Microsoft Agent Framework

เป้าหมายคือให้ความรู้แก่คุณเพื่อเปลี่ยนตัวแทน "กล่องดำ" ให้กลายเป็นระบบที่โปร่งใส จัดการได้ และเชื่อถือได้

_**หมายเหตุ:** สำคัญที่จะต้องปรับใช้งานตัวแทน AI ที่ปลอดภัยและน่าเชื่อถือ ลงไปดูบทเรียน [Building Trustworthy AI Agents](../06-building-trustworthy-agents/README.md) ด้วย_

## ร่องรอยและช่วงเวลา (Traces and Spans)

เครื่องมือการสังเกตการณ์อย่าง [Langfuse](https://langfuse.com/) หรือ [Microsoft Foundry](https://learn.microsoft.com/en-us/azure/ai-foundry/what-is-azure-ai-foundry) มักจะแสดงการทำงานของตัวแทนในรูปแบบร่องรอยและช่วงเวลา

- **Trace** คือการแสดงงานตัวแทนครบช่วงตั้งแต่ต้นจนจบ (เช่น การจัดการคำถามของผู้ใช้)
- **Spans** คือขั้นตอนย่อยๆ ภายในร่องรอยนั้น (เช่น การเรียกโมเดลภาษา หรือการดึงข้อมูล)

หากไม่มีการสังเกตการณ์ ตัวแทน AI อาจรู้สึกเป็น "กล่องดำ" — สถานะภายในและเหตุผลเชิงตรรกะถูกปิดบัง ทำให้ยากในการวินิจฉัยปัญหาหรือปรับประสิทธิภาพ ด้วยการสังเกตการณ์ ตัวแทนจะกลายเป็น "กล่องแก้ว" ที่เปิดเผยความโปร่งใสซึ่งสำคัญสำหรับการสร้างความเชื่อถือและเพื่อให้มั่นใจว่าทำงานตามที่ตั้งใจไว้

## ทำไมการสังเกตการณ์จึงมีความสำคัญในสภาพแวดล้อมการผลิต

การนำตัวแทน AI เข้าสู่สภาพแวดล้อมการผลิตก่อให้เกิดความท้าทายและความต้องการใหม่ ๆ การสังเกตการณ์ไม่ใช่แค่ "สิ่งดีที่ควรมี" แต่เป็นความสามารถที่สำคัญ:

*   **การดีบักและวิเคราะห์สาเหตุหลัก**: เมื่อเกิดความล้มเหลวหรือลัพธ์ที่ไม่คาดคิด เครื่องมือสังเกตการณ์จะให้ร่องรอยต่าง ๆ ที่จำเป็นในการหาจุดต้นเหตุของข้อผิดพลาด ซึ่งสำคัญมากสำหรับตัวแทนที่ซับซ้อนที่อาจมีการเรียก LLM หลายครั้ง การโต้ตอบกับเครื่องมือ และตรรกะเงื่อนไขต่างๆ
*   **การจัดการความหน่วงและค่าใช้จ่าย**: ตัวแทน AI มักพึ่งพา LLM และ API ภายนอกที่คิดค่าใช้จ่ายตามจำนวนโทเคนหรือการเรียกใช้ การสังเกตการณ์ช่วยติดตามการเรียกใช้เหล่านี้อย่างแม่นยำ ช่วยระบุการดำเนินงานที่ช้าหรือมีค่าใช้จ่ายสูงเกินไป ทำให้ทีมสามารถปรับแต่งคำสั่ง เลือกโมเดลที่มีประสิทธิภาพ หรือออกแบบ workflow ใหม่เพื่อลดต้นทุนและให้ประสบการณ์ผู้ใช้ที่ดีขึ้น
*   **ความเชื่อถือ ความปลอดภัย และการปฏิบัติตามข้อกำหนด**: ในหลายแอปพลิเคชัน จำเป็นต้องแน่ใจว่าตัวแทนปฏิบัติได้อย่างปลอดภัยและมีจริยธรรม การสังเกตการณ์ให้เส้นทางตรวจสอบการกระทำและการตัดสินใจของตัวแทน ซึ่งสามารถใช้เพื่อตรวจจับและป้องกันปัญหาเช่น การแทรกแซงคำสั่ง, การสร้างเนื้อหาที่เป็นอันตราย หรือการจัดการข้อมูลระบุตัวตนส่วนบุคคล (PII) อย่างไม่ถูกต้อง ตัวอย่างเช่น คุณสามารถตรวจสอบร่องรอยเพื่อเข้าใจว่าทำไมตัวแทนถึงตอบสนองแบบใด หรือใช้เครื่องมือเฉพาะอย่างไร
*   **วงจรการปรับปรุงอย่างต่อเนื่อง**: ข้อมูลจากการสังเกตการณ์เป็นรากฐานของกระบวนการพัฒนาที่ทำซ้ำได้ โดยการติดตามประสิทธิภาพของตัวแทนในโลกจริง ทีมงานสามารถระบุจุดที่ต้องปรับปรุง รวบรวมข้อมูลเพื่อปรับแต่งโมเดล และยืนยันผลกระทบของการเปลี่ยนแปลง สร้างวงจรป้อนกลับที่ข้อมูลจากการประเมินออนไลน์ช่วยแจ้งผลการทดสอบและปรับปรุงออฟไลน์ นำไปสู่ประสิทธิภาพของตัวแทนที่ดีขึ้นอย่างต่อเนื่อง

## ตัวชี้วัดสำคัญที่ควรติดตาม

เพื่อตรวจสอบและเข้าใจพฤติกรรมของตัวแทน ควรติดตามตัวชี้วัดและสัญญาณหลายรูปแบบ แม้ว่าตัวชี้วัดเฉพาะอาจแตกต่างกันตามวัตถุประสงค์ของตัวแทน แต่บางตัวชี้วัดเป็นที่สำคัญโดยทั่วไป

นี่คือตัวชี้วัดที่ใช้กันบ่อยมากที่เครื่องมือการสังเกตการณ์มักติดตาม:

**ความหน่วง (Latency):** ตัวแทนตอบสนองรวดเร็วแค่ไหน? เวลารอนานส่งผลเสียต่อประสบการณ์ผู้ใช้ คุณควรวัดความหน่วงสำหรับงานและขั้นตอนย่อยโดยการติดตามร่องรอยของตัวแทน เช่น ตัวแทนที่ใช้เวลาทั้งหมด 20 วินาทีในการเรียกโมเดลทั้งหมดสามารถเร่งได้โดยใช้โมเดลที่เร็วกว่า หรือเรียกโมเดลพร้อมกัน

**ค่าใช้จ่าย (Costs):** ค่าใช้จ่ายต่อการรันตัวแทนเท่าไหร่? ตัวแทน AI พึ่งพา LLM ที่คิดค่าใช้จ่ายตามโทเคน หรือ API ภายนอก การใช้เครื่องมือบ่อยครั้ง หรือการส่งคำสั่งหลายครั้ง อาจทำให้ค่าใช้จ่ายสูงขึ้นอย่างรวดเร็ว เช่น ถ้าตัวแทนเรียก LLM ห้าครั้งเพียงเพื่อปรับปรุงคุณภาพเล็กน้อย คุณต้องประเมินว่าค่าใช้จ่ายคุ้มค่าหรือไม่ หรือลดจำนวนการเรียกใช้ หรือใช้โมเดลที่ถูกกว่า การตรวจสอบแบบเรียลไทม์ช่วยระบุการกระโดดของค่าใช้จ่ายโดยไม่คาดคิด (เช่น บั๊กทำให้เกิดลูป API มากเกินไป)

**ข้อผิดพลาดในการร้องขอ (Request Errors):** กี่คำขอที่ตัวแทนล้มเหลว? รวมถึงข้อผิดพลาด API หรือการเรียกใช้เครื่องมือที่ล้มเหลว เพื่อเพิ่มความทนทานของตัวแทนในสภาพแวดล้อมการผลิต คุณสามารถตั้งค่าการสำรองหรือการลองใหม่ เช่น ถ้า LLM ผู้ให้บริการ A ล่ม คุณเปลี่ยนไปใช้ LLM ผู้ให้บริการ B เป็นสำรอง

**คำติชมจากผู้ใช้ (User Feedback):** การประเมินจากผู้ใช้โดยตรงให้ข้อมูลเชิงลึกที่มีค่า อาจรวมถึงการให้คะแนนโดยตรง (👍ชอบ/👎ไม่ชอบ, ⭐1-5 ดาว) หรือความคิดเห็นเป็นข้อความ คำติชมเชิงลบอย่างต่อเนื่องควรแจ้งเตือนคุณว่านี่คือสัญญาณว่าตัวแทนไม่ทำงานตามที่คาดหวัง

**คำติชมโดยนัยจากผู้ใช้ (Implicit User Feedback):** พฤติกรรมผู้ใช้ให้คำติชมโดยอ้อมแม้ไม่มีคะแนนโดยตรง เช่น การเปลี่ยนคำถามทันที ถามซ้ำ หรือคลิกปุ่มลองใหม่ เช่น ถ้าคุณเห็นว่าผู้ใช้ถามคำถามเดิมซ้ำๆ นี่คือสัญญาณว่าตัวแทนไม่ได้ทำงานตามที่คาดหวัง

**ความแม่นยำ (Accuracy):** ตัวแทนสร้างผลลัพธ์ที่ถูกต้องหรือเป็นที่ต้องการบ่อยแค่ไหน? ความหมายของความแม่นยำต่างกันไป (เช่น ความถูกต้องในการแก้ปัญหา, ความแม่นยำในการดึงข้อมูล, ความพึงพอใจของผู้ใช้) ขั้นตอนแรกคือต้องกำหนดว่า "ความสำเร็จ" ของตัวแทนของคุณคืออะไร คุณสามารถติดตามความแม่นยำผ่านการตรวจสอบอัตโนมัติ, คะแนนประเมิน หรือป้ายกำกับการทำงานสำเร็จ เช่น การทำเครื่องหมายร่องรอยว่า "สำเร็จ" หรือ "ล้มเหลว"

**เมตริกการประเมินอัตโนมัติ (Automated Evaluation Metrics):** คุณยังสามารถตั้งค่าการประเมินอัตโนมัติ เช่น ใช้ LLM ให้คะแนนผลลัพธ์ของตัวแทน เช่น ว่าช่วยเหลือ แม่นยำ หรือไม่ มีไลบรารีโอเพ่นซอร์สหลายตัวที่ช่วยคุณให้คะแนนด้านต่าง ๆ ของตัวแทน เช่น [RAGAS](https://docs.ragas.io/) สำหรับตัวแทน RAG หรือ [LLM Guard](https://llm-guard.com/) เพื่อตรวจจับภาษาเป็นอันตรายหรือการแทรกแซงคำสั่ง

ในทางปฏิบัติ การผสมผสานตัวชี้วัดเหล่านี้ให้ภาพรวมสุขภาพของตัวแทน AI ได้ดีที่สุด ในตัวอย่าง [notebook ในบทนี้](./code_samples/10-expense_claim-demo.ipynb) เราจะแสดงให้เห็นว่าตัวชี้วัดเหล่านี้เป็นอย่างไรในตัวอย่างจริง แต่ก่อนอื่น เราจะเรียนรู้ว่า workflow การประเมินทั่วไปเป็นอย่างไร

## ติดตั้งเครื่องมือให้ตัวแทนของคุณ

เพื่อเก็บข้อมูลการติดตาม คุณต้องติดตั้งเครื่องมือในโค้ดเป้าหมาย เป้าหมายคือการติดตั้งโค้ดตัวแทนให้ส่งร่องรอยและเมตริกที่สามารถถูกจับ ประมวลผล และแสดงผลโดยแพลตฟอร์มการสังเกตการณ์

**OpenTelemetry (OTel):** [OpenTelemetry](https://opentelemetry.io/) ได้กลายเป็นมาตรฐานอุตสาหกรรมสำหรับการสังเกตการณ์ LLM มันให้ชุด API, SDK และเครื่องมือสำหรับการสร้าง รวบรวม และส่งออกข้อมูลโทรเมทรี

มีไลบรารีการติดตั้งหลายตัวที่ครอบตัวแทนเฟรมเวิร์กที่มีอยู่และทำให้ง่ายต่อการส่งออก OpenTelemetry spans ไปยังเครื่องมือสังเกตการณ์ Microsoft Agent Framework รองรับการทำงานร่วมกับ OpenTelemetry โดยตรง ด้านล่างเป็นตัวอย่างการติดตั้งสำหรับตัวแทน MAF:

```python
from agent_framework.observability import get_tracer, get_meter

tracer = get_tracer()
meter = get_meter()

with tracer.start_as_current_span("agent_run"):
    # การดำเนินการของตัวแทนถูกติดตามโดยอัตโนมัติ
    pass
```

[ตัวอย่าง notebook](./code_samples/10-expense_claim-demo.ipynb) ในบทนี้จะแสดงวิธีการติดตั้งเครื่องมือให้กับตัวแทน MAF ของคุณ

**การสร้าง Span ด้วยตนเอง:** แม้ไลบรารีติดตั้งจะให้ฐานที่ดี แต่มีกรณีที่ต้องการข้อมูลละเอียดหรือกำหนดเองมากขึ้น คุณสามารถสร้าง spans ด้วยตนเองเพื่อเพิ่มตรรกะแอปพลิเคชันแบบกำหนดเอง ที่สำคัญคือ spans เหล่านี้สามารถเติมข้อมูลเพิ่มได้ ทั้งแบบอัตโนมัติหรือด้วยมือด้วยแอตทริบิวต์กำหนดเอง (หรือที่เรียกว่าป้ายกำกับหรือเมตาดาต้า) ซึ่งอาจประกอบด้วยข้อมูลเฉพาะทางธุรกิจ การคำนวณระหว่างขั้นตอน หรือบริบทอื่นๆ ที่อาจช่วยในการดีบักหรือวิเคราะห์ เช่น `user_id`, `session_id` หรือ `model_version`

ตัวอย่างการสร้างร่องรอยและ spans ด้วยตนเองโดยใช้ [Langfuse Python SDK](https://langfuse.com/docs/sdk/python/sdk-v3):

```python
from langfuse import get_client
 
langfuse = get_client()
 
span = langfuse.start_span(name="my-span")
 
span.end()
```

## การประเมินตัวแทน

การสังเกตการณ์ให้เมตริก แต่การประเมินเป็นกระบวนการวิเคราะห์ข้อมูลเหล่านั้น (และการทดสอบ) เพื่อกำหนดว่าตัวแทน AI ทำงานได้ดีแค่ไหนและจะปรับปรุงได้อย่างไร กล่าวอีกนัยหนึ่ง เมื่อคุณมีร่องรอยและเมตริกเหล่านั้นแล้ว คุณจะใช้มันตัดสินตัวแทนและตัดสินใจอย่างไร

การประเมินอย่างสม่ำเสมอสำคัญเพราะตัวแทน AI มักไม่สามารถคาดเดาได้และพัฒนาไปตามกาลเวลา (ผ่านการอัปเดตหรือพฤติกรรมโมเดลที่เปลี่ยนแปลง) – หากไม่ได้ประเมิน คุณจะไม่รู้ว่า “ตัวแทนอัจฉริยะ” ของคุณทำงานได้ดีจริงหรือถดถอยลง

มีการประเมินสองประเภทสำหรับตัวแทน AI: **การประเมินออนไลน์** และ **การประเมินออฟไลน์** ทั้งคู่มีคุณค่าและเสริมกัน เรามักเริ่มด้วยการประเมินออฟไลน์ เพราะเป็นขั้นตอนขั้นต่ำที่จำเป็นก่อนนำตัวแทนไปใช้งานจริง

### การประเมินออฟไลน์

![Dataset items in Langfuse](https://langfuse.com/images/cookbook/example-autogen-evaluation/example-dataset.png)

เกี่ยวข้องกับการประเมินตัวแทนในสภาพแวดล้อมที่ควบคุมได้ โดยปกติใช้ชุดข้อมูลทดสอบ ไม่ใช่คำถามจากผู้ใช้จริง คุณใช้ชุดข้อมูลที่คัดสรรซึ่งคุณรู้ว่าผลลัพธ์หรือพฤติกรรมที่ถูกต้องเป็นอย่างไร แล้วรันตัวแทนของคุณบนชุดข้อมูลเหล่านั้น

เช่น ถ้าคุณสร้างตัวแทนแก้โจทย์คณิตศาสตร์ อาจมี [ชุดข้อมูลทดสอบ](https://huggingface.co/datasets/gsm8k) ของปัญหา 100 ข้อที่มีคำตอบที่รู้จัก การประเมินออฟไลน์มักทำในระหว่างพัฒนา (และอาจเป็นส่วนหนึ่งของ pipeline CI/CD) เพื่อตรวจสอบการปรับปรุงหรือป้องกันการถดถอย ข้อดีคือมัน **ทำซ้ำได้และคุณได้เมตริกความแม่นยำที่ชัดเจนเพราะมีความจริงฐานข้อมูล (ground truth)** คุณยังอาจจำลองคำถามผู้ใช้และวัดคำตอบของตัวแทนเทียบกับคำตอบที่ดีที่สุด หรือใช้เมตริกอัตโนมัติตามที่อธิบายไว้ข้างต้น

ความท้าทายหลักกับการประเมินออฟไลน์คือการทำให้ชุดข้อมูลทดสอบของคุณครอบคลุมและยังคงสอดคล้อง — ตัวแทนอาจทำงานได้ดีในชุดทดสอบที่ตายตัวแต่เจอคำถามจริงในผลิตภัณฑ์ที่แตกต่างมาก ดังนั้นจึงควรอัปเดตชุดทดสอบอย่างสม่ำเสมอด้วยกรณีที่ไม่ปกติและตัวอย่างใหม่ที่สะท้อนสถานการณ์จริง การผสมผสานระหว่างชุดทดสอบเล็กๆ (“smoke test”) กับชุดประเมินที่ใหญ่ขึ้นมีประโยชน์: ชุดเล็กสำหรับตรวจสอบด่วน และชุดใหญ่เพื่อวัดประสิทธิภาพโดยรวม

### การประเมินออนไลน์

![Observability metrics overview](https://langfuse.com/images/cookbook/example-autogen-evaluation/dashboard.png)

หมายถึงการประเมินตัวแทนในสภาพแวดล้อมจริงแบบออนไลน์ คือ ในระหว่างการใช้งานจริง การประเมินออนไลน์เกี่ยวข้องกับการติดตามประสิทธิภาพของตัวแทนจากปฏิสัมพันธ์จริงกับผู้ใช้และวิเคราะห์ผลลัพธ์อย่างต่อเนื่อง

ตัวอย่างเช่น คุณอาจติดตามอัตราความสำเร็จ คะแนนความพึงพอใจของผู้ใช้ หรือเมตริกอื่น ๆ บนทราฟฟิกจริง ข้อดีของการประเมินออนไลน์คือมัน **จับสิ่งที่คุณอาจไม่คาดการณ์ในห้องแล็บ** — คุณสามารถสังเกตพฤติกรรมโมเดลดริฟต์ได้เมื่อเวลาผ่านไป (ถ้าประสิทธิภาพของตัวแทนลดลงเมื่อรูปแบบข้อมูลป้อนเข้ามีการเปลี่ยนแปลง) และจับคำถามหรือสถานการณ์ที่ไม่อยู่ในชุดข้อมูลทดสอบ นอกจากนี้ยังให้ภาพที่แท้จริงของพฤติกรรมตัวแทนในโลกจริง

การประเมินออนไลน์มักเกี่ยวข้องกับการเก็บคำติชมทั้งอย่างชัดเจนและโดยนัยของผู้ใช้ ดังที่กล่าวไป และอาจรวมถึงการทดสอบแบบเงาหรือ A/B ทดสอบ (ที่เวอร์ชันใหม่ของตัวแทนทำงานคู่ขนานเพื่อเปรียบเทียบกับรุ่นเดิม) ความท้าทายคือการได้ฉลากหรือคะแนนที่เชื่อถือได้จากปฏิสัมพันธ์จริง อาจพึ่งพาคำติชมของผู้ใช้ หรือเมตริกทางลึก (เช่น ผู้ใช้คลิกผลลัพธ์หรือไม่)

### การรวมกันของทั้งสองแบบ

การประเมินออนไลน์และออฟไลน์ไม่ได้แยกขาดจากกัน แต่เสริมกันได้ดี ข้อมูลเชิงลึกจากการติดตามออนไลน์ (เช่น ประเภทคำถามผู้ใช้ใหม่ที่ตัวแทนทำงานไม่ดี) สามารถใช้เพิ่มชุดข้อมูลทดสอบออฟไลน์ได้ ในทางกลับกัน ตัวแทนที่ทำงานดีในชุดทดสอบออฟไลน์สามารถนำไปใช้ในสภาพแวดล้อมจริงและติดตามได้อย่างมั่นใจ

จริงๆ แล้ว ทีมงานหลายทีมใช้วงจรเช่นนี้:

_ประเมินออฟไลน์ -> นำไปใช้ -> ติดตามออนไลน์ -> รวบรวมกรณีล้มเหลวใหม่ -> เพิ่มเข้าสู่ชุดข้อมูลออฟไลน์ -> ปรับปรุงตัวแทน -> ทำซ้ำ_

## ปัญหาทั่วไป

ขณะนำตัวแทน AI ไปใช้งานจริง คุณอาจพบกับความท้าทายต่างๆ นี่คือปัญหาทั่วไปและวิธีแก้ไขที่เป็นไปได้:

| **ปัญหา**    | **ทางแก้ไขที่เป็นไปได้**   |
| ------------- | ------------------ |
| ตัวแทน AI ทำงานไม่สม่ำเสมอ | - ปรับแต่งคำสั่งที่ส่งให้ตัวแทนให้ชัดเจนเรื่องเป้าหมาย<br>- กำหนดแบ่งงานเป็นงานย่อยและให้ตัวแทนหลายตัวดูแลในส่วนต่าง ๆ |
| ตัวแทน AI ติดอยู่ในลูปไม่มีที่สิ้นสุด  | - มีเงื่อนไขการยุติที่ชัดเจนให้ตัวแทนรู้ว่าเมื่อไรควรหยุด<br>- สำหรับงานที่ซับซ้อนและต้องใช้เหตุผลและการวางแผน ใช้โมเดลขนาดใหญ่ที่เชี่ยวชาญงานเหล่านี้ |
| การเรียกใช้เครื่องมือของตัวแทน AI ไม่ดี   | - ทดสอบและตรวจสอบผลลัพธ์ของเครื่องมือแยกกันนอกระบบตัวแทน<br>- ปรับแต่งพารามิเตอร์ คำสั่ง และการตั้งชื่อของเครื่องมือ |
| ระบบหลายตัวแทนทำงานไม่สม่ำเสมอ | - ปรับแต่งคำสั่งที่ส่งให้แต่ละตัวแทนให้เฉพาะเจาะจงและแตกต่างกัน<br>- สร้างระบบลำดับชั้นโดยใช้ตัวแทนควบคุม (routing/controller) เพื่อตัดสินใจว่าตัวแทนใดถูกต้อง |

หลายปัญหาเหล่านี้สามารถระบุได้ดียิ่งขึ้นเมื่อมีการสังเกตการณ์ ประเภทของร่องรอยและเมตริกที่กล่าวถึงก่อนหน้านี้ช่วยชี้จุดที่เกิดปัญหาใน workflow ของตัวแทน ทำให้การดีบักและการปรับแต่งมีประสิทธิภาพมากขึ้น

## การจัดการค่าใช้จ่าย
นี่คือกลยุทธ์บางประการในการจัดการค่าใช้จ่ายในการนำ AI agents ไปใช้งานจริง:

**การใช้โมเดลขนาดเล็ก:** Small Language Models (SLMs) สามารถทำงานได้ดีในกรณีการใช้งาน agentic บางประเภท และจะช่วยลดค่าใช้จ่ายอย่างมาก ดังที่ได้กล่าวไปแล้ว การสร้างระบบประเมินผลเพื่อกำหนดและเปรียบเทียบประสิทธิภาพกับโมเดลขนาดใหญ่เป็นวิธีที่ดีที่สุดในการเข้าใจว่า SLM จะทำงานได้ดีเพียงใดในกรณีใช้งานของคุณ พิจารณาการใช้ SLM สำหรับงานที่ง่ายกว่าตัวอย่างเช่น การจำแนกเจตนา หรือการสกัดพารามิเตอร์ ขณะเดียวกันเก็บโมเดลขนาดใหญ่ไว้ใช้กับงานที่ต้องการเหตุผลซับซ้อน

**การใช้โมเดล Router:** กลยุทธ์ที่คล้ายกันคือการใช้ความหลากหลายของโมเดลและขนาด คุณสามารถใช้ LLM/SLM หรือฟังก์ชันแบบเซิร์ฟเวอร์เลสในการกำหนดเส้นทางคำขอตามความซับซ้อนไปยังโมเดลที่เหมาะสมที่สุด ซึ่งจะช่วยลดค่าใช้จ่ายในขณะเดียวกันก็ช่วยให้มั่นใจได้ว่ามีประสิทธิภาพในงานที่ถูกต้อง ตัวอย่างเช่น กำหนดเส้นทางคำถามง่ายไปยังโมเดลขนาดเล็กและเร็วกว่า และใช้โมเดลขนาดใหญ่ที่มีค่าใช้จ่ายสูงเฉพาะสำหรับงานเหตุผลซับซ้อน

**การเก็บแคชคำตอบ:** การระบุคำขอและงานที่พบบ่อยและให้คำตอบล่วงหน้าก่อนที่จะผ่านระบบ agentic ของคุณเป็นวิธีที่ดีในการลดปริมาณคำขอที่คล้ายคลึงกัน คุณยังสามารถสร้างกระบวนการเพื่อระบุความคล้ายคลึงของคำขอกับคำขอที่เก็บแคชไว้โดยใช้โมเดล AI ที่พื้นฐานกว่า กลยุทธ์นี้สามารถลดค่าใช้จ่ายอย่างมากสำหรับคำถามที่ถามบ่อยหรือ workflow ที่พบบ่อย
