# ထုတ်လုပ်မှုရှိ AI Agent များ: ကြည့်ရှုနိုင်မှုနှင့် အကဲဖြတ်ခြင်း

[![AI Agents in Production](../../../translated_images/my/lesson-10-thumbnail.2b79a30773db093e.webp)](https://youtu.be/l4TP6IyJxmQ?si=reGOyeqjxFevyDq9)

AI agent များသည် စမ်းသပ်မှု prototype များမှ အမှန်တကယ် အသုံးချနိုင်သော application များသို့ ရွှေ့ပြောင်းလာသည်နှင့်အမျှ၊ ၎င်းတို့၏ အပြုအမှုကို နားလည်ခြင်း၊ ထိန်းကြပ်စစ်ဆေးခြင်းနှင့် output များကို စနစ်တကျ အကဲဖြတ်ခြင်း၏ အရေးပါမှု တိုးလာသည်။

## သင်ကြားသင့်သည့် အချက်များ

ဤသင်ခန်းစာပြီးမြောက်ပြီးနောက် သင်သည်အောက်ပါအချက်များကို နားလည်ပြီး သိရှိထားမည်။
- Agent ကြည့်ရှုနိုင်မှုနှင့် အကဲဖြတ်မှု၏ အခြေခံအယူအဆများ
- Agent များ၏ အရည်အသွေး၊ ကုန်ကျစရိတ်နှင့် ထိရောက်မှု တိုးတက်စေရန် နည်းပညာများ
- သင့် AI agent များကို စနစ်တကျ ရှာဖွေ အကဲဖြတ်ရန် ဘာများနှင့် ဘယ်လိုလုပ်ရမည်ကို
- AI agent များကို ထုတ်လုပ်မှုသို့ ထည့်သွင်းရာတွင် ကုန်ကျစရိတ် ထိန်းချုပ်နည်း
- Microsoft Agent Framework ဖြင့် တည်ဆောက်ထားသော agent များကို instrument လုပ်နည်း

ရည်ရွယ်ချက်မှာ သင့် "black box" agent များကို ကြည်လင်မြင်သာ၊ စနစ်တကျ ထိန်းချုပ်နိုင်ပြီး ယုံကြည်စိတ်ချရသော စနစ်များအဖြစ် ပြောင်းလဲနိုင်ရန် လိုအပ်သော သိပ္ပံပညာနှင့် အတတ်ပညာများ ပေးဆောင်ခြင်းဖြစ်သည်။

_**မှတ်ချက်။** AI Agent များကို လုံခြုံပြီး ယုံကြည်စိတ်ချရသောအတိုင်း ထုတ်လုပ်မှုတွင် ထည့်သွင်းရန် အလွန် အရေးကြီးပါသည်။ [Building Trustworthy AI Agents](../06-building-trustworthy-agents/README.md) သင်ခန်းစာကိုလည်း ကြည့်ပါ။_

## Traces နှင့် Spans

ကြည့်ရှုနိုင်မှုကိရိယာများဖြစ်သော [Langfuse](https://langfuse.com/) သို့မဟုတ် [Microsoft Foundry](https://learn.microsoft.com/en-us/azure/ai-foundry/what-is-azure-ai-foundry) သည် agent လည်ပတ်မှုများကို traces နှင့် spans အဖြစ် ကိုယ်စားပြုလေ့ရှိသည်။

- **Trace** သည် စတင်ကတည်းက အပြီးဆုံးအထိ သက်ဆိုင်သော agent တာဝန်တစ်ခုလုံးကို ကိုယ်စားပြုသည် (ဥပမာ - အသုံးပြုသူ တွေ့ဆုံမှု တုံ့ပြန်မှု)
- **Spans** သည် trace အတွင်း တစ်ဆင့်ချင်း ကိုယ်စားပြုသော လုပ်ငန်းအပိုင်းများဖြစ်သည် (ဥပမာ - ဘာသာစကားမော်ဒယ်ခေါ်သည် သို့မဟုတ် ဒေတာ ရယူသည်)

ကြည့်ရှုနိုင်မှုမရှိပါက AI agent သည် "black box" တစ်ခုကဲ့သို့ဖြစ်နိုင်ပြီး ၎င်း၏ အတွင်းအခြေအနေ နှင့် ချဉ်းကပ်နည်းများ မမြင်သာကြောင်းဖြင့် ပြဿနာများ သုံးသပ်ရန် သို့မဟုတ် အမြင့်မားဆုံး ထိရောက်မှု ရရှိစေရန် ခက်ခဲသည်။ ကြည့်ရှုနိုင်မှုဖြင့် agent များသည် "glass boxes" ခံစားချက်ရပြီး ယုံကြည်စိတ်ချမှု တည်ဆောက်ရာတွင် မရှိမဖြစ် လိုအပ်သော ထင်ရှား ကြည်လင်မြင်သာမှုကို ပေးပါသည်။

## ထုတ်လုပ်မှု ပတ်ဝန်းကျင်များတွင် ကြည့်ရှုနိုင်မှု အရေးကြီးသော အကြောင်းရင်းများ

AI agent များကို ထုတ်လုပ်မှု ပတ်ဝန်းကျင်သို့ ရွှေ့ပြောင်းမှုသည် စိန်ခေါ်မှုများနှင့် တောင်းဆိုချက်အသစ်များကို ဖန်တီးပေးသည်။ ကြည့်ရှုနိုင်မှုသည် "ရသေးလို့ကောင်း" ဖြစ်ခြင်းမဟုတ်ဘဲ အရေးကြီးသော စွမ်းရည်တစ်ခု ဖြစ်လာသည်။

*   **Debugging နှင့် အကြောင်းရင်းရှာဖွေရေး**: Agent တစ်ယောက် မအောင်မြင်လျှင် သို့မဟုတ် မမှန်ကန်သော output ထုတ်လွှင့်လျှင်၊ ကြည့်ရှုနိုင်မှုကိရိယာများသည် အမှားရင်းမြစ်ကို ရှာဖွေရန်လိုအပ်သော trace များကို ပေးသည်။ ၎င်းသည် LLM ခေါ်ဆိုမှုများစွာ၊ ကိရိယာပေါင်းများစွာနှင့် အခြေအနေ ဂရမ်မာရှိသော agent များတွင် အထူးအရေးပါသည်။
*   **Latency နှင့် ကုန်ကျစရိတ် စီမံခန့်ခွဲမှု**: AI agent များသည် token သို့မဟုတ် ခေါ်ဆိုမှုတစ်ခါတည်းဖြင့် ဘီလ်ထုတ်သော LLM များနှင့် အခြား APIs များကို မကြာခဏ အားထားသည်။ ကြည့်ရှုနိုင်မှုကိရိယာသည် ၎င်းခေါ်ဆိုမှုတို့ကို တိကျစွာ မှတ်တမ်းတင်စေကာ ဆွဲဆောင်မှုကို မြှင့်တင်ရန် အသုံးချရမည့် လုပ်ဆောင်ချက်များကို ရှာဖွေခြင်း၊ ပုံစံများရွေးချယ်ခြင်း သို့မဟုတ် Workflow များပြန်လည် အပြင်အဆင်ပြုခြင်းများကို လုပ်ဆောင်နိုင်သည်။
*   **ယုံကြည်မှု၊ လုံခြုံမှုနှင့် လိုက်နာမှု**: အများအပြား application များတွင် agent များသည် အန္တရာယ်ကင်းရှင်းပြီး တရားဝင်လူမှုထိန်းသိမ်းမှုကို လိုက်နာသည့်အတိုင်း အပြုအမှု ပြုလုပ်ရမည်။ ကြည့်ရှုနိုင်မှုသည် agent လုပ်ဆောင်မှုနှင့် ဆုံးဖြတ်ချက်အတောင်းများအတွက် စစ်ဆေးနိုင်မှု အသွင်ကူးပုံကို ပေးသည်။ ၎င်းသည် prompt injection၊ စွန့်ပစ်ရမည့် မဟုတ်သောအကြောင်းအရာများထုတ်လုပ်ခြင်း သို့မဟုတ် အမည်ရှိသူ သတင်းအချက်အလက်မှားသုံးစွဲမှုများကို တားဆီးနိုင်ရန် အတွက် အသုံးပြုနိုင်သည်။ ဥပမာ၊ trace များကို ပြန်လည်ကြည့်ရှု၍ agent တစ်ယောက်သည် ကွ particular ိုသော တုံ့ပြန်မှုမည်ရေး ြော ို တို့ သုံးခဲ့သည်ကို နားလည်နိုင်သည်။
*   **ဆက်လက်တိုးတက်မှု အပြန်အလှန်လှည့်ခန်းများ**: ကြည့်ရှုနိုင်မှုဒေတာသည် ဖြစ်ပေါ်မှုမြှင့်တင်ရေးလုပ်ငန်းစဉ်၏ အခြေခံဖြစ်သည်။ အကောင်အထည်ဖြစ်စဉ်တွင် agent များ၏ အပြုအမှုကို ကြည့်ရှု၍ တိုးတက်အကျိုးရှိသော နယ်ပယ်များ ရှာဖွေကူညီပေးကာ မော်ဒယ်များကို သိသင့်သည့် ဒေတာများစုဆောင်းခြင်းနှင့် ပြင်ဆင်မှုတို့ကို စစ်ဆေးတည်ဆောက်နိုင်သည်။ ၎င်းသည် ထုတ်လုပ်မှုအမြင်များကို အွန်လိုင်းအကဲဖြတ်ခြင်းမှ ကောက်ချက်များ ဆောင်ကြဉ်း၍ အော့ဖ်လိုင်း စမ်းသပ်ပြီး ပြင်ဆင်မှုလုပ်ငန်းစဉ်များကို အမြဲတမ်းတိုးတက်စေသည်။

## လိုက်နာစောင့်ကြည့်သင့်သည့် အချက်အလက်များ

Agent အပြုအမှုကို ညှိနှိုင်းနှင့် နားလည်ရန် metrics နှင့် signal များစွာကို စောင့်ကြည့်ရမည်။ အချက်အလက်များသည် agent ၏ ရည်ရွယ်ချက်ပေါ်မူတည်၍ ကွဲပြားနိုင်သော် သာမန်မှာ အောက်ပါအချက်များ အရေးပါသည်။

ကြည့်ရှုနိုင်မှုကိရိယာများသည် စောင့်ကြည့်သော အဓိက metrics များအချို့မှာ အောက်ပါအတိုင်းဖြစ်သည် -

**Latency:** Agent ၏ တုံ့ပြန်မှုအမြန်နှုန်း ကဟုတ်သလား? စောင့်ဆိုင်းချိန်ကြာခဲခြင်းသည် အသုံးပြုသူအတွေ့အကြုံကို ဆိုးရွားစေသည်။ တစ်ခုချင်း task နှင့် တစ်ဆင့်စီကို trace မှတဆင့် latency ကိုတိုင်းတာရမည်။ ဥပမာ - ၂၀ စက္ကန့်ကြာသော agent မှ မြန်ဆန်သော မော်ဒယ် သို့မဟုတ် သင်တန်းတူတစ်ပြိုင်နက်တွင် ခေါ်ဆိုမှုများပြုလုပ်ခြင်းဖြင့် မြန်မြန်ဆန်ဆန်လုပ်နိုင်သည်။

**ကုန်ကျစရိတ်:** Agent တစ်ကြိမ်လည်ပတ်စဉ်၏ တန်ဖိုးဟု ဘယ်လောက်အများကြီးကြေးနှုန်းရှိနေလဲ? AI agent များသည် token တစ်ခုလျှင်သို့မဟုတ် API ခေါ်ဆိုမှုတိုင်းအတွက် ဘီလ်ထုတ်ခံသည်။ အတော်များများသော ကိရိယာနှင့် ပြန်ခေါ်စကားများသည် စရိတ်ကို မြင့်တက်စေသည်။ ဥပမာ - Agent တစ်ယောက်မှာ marginal quality တိုးတက်စေရန် LLM ကို ငါးကြိမ် ခေါ်လျှင် လိုအပ်ချက်ကို သုံးသပ်ပြီး ခေါ်ဆိုမှုပမာဏကို လျော့ချရန် သို့မဟုတ် စရိတ်သက်သာသော မော်ဒယ်တစ်ခု အသုံးပြုရန် ဆုံးဖြတ်ရမည်။ အချိန်နဲ့တပြေးညီ စိစစ်ခြင်းဖြင့် မမျှော်လင့်ထားသောအပူပြင်းများ ဖော်ထုတ်နိုင်သည် (ဥပမာ - API loops များများစွာဖြစ်စေသော bug များ)။

**တောင်းဆိုမှုအမှားများ:** Agent သည် မည်မျှသော တောင်းဆိုမှုများ မအောင်မြင်ခဲ့ပါသလဲ? ၎င်းတွင် API အမှားများ သို့မဟုတ် ကိရိယာခေါ်ဆိုမှု မအောင်မြင်မှုများ ပါဝင်နိုင်သည်။ ထုတ်လုပ်မှုတွင် agent ကို ပိုမိုခိုင်မာစေလိုပါက fallback များ သို့မဟုတ် retry များ set up ပြုလုပ်နိုင်သည်။ ဥပမာ - LLM ပံ့ပိုးသူ A တိတ်ဆိတ်နေပါက LLM ပံ့ပိုးသူ B ကို backup အဖြစ် ရွှေ့ပြောင်းနိုင်သည်။

**အသုံးပြုသူ တုံ့ပြန်ချက်:** တိုက်ရိုက် user evaluation များ အတုယူရန် တန်ဖိုးရှိသော အချက်အလက်များ ထည့်သွင်းပါ။ ၎င်းတွင် ပြင်းထန်သော rating များ (👍thumbs-up/👎down၊ ⭐1-5 ကြယ်) သို့မဟုတ် စာသားဝေဖန်ချက်များ ပါဝင်နိုင်သည်။ ဆက်တိုက် မကောင်းသော feedback များက agent မစောင့်မနေသော သဘောရှိကြောင်း သတိပေးသည်။

**မှတ်မိသိထားသော အသုံးပြုသူ feedback:** အသုံးပြုသူများ၏ အပြုအမူများသည် rating မရှိပဲလည်း အကြောင်းပြန်များ ပေးသည်။ ဤအတိုင်းအတာတွင် စကားမေးခွန်းအလျင်တုန့်ပြန်မှု၊ ထပ်ခါထပ်ခါ မေးခွန်းမေးခြင်း သို့မဟုတ် retry ခလုတ်နှိပ်ခြင်း ပါဝင်သည်။ ဥပမာ - အသုံးပြုသူများ အတုတော်ကြီးတူသောမေးခွန်း မေးလျှင် agent တွင် ပြဿနာရှိသည်ကို ပြသသည်။

**တိကျမှု:** Agent သည် မှန်ကန်သော output များထုတ်လုပ်မှု ဘယ်လောက်များရှိသနည်း? တိကျမှု၏ နောက်ခံ ပြင်ဆင်မှုများကွဲပြားနိုင်သည် (ဥပမာ - ပြဿနာဖြေရှင်းမှုမှန်ကန်မှု၊ သတင်းအချက်အလက် ရယူမှု တိကျမှု၊ အသုံးပြုသူကျေနပ်မှု)။ ပထမဆင့်တွင် သင့် agent အတွက် အောင်မြင်မှုပုံစံကို သတ်မှတ်ရမည်။ တိကျမှုကို automated စစ်ဆေးမှုများ၊ အကဲဖြတ်မှတ်ဆိုင်များ သို့မဟုတ် task ပြီးမြောက်မှု လက္ခဏာများမှတဆင့် တိုင်းတာနိုင်သည်။ ဥပမာ - trace များကို "succeeded" သို့မဟုတ် "failed" အဖြစ် အမှတ်ပေးခြင်း။

**အလိုအလျောက် အကဲဖြတ် နည်းများ:** Automated eval များလည်း တင်ဆက်နိုင်သည်။ ဥပမာ - LLM ကို အသုံးပြု၍ agent ၏ output ကို အကဲဖြတ် scoring ပြုလုပ်နိုင်သည်။ agent output မှာ အထောက်အကူပြုမှု၊ တိကျမှု၊ မရှိမှု စသည့် element များကို စစ်ဆေးနိုင်သည်။ RAG agent များအတွက် [RAGAS](https://docs.ragas.io/) သို့မဟုတ် Language ဆိုးရွားမှုသတိပေး Guard tool တို့လိုမျိုး လုပ်ဆောင်ချက်များဖြစ်စေသော open source libraries များလည်း ရှိသည်။ [LLM Guard](https://llm-guard.com/) သည် ဟာရီသော ဘာသာစကား သို့မဟုတ် prompt injection ကို မွမ်းမံဖော်ထုတ်ခြင်းတွင် အသုံးပြုသည်။

လက်တွေ့၌၊ ဤ metrics များ ပေါင်းစပ်မှုမှ AI agent ၏ ကျန်းမာရေးကို အကောင်းဆုံး ဖော်ပြနိုင်သည်။ ၎င်းတို့ကို ဤအခန်းမှ [နမူနာ notebook](./code_samples/10-expense_claim-demo.ipynb) တွင် ကိုယ်စားပြု ကုသိုလ်ချက်ကြည့်ရှုမှာဖြစ်ပြီး ပထမဆုံး typical evaluation workflow ကိုလည်း သင်ယူပါမည်။

## သင့် Agent ကို Instrument လုပ်ပါ

tracing ဒေတာ စုဆောင်းရန် အတွက် သင့် code ကို instrument လုပ်ဖို့ လိုအပ်သည်။ ရည်ရွယ်ချက်မှာ agent code တွင် tracing နှင့် metric များ ထုတ်ပေး၍ ကြည့်ရှုနိုင်သည့် စနစ်တစ်ခုမှ ဖမ်းယူ၊ ပြန်လည်သုံးသပ်၊ ပြသနိုင်ရန် ဖြစ်သည်။

**OpenTelemetry (OTel):** [OpenTelemetry](https://opentelemetry.io/) သည် LLM ကြည့်ရှုနိုင်မှု အတွက် စက်မှုလုပ်ငန်းစံပြ တစ်ခုဖြစ်လာသည်။ ၎င်းသည် telemetry data ထုတ်လုပ်ခြင်း၊ စုဆောင်းခြင်းနှင့် တင်ပို့ရေး အတွက် API များ၊ SDK များနှင့် ကိရိယာများ စုပေါင်းပေးသည်။

instrument လုပ်ရာတွင် လုပ်ဆောင်ချက် ရှိသော library များစွာရှိသည်။ ၎င်း libraries များသည် agent framework များကို ဖုံးကွင်းပြီး OpenTelemetry span များကို ကြည့်ရှုနိုင်သောကိရိယာသို့ အလွယ်တကူ တင်ပို့နိုင်စေသည်။ Microsoft Agent Framework သည် OpenTelemetry နှင့် ပေါင်းစပ်ထားပြီး အောက်ပါဥပမာမှာ MAF agent instrument လုပ်ခြင်းဖြစ်သည် -

```python
from agent_framework.observability import get_tracer, get_meter

tracer = get_tracer()
meter = get_meter()

with tracer.start_as_current_span("agent_run"):
    # ကိုယ်စားလှယ် ဆောင်ရွက်ချက်ကို အလိုအလျောက် လိုက်လံ မှတ်တမ်းတင်ထားသည်
    pass
```

ဤအခန်းရှိ [နမူနာ notebook](./code_samples/10-expense_claim-demo.ipynb) မှတဆင့် သင့် MAF agent ကို instrument လုပ်နည်းကို ပြသပေးမည်။

**Manual Span Creation:** Instrumentation library များသည် မူလအခြေခံကို ကောင်းစွာ အသုံးပြုစေသော်လည်း အသေးစိတ်နေရာ သို့မဟုတ် အသုံးအနှုန်းအသစ်များကို လိုအပ်သည့် အခါသည် manual span များကို ဖန်တီးနိုင်သည်။ အဓိကအားဖြင့် automated သို့မဟုတ် manual span များကို စီးပွားရေးဆိုင်ရာ သတ်မှတ်ချက်များ (tag များ သို့မဟုတ် metadata) ဖြင့် အကြောင်းပြု၍ တွဲဖက် ထောက်ပံ့ပေးနိုင်သည်။ ဤ attribute များတွင် user_id, session_id သို့မဟုတ် model_version ကဲ့သို့သော များ ပါဝင်နိုင်သည်။

[Langfuse Python SDK](https://langfuse.com/docs/sdk/python/sdk-v3) ဖြင့် traces နှင့် spans ကို လက်တွေ့ပြုလုပ်ခြင်း၏ ဥပမာ-

```python
from langfuse import get_client
 
langfuse = get_client()
 
span = langfuse.start_span(name="my-span")
 
span.end()
```

## Agent အကဲဖြတ်ခြင်း

ကြည့်ရှုနိုင်မှုသည် metric များပေးသော်လည်း အကဲဖြတ်ခြင်းသည် ထိုဒေတာများကို လေ့လာသုံးသပ်၍ AI agent ၏ လုပ်ဆောင်ချက် ဘယ်လိုဖြစ်နေသည်၊ ဘယ်လိုတိုးတက်အောင်ပြုလုပ်မည်ကို ဆုံးဖြတ်ခြင်းဖြစ်သည်။ ၎င်းကတော့ trace နှင့် metrics ရယူပြီးနောက် Agent ကို စိစစ်သည်ကို ဆိုလိုသည်။

AI agent များသည် ပုံမှန်အားဖြင့် non-deterministic ဖြစ်ပြီး အသစ်ပြောင်းလဲမှုများ (update များ သို့မဟုတ် model drift) ဖြစ်နိုင်သောကြောင့် ဖြစ်စဉ်တွေမရှိရင်၊ "smart agent" သည် အလုပ်ကောင်းမလုပ်သည့် ဒါမှမဟုတ် regress ဖြစ်သွားသည်ကို သင် မသိနိုင်ပါ။

AI agent များအတွက် အကဲဖြတ်ရေးနှစ်မျိုးရှိသည် - **online evaluation** နှင့် **offline evaluation**။ နှစ်မျိုးလုံးမှာ တန်ဖိုးရှိပြီး တစ်ရပ်တည်းဖြစ်သော အကျိုးတူအထောက်အကူဖြစ်သည်။ ကျွန်ုပ်တို့သည် agent တစ်ခု မတင်ပို့မီ အနည်းဆုံးလိုအပ်သည့်အဆင့်ဖြစ်သည့် offline evaluation မျှပထမတစ်ဆင့်အဖြစ် စတင်လေ့လာသည်။

### Offline Evaluation

![Dataset items in Langfuse](https://langfuse.com/images/cookbook/example-autogen-evaluation/example-dataset.png)

offline evaluation သည် ထိန်းချုပ်ထားသည့် ပတ်ဝန်းကျင်တွင် agent ကို စမ်းသပ်ခြင်းဖြစ်ပြီး ပုံမှန်အားဖြင့် စမ်းသပ်ဒေတာအသုံးပြု၍၊ အသက်သက်ရှိ အသုံးပြုသူမေးခွန်းများမဟုတ်ပါ။ မျှော်မှန်းထားသော output သို့မဟုတ် မှန်ကန်သော အပြုအမူကို သိရှိထားသော curated dataset များကို အသုံးပြုသည်။

ဥပမာ - သင်သည် သင်္ချာ ပေါ့စ်ပွန်းဖြေရှင်းရေး Agent တစ်ခု တည်ဆောက်ကာ [test dataset](https://huggingface.co/datasets/gsm8k) ၁၀၀ ခုရှိသည်ဟုပြောပါက စမ်းသပ် dataset များကို အသုံးပြုပြီး agent ကို စမ်းသပ်ပါမည်။ Offline evaluation ကိုဖွံ့ဖြိုးတိုးတက်စဉ်၊ CI/CD pipeline များတွင်လည်း အသုံးပြုသည်။ ၎င်း၏ အားသာချက်မှာ **ပြန်လည်လုပ်ဆောင်နိုင်ခြင်းနှင့် ground truth ရှိသို့မဟုတ် မှန်ကန်မှု metric များ ရရှိနိုင်ခြင်း** ဖြစ်သည်။ အသုံးပြုသူ မေးခွန်းများကို simulation ပြုလုပ်ပြီး ideal response နဲ့ နှိုင်းယှဉ်တာဝန်ကို တိုင်းတာနိုင်သည်။

Offline evaluation ၏ အဓိက စိန်ခေါ်မှုမှာ စမ်းသပ် dataset ကို ကျယ်ပြန့်၍ သက်ဆိုင်မှုရှိစေရန် ဖြစ်ပြီး Production မှာ ပထမဦးဆုံး မူကား မတူညီသော မေးခွန်းများ ကြုံတွေ့နိုင်သည်။ ထို့ကြောင့် စမ်းသပ် dataset များကို အသစ်ထပ်မံထည့်သွင်းပြီး edge case များနှင့် နမူနာနောက်ထပ်များဖြင့် update ဖို့ လိုသည်။ ကျဉ်းမြောင်းသော "smoke test" များနှင့် ကျယ်ပြန့်သော evaluation sets များကို အားလုံးပေါင်းစပ်အသုံးပြုပါ။

### Online Evaluation 

![Observability metrics overview](https://langfuse.com/images/cookbook/example-autogen-evaluation/dashboard.png)

အဓိက သုံးစွဲမှု ပတ်ဝန်းကျင်၊ ထုတ်လုပ်မှုတွင် ကိုယ်တိုင် agent ကို စစ်ဆေးလေ့လာခြင်းဖြစ်သည်။ Online evaluation သည် တိုက်ရိုက် အသုံးပြုသူ တွဲလျက် လည်ပတ်ခြင်း performance ကို သတင်းအချက်အလက် စနစ်တကျ စူးစမ်းသုံးသပ်ခြင်း ဖြစ်သည်။

ဥပမာ - စွမ်းဆောင်ရည်အောင်မြင်မှုနှုန်း၊ အသုံးပြုသူ ကျေနပ်မှု အဆင့်များ သို့မဟုတ် အခြား metric များကို ပြခန်းရှိအားဖြင့် မှတ်တမ်းတင်သည်။ Online evaluation ၏ အားသာချက်မှာ **ဓာတ်ခွဲခန်းတွင် မမြင်ရသည့် အချက်များကို ဖော်ထုတ်နိုင်ခြင်း** ဖြစ်ပြီး agent ၏ ထိရောက်မှုသည် input ပုံစံများ ပြောင်းလဲသည့်အခါ model drift ဖြစ်နိုင်ခြင်းကို တွေ့ရှိနိုင်သည်။ အချို့ မျှော်လင့်မထားသော မေးခွန်းများ သို့မဟုတ် အခြေအနေများကိုလည်း သိရှိနိုင်သည်။ ထို့ကြောင့် agent ၏ တကယ်ပြုလုပ်နေသည့်အတိုင်း သဘာဝကိုတိတိကျကျ ဖော်ပြပေးသည်။

Online evaluation တွင် ထိတွေ့/မထိတွေ့ user feedback များ စုဆောင်းပြီး A/B test သို့မဟုတ် shadow testing များ လုပ်နိုင်သည် (agent version အသစ်ကို agent လက်ရှိနဲ့ မတူညီသည်ကို နှိုင်းယှဉ်ရန် parallel တွင် run ပြုလုပ်ခြင်း)။ ပြဿနာမှာ live interaction များအတွက် ယုံကြည်လို့ရမည့် label များ သို့မဟုတ် score များ ရရန်ခက်ခဲပါသည် – အသုံးပြုသူ feedback သို့မဟုတ် downstream metrics (ဥပမာ - user result ကို ကလစ်နှိပ်ခဲ့ပါသလား) အားမှာ ယုံကြည်ရန်လိုသည်။

### နှစ်ခု ပေါင်းစပ်ခြင်း

Online နှင့် offline evaluation များသည် မတူညီခြားနားမှု မရှိပေ၊ အတူတကွ အားဖြည့်ပေးညီမျှသည်။ Online စောင့်ကြည့်မှုမှ ရရှိသည့် အချက်အလက်များ (ဥပမာ - agent မကောင်းသော အသုံးပြုသူ မေးခွန်းအသစ်များ) သည် offline စမ်းသပ် dataset များ ကို တိုးချဲ့ကူညီပေးနိုင်သည်။ အကြောင်းရင်းအားဖြင့် offline စမ်းသပ်မှုတွင် အောင်မြင်သော agent များသည် ထို့နောက် online တွင် ပိုမိုယုံကြည်စိတ်ချစွာ deploy လုပ်နိုင်ပြီး စောင့်ကြည့်နိုင်သည်။

အမှန်တကယ်တော့ အဖွဲ့အစည်းများသည် အောက်ပါ လှည့်ပတ်အစဉ်များကို လက်ခံသည်։

_offline စမ်းသပ်သည် -> ထုတ်လုပ်မှုသို့ ထည့်သည် -> online တွင် စောင့်ကြည့်သည် -> ပြဿနာသစ်များ စုဆောင်းသည် -> offline စမ်းသပ် dataset ထည့်သည် -> agent တိုးတက်တင်ပြ ပြုလုပ်သည် -> ထပ်မံလုပ်ဆောင်သည်_။

## ရိုးရိုးရှင်းရှင်း ပြဿနာများ 

AI agent များကို ထုတ်လုပ်မှုတွင် တင်သွင်းသည့်အခါ၊ သင်သည် မျိုးဆက်စုံသော ပြဿနာများနှင့် ရင်ဆိုင်နိုင်သည်။ အောက်တိုဘာ အများဆုံးတွေ့ကြုံရသော ပြဿနာများနှင့် ၎င်းတို့အတွက်ဖြေရှင်းချက်များကို ဖော်ပြထားသည်။ 

| **ပြဿနာ**    | **ဖြေရှင်းနည်း အကြံပြုချက်**   |
| ------------- | ------------------ |
| AI Agent သည် တာဝန်များကို တပြေ့ပြေ့ မပြုလုပ်နိုင်ပါ | - AI Agent သို့ ပေးသော prompt ကို ပြင်ဆင်ပါ၊ ရည်မှန်းချက်ကို သေချာပြောပါ။<br>- တာဝန်များကို မျိုးထွက်ခွဲပြီး အော်ပရေတာ agent များဖြင့် ကိုင်တွယ်ခြင်းကို ခွဲခေါ်တာဝန်ထမ်းဆောင်မှုအတွက် ကြိုးပမ်းပါ။ |
| AI Agent သည် ဆက်လက် Loop ဝင်နေသည် | - Agent သည် အဆုံးသတ်ရေးချက်များနှင့် အခြေအနေများ ရှင်းလင်း သိရှိစေရန် သေချာစေပါ။<br>- ရှင်းလင်းစဉ်းစားရန်နှင့် စီမံခန့်ခွဲရန် လိုအပ်သော အဆင့်မြင့် မော်ဒယ်အသုံးပြုပါ။ |
| AI Agent ရဲ့ tool calls မပြည့်မစုံဖြစ်နေသည် | - Agent system အပြင်တွင် tool output များစမ်းသပ်အတည်ပြုပါ။<br>- သတ်မှတ်ထားသော parameter များ၊ prompt များ၊ tool အမည်များကို ပြင်ဆင်ပါ။  |
| Multi-Agent system သည် တပြေ့တပြေ့ မအောင်မြင်ပါ | - Agent တစ်ဦးချင်းသို့ ပေးသော prompt များကို သေချာပြင်ဆင်၍ အတူတူမဖြစ်စေရန် သေချာစေပါ။<br>- ဘယ် Agent ဖြစ်သင့်ကြောင်း သတ်မှတ်ရန် controller agent သို့မဟုတ် routing system တစ်ခု တည်ဆောက်ပါ။ |

ဤပြဿနာအများစုကို ကြည့်ရှုနိုင်မှု ရှိလျှင် ပိုမိုရိုးရှင်းစွာ တွေ့ရှိနိုင်သည်။ ယခင်က ဆွေးနွေးခဲ့သည့် trace များနှင့် metric များက agent workflow ထဲမှာ ပြဿနာ ဖြစ်ပေါ်ရာနေရာကို တိတိကျကျ ရှာဖွေခြင်း၊ debugging နှင့် ပြုပြင်ရေးကို ပိုထိရောက်စေပါသည်။

## ကုန်ကျစရိတ် စီမံခန့်ခွဲမှု


AI အေးဂျင့်များကို ထုတ်လုပ်မှုတွင် တပ်ဆင်စေနည်းလမ်းများနှင့် စရိတ်များကို စီမံခန့်ခွဲရန် များအနက်မှအချို့သည် ယခုလမ်းညွှန်မှုအောက်ပါမျိုးဖြစ်ပါသည် -

**အသေးစား မော်ဒယ်များကို အသုံးပြုခြင်း:** Small Language Models (SLMs) သည် အချို့သော agentic အသုံးအေဆာင်များတွင် ကောင်းမွန်စွာ ဆောင်ရွက်နိုင်ပြီး စရိတ်များကို အလွန်လျော့နည်းစေပါသည်။ ရှေ့တွင်ဖော်ပြခဲ့သလို အသေးစား မော်ဒယ်တစ်ခု၏ စွမ်းဆောင်ရည်နှင့် အကြီးစား မော်ဒယ်များ၏ စွမ်းဆောင်ရည်များကို နှိုင်းယှဉ်သုံးသပ်ရန် အကဲဖြတ်စနစ်တစ်ခု တည်ဆောက်ခြင်းသည် SLM သည် သင့်အသုံးအေဆာင်တွင် ဘယ်လောက်ကောင်းမွန်စွာ ဆောင်ရွက်နိုင်မည်ကို နားလည်ရန် ပိုမိုကောင်းမွန်သော နည်းလမ်းဖြစ်သည်။ ရိုးရှင်းသော အလုပ်များနဲ့ အဆင့်ပိုင်းခွဲခြားရေး (intent classification) သို့မဟုတ် ပါရာမီတာ ထုတ်ယူမှုကဲ့သို့သော အလုပ်များအတွက် SLM များကို အသုံးပြုခြင်းကို တွေးပါ၊ အခက်အခဲများသော ယူဆချက်အပြုအမူများအတွက် အကြီးစား မော်ဒယ်များကို သတ်မှတ်ထားပေးပါ။

**Router မော်ဒယ်ကို အသုံးပြုခြင်း:** ဤနည်းလမ်းတွင် မော်ဒယ်များ၊ အရွယ်အစားများ မျိုးစုံကို အသုံးပြုသည်။ LLM/SLM သို့မဟုတ် serverless function ကို အသုံးပြု၍ စုံလင်အောင် လိုအပ်ချက်များကို ကောင်းစွာသင့်လျော်သော မော်ဒယ်များအထိ လမ်းညွှန်နိုင်သည်။ ၎င်းသည် စရိတ်လျော့နည်းစေပြီး ကိစ္စတစ်ခုတွင် လုပ်ဆောင်မှုမွန်ကန်မှုကို အာမခံပေးနိုင်သည်။ ဥပမာအားဖြင့် ရိုးရှင်းသော မေးခွန်းများကို အသေးစား၊ မြန်ဆန်သော မော်ဒယ်များသို့ လမ်းညွှန်ပေးပြီး အခက်အခဲများသော ယူဆချက်အတွက်သာ တန်ဖိုးမြင့် အကြီးစားမော်ဒယ်များကို အသုံးပြုပါ။

**ဖြေကြားချက်များကို က င်အတည်ပြုထားခြင်း (Caching Responses):** မကြာခဏတွေ့ကြုံရသော တောင်းဆိုမှုများနှင့် အလုပ်များကို သတ်မှတ်ရန် နိုင်ပြီး ၎င်းကို သင့် agentic စနစ် မတိုင်မှီ ပြန်လည်ဖြေကြားပေးခြင်းဖြင့် ဆန့်ကျင်တုံ့ပြန်မှုများ၏ အရေအတွက်ကို လျော့နည်းစေပါသည်။ လေ့လာမှုတစ်ခုလည်း ရေးဆွဲ၍ Requests များကို Cached request များနှင့် ဘယ်လောက်ဆင်တူနေသည်ဆိုသော ကိုယ်တိုင့် AI မော်ဒယ်များ အသုံးပြုနိုင်သည်။ ဤနည်းလမ်းသည် မေးခွန်းများ မကြာခဏမေးမြန်းမှုများကို သို့မဟုတ် ရိုးရှင်းသော လုပ်ငန်းစဉ်များတွင် စရိတ်အလွန်လျော့နည်းစေရန် အထောက်အကူပြုနိုင်သည်။
