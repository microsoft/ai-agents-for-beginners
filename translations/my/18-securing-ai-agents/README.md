# Cryptographic Receipts များဖြင့် AI ကိုယ်စားလှယ်များကိုလုံခြုံစေရန်

## နိဒါန်း

ဤသင်ခန်းစာတွင် ဖော်ပြမည့်အကြောင်းအရာများမှာ -

- AI ကိုယ်စားလှယ်များအတွက် audit trails မည်သို့ လိုအပ်သလဲ၊ လိုက်နာမှု၊ အမှားရှာဖွေခြင်းနှင့် ယုံကြည်ခြင်းအတွက်။
- Cryptographic receipt ဆိုတာဘာလဲ၊ unsigned log line မှ မည်သို့ကွာခြားသလဲ။
- Python ရိုးရိုးဖြင့် ကိုယ်စားလှယ်၏ tool ခေါ်ဆိုမှုအတွက် စာမှတ်ရေးထားသော receipt ကို မည်သို့ ထုတ်လုပ်မလဲ။
- Receipt ကို offline မှာ စစ်ဆေးဖို့နည်းလမ်းနှင့် မဖြစ်မနေ ပြောင်းလဲမှု ရှာဖွေခြင်း။
- Receipt များကို ပေါင်းသင်္ကေတမျဉ်းဆွဲပြီး တစ်ခု ဖယ်ရှားသို့မဟုတ် အစီအစဉ်ပြောင်းလဲခြင်းဖြင့် ကွင်းဆက်ပျက်စီးခြင်း။
- Receipt များဖြင့် ဘာကို သက်သေပြနိုင်ပြီး ဘာကို မသက်သေပြနိုင်သလဲ။

## သင်ယူရန်ရည်ရွယ်ချက်များ

ဤသင်ခန်းစာပြီးဆုံးအောင်ပြုလုပ်ပြီးနောက် သင်သိရှိရမည့်အချက်များမှာ -

- ကိုယ်စားလှယ် လုပ်ဆောင်ချက်များအတွက် cryptographic provenance ကို ဖော်ဖြေစေသည့် မအောင်မြင်မှု မျိုးစုံကို ဖော်ထုတ်ခြင်း။
- Canonical JSON ပိုင်လုပ်သော ပေးပို့မှုအပေါ် Ed25519 ဖြင့် အတည်ပြုထားသော receipt ထုတ်လုပ်ခြင်း။
- အတည်ပြုသူအများလက်မှတ်အညီ Receipt ကို လွတ်လပ်စွာ စစ်ဆေးနိုင်ခြင်း။
- ပြောင်းလဲမှု ရှာဖွေရန် အတည်ပြုချက်ကို ပြန်လည်လုပ်ဆောင်ခြင်း။
- Receipt များကို hash chain ဖြင့်တပ်ဆက်ခြင်းနှင့် ၎င်းကွင်းဆက်က အကြောင်းရင်းကို ဖော်ရွေခြင်း။
- Receipt များ သက်သေပြတတ်သည့် အရာများ (သက်သေပြချက်၊ တင်းကျပမှု၊ အစဉ်လိုက်မှု) နှင့် မသက်သေပြတိုက်နယ် (လုပ်ဆောင်ချက်မှန်ကန်မှု၊ မူဝါဒဖြင့် သက်သေပြမှု) များ ခွဲခြားသိရှိခြင်း။

## ပြဿနာ: သင့်ကိုယ်စားလှယ်၏ audit trail

ကွန်တော်ဆိုတိုး ခရီးသွားလုပ်ငန်းအတွက် AI ကိုယ်စားလှယ် တစ်ယောက် ဖန်တီးထားတယ်လို့ စဥ်းစားပါ။ ကိုယ်စားလှယ်သည် ဖောက်သည်တောင်းဆိုချက်များကို ဖတ်ချက်ယူပြီး လေယာဉ်လိုင်း API ကို ခေါ်ယူကာ ရွေးချယ်မှုများလေ့လာ၊ ဖောက်သည်အတွက် လေယာဉ်လက်မှတ်များ စီစဉ်ပေးသည်။ လွန်ခဲ့သည့်သုံးလပတ်တွင် ကိုယ်စားလှယ်သည် ၅၀,၀၀၀ ခုံစာရင်း စနစ်တကျ ဆောင်ရွက်ပေးခဲ့သည်။

ယနေ့ သက်ဆိုင်ရာ စစ်ဆေးသူ တစ်ဦး ရောက်ရှိလာသည်။ ၎င်းက စာမေးခွန်း ရိုးရှင်းသွားမေးသည် - "သင့်ကိုယ်စားလှယ် ဘာလုပ်ခဲ့တယ်ဆိုတာကို ပြပါ။"

သင်သည် သင့် log ဖိုင်များကို ထမ်းပေးသည်။ စစ်ဆေးသူက ပိုခက်ခဲသည့် မေးခွန်းမေးသည် - "ဘယ်လိုသိရမလဲ၊ ဒီ log များကို ပြောင်းလဲခြင်း မရှိဘူးလို့။"

ဤသည်မှာ audit-trail ပြဿနာဖြစ်သည်။ ယနေ့အတော်များများ သင့်ကိုယ်စားလှယ် deployment များမှာ မှီငြမ်းသောအရာများမှာ -

- **အပလီကေးရှင်း log များ**: ကိုယ်စားလှယ်က ရေးသားထားပြီး ဖိုင်စနစ် အသုံးပြုသူ မည်သူမဆို ပြင်ဆင်နိုင်သည်။
- **Cloud logging services**: platform အဆင့်တွင် tamper-evident ဖြစ်ပေမယ့် စစ်ဆေးသူမှာ platform လုပ်ငန်းစီမံသူကို ယုံကြည်ရမည့်အခါသာ။
- **ဒေတာဘေ့စ် လုပ်ငန်းလမ်းညွှန် log များ**: ဒေတာဘေ့စ် ပြောင်းလဲမှုများအတွက် သင့်တော်ပေမယ့် အခြား tool ခေါ်ဆိုမှုများအတွက်တော့ မဟုတ်ပါ။

ဤအရာတိုင်းသည် စစ်ဆေးသူ၏မေးခွန်းကို တုံ့ပြန်ပေးနိုင်စေခြင်း မရှိဘဲ၊ စစ်ဆေးသူရှိသော ယုံကြည်မှု အား ဖော်ပါရန်လိုအပ်သည် (သင်၊ သင့် cloud ပံ့ပိုးသူ၊ သင့်ဒေတာဘေ့စ် ပေးသူ)။ အတွင်းပိုင်း သုံးစွဲမှုအတွက် ယုံကြည်မှုသည် ခွင့်ပြုနိုင်သော်လည်း၊ ကန့်သတ်ထားသည့် ကုန်ကျစရိတ် (ငွေကြေး၊ ကျန်းမာရေး၊ EU AI Act အောက်ခံ) အတွက် မဖြစ်နိုင်ပါ။

Cryptographic receipts များက ကိုယ်စားလှယ်တစ်ယောက်တည်းအားလုံး လွတ်လပ်စွာ စစ်ဆေးနိုင်စေရန် ဖြေရှင်းပေးသည်။ စစ်ဆေးသူသည် သင့်ကို ယုံကြည်စရာမလိုဘဲ သင့် လူမှုမှတ်တမ်းများအတွက်ပဲ public key နဲ့ receipt ကိုသာ လိုအပ်ပါသည်။

## Cryptographic Receipt ဆိုတာဘာလဲ?

Receipt ဆိုသည်မှာ ကိုယ်စားလှယ် လုပ်ဆောင်ခဲ့သည်များကို မှတ်တမ်းတင်ထားသော JSON object တစ်ခုဖြစ်ပြီး ဒီဂျစ်တယ် လက်မှတ်ဖြင့် လက်မှတ်ရေးထိုးထားသည်။

```mermaid
flowchart LR
    A[အေးဂျင့်သည် ကိရိယာတစ်ခုကို ခေါ်ယူသည်] --> B[လက်ခံလွှာအချက်အလက် ဖန်တီးသည်]
    B --> C[JSON RFC 8785 ကို canonicalize ပြုလုပ်သည်]
    C --> E[Canonical bytes များကို Ed25519 ဖြင့် လက်မှတ်ထိုးသည်]
    E --> F[လက်မှတ်ပါ လက်ခံလွှာ]
    F --> G[စစ်ဆေးသူသည် အော့ဖ်လိုင်းတွင် သတိပြုစစ်ဆေးသည်]
    G --> H{လက်မှတ်မှန်ကန်ပါသလား?}
    H -- yes --> I[ထိခိုက်မှုထင်ပေါ်မှု အထောက်အထား]
    H -- no --> J[လက်ခံလွှာ ငြင်းပယ်သည်]
```

Receipt အနည်းဆုံး ပုံစံက ဒီလိုပဲ ဖြစ်ပါသည်။

```json
{
  "type": "agent.tool_call.v1",
  "agent_id": "contoso-travel-bot",
  "tool_name": "lookup_flights",
  "tool_args_hash": "sha256:a3f9c1...",
  "result_hash": "sha256:7b2e1d...",
  "policy_id": "contoso-travel-policy-v3",
  "timestamp": "2026-04-25T14:30:00Z",
  "sequence": 47,
  "previous_receipt_hash": "sha256:9d4e6a...",
  "signature": {
    "alg": "EdDSA",
    "sig": "c5af83...",
    "public_key": "8f3b2c..."
  }
}
```

အောက်ပါသုံးချက်သည် အဓိကတာဝန်ရှိပါသည် -

1. **လက်မှတ်**။ Receipt ကို ကိုယ်စားလှယ်၏ gateway က Ed25519 private key ဖြင့် လက်မှတ်ရေးထိုးထားသည်။ အတူတူ public key ပါရှိသူတိုင်းသည် signature ကို offline မှာ စစ်ဆေးနိုင်သည်။ field တစ်ခုခု ပြောင်းလဲခဲ့လျှင် လက်မှတ် မတည်မြဲတော့ပါ။

2. **Canonical encoding**။ လက်မှတ်ရေးထိုးမည့်မတိုင်မီ Receipt ကို JSON Canonicalization Scheme (JCS, RFC 8785) အတိုင်း serialized လုပ်ထားသည်။ ဤနည်းလမ်းသည် အတူတူအကြောင်းအရာရှိ JSON serializer နှစ်ခုမှ byte-identical output ထုတ်ပေးစေရန် အတည်ပြုသည်။ Canonicalization မရှိပါက serializer ပေးသော လက်မှတ်များ သက်ဆိုင်ရာအကြောင်းအရာတူဖြစ်ပေမယ့် မတူညီနိုင်ပါ။

3. **Hash chaining**။ `previous_receipt_hash` field မှ တစ်ခုချင်းစီ receipt ကို ယခင် receipt နှင့် ချိတ်ဆက်ပေးသည်။ Receipt တစ်ခုကို ဖယ်ရှား သို့မဟုတ် အစီအစဉ်ပြောင်းလဲခြင်းသည် ၎င်းကို နောက်တစ်ခု မှတ်တမ်းစဉ်အားလုံး ပျက်စီးနိုင်သည်။ တစ်ခုချက်လောက် လက်မှတ် မဆောင်ဘဲလည်း ၎င်းကွင်းဆက်မှာ ပြောင်းလဲမှုများ မျက်မှောက်အမြင်ဖြင့် ကြည့်ရူနိုင်သည်။

ဤသုံးရပ်များသည် အောက်ပါ သုံးချက်ကို အာမခံပေးသည် -

- **အတည်ပြုချက်**: ဤ key သည် ဤအကြောင်းအရာကို လက်မှတ်ရေးထိုးခဲ့သည်။
- **တင်းကျပမှု**: လက်မှတ်ရေးထိုးထားစဉ်ကတည်းက အကြောင်းအရာမပြောင်းလဲဘဲ ရှိခဲ့သည်။
- **အဆက်လိုက်မှု**: ဤ receipt သည် ကွင်းဆက်တွင် ထို receipt အပြီးတွင် ဖြစ်ခဲ့သည်။

## Python တွင် Receipt ထုတ်လုပ်ခြင်း

Receipt ထုတ်လုပ်ဖို့ အထူးစာကြည့်တိုက်မလိုပါ။ Cryptographic primitives များ အများကြီးရရှိနိုင်ပြီး logic သည် Python အတန်းချိုင့် ခြောက်သန်းခွဲဖြစ်သည်။

`code_samples/18-signed-receipts.ipynb` မှ လက်တွေ့လေ့ကျင့်မှုပြုခြင်းသည် ဤလုပ်ငန်းစဉ်အားလုံးကို ပတ်လမ်းစဉ်အတိုင်း ဖြတ်သွားသည်။ အကျဉ်းချုပ် -

```python
import json
import hashlib
import base64
from nacl import signing
from jcs import canonicalize  # RFC 8785 canonical JSON

def b64url_nopad(data: bytes) -> str:
    return base64.urlsafe_b64encode(data).decode("ascii").rstrip("=")

def sha256_canonical(obj) -> str:
    """SHA-256 of a Python object's JCS-canonical JSON form."""
    return f"sha256:{hashlib.sha256(canonicalize(obj)).hexdigest()}"

# စာချုပ်ရေးရန်သော key ကို ထုတ်လုပ်ခြင်း သို့မဟုတ် လွှတ်ယူခြင်း (ထုတ်လုပ်ရေးတွင် key vault ထဲသိမ်းဆည်းပါ)
signing_key = signing.SigningKey.generate()
verify_key = signing_key.verify_key

# လက်မှတ်ဆိုင်သော payload ကို ဆောက်လုပ်ခြင်း (လက်မှတ်မထည့်ခင်)
tool_args = {"origin": "SYD", "destination": "LAX"}
tool_result = [{"flight": "QF11", "price": 1850, "stops": 0}]

payload = {
    "type": "agent.tool_call.v1",
    "agent_id": "contoso-travel-bot",
    "tool_name": "lookup_flights",
    "tool_args_hash": sha256_canonical(tool_args),
    "result_hash": sha256_canonical(tool_result),
    "policy_id": "contoso-travel-policy-v3",
    "timestamp": "2026-04-25T14:30:00Z",
    "sequence": 0,
    "previous_receipt_hash": None,
}

# JCS bytes ကို တိုက်ရိုက် canonicalize လုပ်ပြီး လက်မှတ်ထိုးပါ။ PureEdDSA သည် အတွင်းပိုင်းတွင် hash လုပ်သည်။
canonical_bytes = canonicalize(payload)
signature_bytes = signing_key.sign(canonical_bytes).signature

# ဖွဲ့စည်းထားသော လက်မှတ်_object ကို ပူးတွဲပါ။
receipt = {
    **payload,
    "signature": {
        "alg": "EdDSA",
        "sig": b64url_nopad(signature_bytes),
        "public_key": b64url_nopad(bytes(verify_key)),
    },
}
```

၎င်းသည် လက်မှတ်ရေးထိုး အစိတ်အပိုင်း အားလုံးဖြစ်သည်။ notebook တွင် အစီအစဉ် အစိတ်အပိုင်းအားလုံးကို လေ့လာပါ။

## Receipt ကို စစ်ဆေးခြင်းနှင့် ပြောင်းလဲမှု ရှာဖွေရန်

စစ်ဆေးခြင်းသည် လုပ်ဆောင်မှု ဆန့်ကျင်ပါသည် -

```python
import base64
import hashlib
from nacl import signing
from nacl.exceptions import BadSignatureError
from jcs import canonicalize

def b64url_decode(s: str) -> bytes:
    padding = "=" * ((4 - len(s) % 4) % 4)
    return base64.urlsafe_b64decode(s + padding)

def verify_receipt(receipt: dict) -> bool:
    # လက်မှတ်သည် ဖွဲ့စည်းထားသော အရာဝတ္တုတစ်ခုဖြစ်သည်။ {"alg", "sig", "public_key"}။
    sig_obj = receipt.get("signature")
    if not sig_obj or sig_obj.get("alg") != "EdDSA":
        return False

    # လက်မှတ်ရေးထိုးထားသော payload ကို ပြန်လည်ဖန်တီးပါ (လက်မှတ်အပါအဝင် မဟုတ်သော အရာအားလုံး)။
    payload = {k: v for k, v in receipt.items() if k != "signature"}

    canonical_bytes = canonicalize(payload)

    try:
        verify_key = signing.VerifyKey(b64url_decode(sig_obj["public_key"]))
        verify_key.verify(canonical_bytes, b64url_decode(sig_obj["sig"]))
        return True
    except BadSignatureError:
        return False
```

ဤ function သည် receipt တစ်ခုကို လက်ခံပြီး signature မှန်ကန်ပါက `True` ကို၊ မဟုတ်လျှင် `False` คืนပါမည်။ network ခေါ်ဆိုမှု၊ service မည်သည့်လိုအပ်ချက်မှ မရှိပါ။

ပြောင်းလဲမှု ရှာဖွေရန် မွေးထုတ်မှုကို ကြည့်ရန် notebook တွင် -

၁။ တရားဝင် receipt ထုတ်လုပ်ပြီး စစ်ဆေးမှုမှန်ကန်မှုကို အတည်ပြုခြင်း။
၂။ `tool_args_hash` field မှ အတိုင်းအတာ တစ်ချက် ပြောင်းလဲခြင်း။
၃။ ပြန်လည် စစ်ဆေးမှု ပြုလုပ်ပြီး မအောင်မြင်မှုကြည့်ခြင်း။

၎င်းသည် receipt များသည် tamper-evident ဖြစ်ကြောင်း လက်တွေ့သက်သေအဖြစ် ဖော်ပြပါသည်။ အနည်းငယ်တောင် ပြောင်းလဲမှုဖြစ်လျှင် signature ပျက်စီးပါသည်။

## များစွာသောလှည်း agent များအတွက် Receipt များချိတ်ဆက်ခြင်း

စာမှတ်လက်မှတ်တစ်ခု သည် လုပ်ဆောင်ချက်တစ်ခုတည်းကို ကာကွယ်ပေးသော်လည်း receipt များကွင်းဆက်က တန်းလိုက် လုပ်ဆောင်မှုစဉ်တစ်ခုကို ကာကွယ်သည်။

```mermaid
flowchart LR
    R0[လက်ခံမှတ်တမ်း 0<br/>အစပြုခြင်း] --> R1[လက်ခံမှတ်တမ်း 1]
    R1 --> R2[လက်ခံမှတ်တမ်း 2]
    R2 --> R3[လက်ခံမှတ်တမ်း 3]
    R1 -. previous_receipt_hash .-> R0
    R2 -. previous_receipt_hash .-> R1
    R3 -. previous_receipt_hash .-> R2
```

တစ်ခုချင်းစီ Receipt တွင် ယခင် Receipt ၏ hash ပါရှိသည်။ Receipt 2 ကို တိတ်ဆိတ် ဖယ်ရှားလိုပါက တရပ်ရပ်တသာတောင်သာ -

- Receipt 3 ၏ `previous_receipt_hash` field ကို ပြောင်းလဲရန် (receipt 3 ၏ လက်မှတ် ပျက်စီးနိုင်သည်။)
- ပြင်ဆင်ထားသော Receipt 3အတွက် လက်မှတ်အသစ် ခိုးကပ်ရေးရန် (ကိုယ်စားလှယ် ၏ private key လိုအပ်သည်)

Private key ကို hardware key vault တွင်ထားရှိပြီး ၎င်း၏ public key ကို receipt တစ်ခုချင်းနဲ့ ထုတ်ပြန်ပါက တိုက်ခိုက်မှု မည်သည့်မျိုးမှ မတော်တဆလျှင် တွေ့ရှိနိုင်ပါသည်။

Notebook တွင် လုပ်ဆောင်ချက်များ -

၁။ Receipt သုံးခု ရှိသော အကြိုး ဆက်တိုင်တည်ဆောက်ခြင်း။
၂။ တစ်ခုချင်း receipt ၏ `previous_receipt_hash` သည် ယခင် receipt ၏ ဟက်ရှ်တန်ဖိုးနှင့်ကိုက်ညီမှု စစ်ဆေးခြင်း။
၃။ အလယ်ရှိ receipt အနည်းငယ် ပြောင်းလဲပြီး သုံးလုံးဆက်တိုင် ပျက်စီးမှုကို တွေ့ရှိခြင်း။

၎င်းသည် ဘယ်သူ့ကိုမှ ယုံကြည်စရာမလိုဘဲ အပြင်မှ စစ်ဆေးသူက အတည်ပြုနိုင်သော Audit trail တစ်ခု ထုတ်လုပ်ပုံဖြစ်သည်။

## Receipt များ သက်သေပြနိုင်သည် (နှင့် မသက်သေပြနိုင်သည့်အရာများ)

ဤအပိုင်းသည် ဤသင်ခန်းစာ၏အရေးကြီးဆုံးအပိုင်းဖြစ်သည်။ Receipt များစွမ်းအားကြီးမားသော်လည်း ၎င်း၏ အာဏာသတ်မှတ်ချက် ရှိသည်။

**Receipt များ သက်သေပြနိုင်သည် သုံးခုမှာ:**

၁။ **အတည်ပြုချက်**: key တိတိဟာ payload တိတိကို လက်မှတ်ရေးထိုးခဲ့သည်။
၂။ **တင်းကျပမှု**: လက်မှတ်ရေးထိုးခဲ့ချိန်မှ စ၍ payload ပြောင်းလဲမှုမရှိပါ။
၃။ **အစီအစဉ်လိုက်မှု**: Receipt သည် ဟက်ရှ်ကြိုးတွင် ထို receipt အပြီးမှ ဖြစ်ပါသည်။

**Receipt များ မသက်သေပြနိုင်သေးသည့်အချက်များမှာ** -

၁။ **မှန်ကန်မှု**: ကိုယ်စားလှယ် လုပ်ဆောင်မှုသည်မှန်ကန်သည်ဟု မသက်သေပြနိုင်ပါ။ Receipt ကို အမှားဖြေပေးမှုအတွက်လည်း တိကျစွာ လက်မှတ်ရေးထိုးနိုင်သည်။
၂။ **မူဝါဒလိုက်နာမှု**: `policy_id` တွင် ဖော်ပြသော မူဝါဒသည် ဝိုင်ကင်းစွာ သုံးသပ်ရှိခဲ့ခြင်း မဟုတ်သည်၊ သာမန်အားဖြင့် action ကို ခွင့်ပြုခဲ့ခြင်း မဟုတ်ပါ။ Receipt သည် မည်သည့်အရာကို မှတ်တမ်းတင်သည်မှာ သက်သေပြသည်၊ မူဝါဒအဖော်ပြချက်များ အတည်ပြုခြင်းမဟုတ်ပါ။
၃။ **key ကိုက်ညီရာ အစိတ်အပိုင်းများအပြီးတွင် လူ့အပေါ် အသိအမှတ်ပြုမှု မရှိခြင်း**: Receipt မှ "ဤ key သည် ထိုအကြောင်းအရာကို လက်မှတ်ရေးထိုးသည်" ဟု ဆိုပါသည်။ "ဤလူ တစ်ဦးက အတည်ပြုခဲ့သည်" ဆို မဟုတ်ပါ။ key ကို လူသို့ တင်မြှောက်ရန် identity infrastructure များလိုပါသည် (directory, public key registry စသည်).
၄။ **အင်ပွတ်တင်းများ၏ မှန်ကန်မှု**: ကိုယ်စားလှယ်သည် ထိန်းချုပ်ထားသော prompt ကို ခံယူကာ လုပ်ဆောင်ကြောင်း Receipt မှတ်တမ်းတင်သည်။ Receipt များသည် input စစ်ဆေးမှု အစားထိုး မဟုတ်ပါ၊ input စစ်ဆေးမှု၏ အောက်ပိုင်းတွင်ရှိသည်။

၎င်းနယ်နိမိတ်သည် အကြောင်း နှစ်ချက်ကြောင့် အရေးကြီးသည် -

- Receipt များ အသုံးဝင်သောနေရာကို ပြောပြသည် - ကိုယ်စားလှယ်အပြုအမူများကို audit ပြုလုပ်နိုင်စေခြင်း နှင့် tamper-evident ဖြစ်ခြင်း၊ အဖွဲ့အစည်း တစ်ခုနှင့်တစ်ခုအကြား တွန်းယှဉ်ခြင်း။
- သင့်အားလိုအပ်သည့် အထပ်ထပ် လမ်းကြောင်းများ ဖြည့်ဆည်းရန်လိုအပ်သည်ဟု ပြောသည် - input validation (သင်ခန်းစာ ၆), policy enforcement (အောက်တွင်အတိုချုံးဖော်ပြထားသည်), identity infrastructure (ဤသင်ခန်းစာမှာ မပါဝင်ပါ။

ယေဘုယျအားဖြင့် "ကျွန်ုပ်တို့မှာ receipts ရှိသည်" ဟူ၍ "ကျွန်ုပ်တို့ကို အုပ်ချုပ်မှု ရှိသည်" ဟုထင်မြင်ခြင်းသည် အမှားကြီးဖြစ်သည်။ Receipt များသည် အခြေခံအဆောက်အအုံဖြစ်ပြီး Governance သည် ၎င်းအပေါ် တည်ဆောက်သည့် စနစ်ဖြစ်သည်။

## လူတစ်ဦးက သတ်မှတ် လုပ်ဆောင်ချက်ကို အတည်ပြုထားသည်ဟု သက်သေပြခြင်း

အပေါ်တွင်ဖော်ပြသော အချက် ၃ သည် အထူး အပိုင်း တစ်ခုတည်းကို တန်ဖိုးထားသင့်သည် - လုပ်ဆောင်ချက် Receipt က "ဤ key သည် ထိုအကြောင်းအရာကို လက်မှတ်ရေးထိုးသည်" ဟုသာ ဆိုသည်။ "လူတစ်ဦးက အတည်ပြုခဲ့သည်" မဟုတ်ပါ။ အန္တရာယ်မြင့် လုပ်ဆောင်ချက်များ (ပြန်လည်ငွေထုတ်ခြင်း၊ ဖျက်သိမ်းခြင်း၊ ကြိုးငွေလွှဲခြင်းများ) တွင် Governance နိယာမများသည် အနည်းဆုံး ဤမပါဝင်သေးသော အဆိုအရပ်ကို လိုအပ်သည်ဟု ဇယားတင်ပြီး၊ ၎င်းကို ဤသင်ခန်းစာ၌တည်ဆောက်ထားသော နည်းလမ်းများဖြင့်ထုတ်လုပ်နိုင်သည်။

ထို့နောက် notebook `code_samples/human-authorization-receipts.ipynb` သည် `human.approval.v1` ဟူသော ဒုတိယ receipt အမျိုးအစားကို ထည့်သွင်းထားသည်၊ ဤ receipt များသည် သင်ခန်းစာကိုယ်တိုင်ထုတ်လုပ်သော receipts များအဖြစ် Ed25519 ဖြင့် canonical JCS bytes ပေါ်တွင် လက်မှတ်ရေးထိုးထားပြီး၊ `signature` အရာဝတ္တုကို signed bytes ပြင်ပတွင်ရှိသည်။ ခေါ်ထားသော approver တစ်ဦးသည် အပြည့်အစုံ canonical လုပ်ဆောင်ချက်နှင့် ၎င်း၏ digest ကို လက်မှတ်ရေးထိုးပြီး ချိန်ခွင် ဖြစ်စဉ်မတိုင်ခင် လုပ်ဆောင်သည်။ ကိုယ်စားလှယ်၏ လုပ်ဆောင်ချက် Receipt သည် **တူညီသော action digest** နှင့် `parent_approval_ref` တို့ ပါရှိပြီး approval ၏ `receipt_hash` ဖြစ်ကာ နှစ်ခုလုံးကို **key pinned registry များတွင်** `verify_chain` တစ်ခုဖြင့် စစ်ဆေးသည် (approver key များနှင့် ကိုယ်စားလှယ် key များကို ခွဲခြားထားသည်) ဆိုသည့် code လမ်းကြောင်း အမျိုးမျိုး မျှဝေသော်လည်း အာဏာပိုင်များ အမြဲမတူညီပါ။

၎င်းသည် သေချာရေးထားသည့် property ဖြစ်သည် - *လူတစ်ဦးက ဤလုပ်ဆောင်ချက်တိတိကို အတည်ပြုခဲ့ပြီး ကိုယ်စားလှယ်သည် ထိုအတည်ပြုထားသောလုပ်ဆောင်ချက်ကို တိတိကျကျ ဆောင်ရွက်ခဲ့သည်*။ Notebook ၏ ဤ refuse fixtures များသည် အဆိုပြုချက်မဟုတ်ပဲ အမှန်တကယ် property ကိုအထောက်အကူပြုသည် -

- မျိုးဆက်အတွက် လက်ဖြင့်ဖြေရှင်းခြင်း: မှားယွင်းမှုများ, confused deputy, replay, လက်မှတ်ကူးယစ်မှု, မမှန်ကန်သောအင်ပွတ်;
- **stale authority**: signature သည် အတည်ပြုထားသော်လည်း policy ဗားရှင်းပြောင်းလဲမှု၊ approver key ပြောင်းလဲမှု၊ သတ်မှတ်ချိန် မီခင် ကာလကုန်ဆုံးမှုကြောင့် ပယ်ချခြင်း;
- **digest substitution**: မှန်ကန်စွာ လက်မှတ်ရေးထိုးထားသော action receipt တစ်ခုသည် အတည်ပြုချက် မတူညီသော canonical action တွင် သွားညွှန်ခြင်း။

တစ်ခုချင်း refuse မှ ပြသသော အကြောင်းပြချက်ကွဲပြားပြီး စစ်ဆေးသူသည် authority ပျက်ဆုံးမှု သို့မဟုတ် လုပ်ဆောင်ချက်ပြောင်းလဲမှုကို အလွယ်တကူ သိနိုင်သည်။ Notebook သင်ကြားသည့် စည်းမျဉ်းသည် - လက်မှတ်ရေးထိုးထားသော အတည်ပြုချက်သည် ကိုယ့်အလိုအလျောက် အာဏာမဟုတ်ပါ။ Authority သည် နှစ်ခုနှင့်တူညီသော canonical action ကို ဆောင်ရွက်ချိန်တွင်သာ အတည်ရှိပါသည်။ လူ့အတည်ပြု Receipt သည် ဤသင်ခန်းစာမှ သင်ယူရေးပြရန်ဖွဲ့စည်းထားသော ရှုထောင့်ဖြစ်ပြီး `draft-farley-acta-signed-receipts` ၏ receipt မဟုတ်ပါ။

## ထုတ်လုပ်မှု ဆိုင်ရာ အညွှန်းများ

ဤသင်ခန်းစာ၌ ပါသော Python ကုဒ်သည် တိတိကျကျနားလည်နိုင်ရန်အတွက် အချက်နှစ်ချက်သာပါရှိသည်။ ထုတ်လုပ်မှုတွင် ရွေးချယ်မှုနှစ်ခုရှိသည် -

၁။ **Cryptographic primitives များကို တိုက်ရိုက်အသုံးပြုရန်။** အထက်တွင် မြင်တွေ့ခဲ့သော နံပါတ် ၅၀ လမ်းကြောင်းသည် အသုံးအဆောင်များအတွက် လုံလောက်သည်။ PyNaCl (Ed25519) နှင့် `jcs` package (canonical JSON) များမှာ ကျယ်ပြန့်စွာ ထိန်းသိမ်း မီနိတာပ်နေပြီး စစ်ဆေးပြီးသား စာကြည့်တိုက်များဖြစ်သည်။

၂။ **ထုတ်လုပ်မှု receipt စာကြည့်တိုက်ကို အသုံးပြုရန်။** အဆင့်မြင့် လက္ခဏာ သတ်မှတ်ချက်များ (key ပြောင်းလဲမှု၊ bundle စစ်ဆေးမှု၊ JWK set မျှဝေမှု၊ policy engine အတူ ပြုလုပ်ခြင်း) ဖြင့် အတူတကွ ဆောင်ရွက်သော open-source project များ ရှိသည် -
   - လက်မှတ်ရေးထိုးခြင်း process သည် JCS နှင့် လက်မှတ် ဒေသဆိုင်ရာ IETF Internet draft ([`draft-farley-acta-signed-receipts`](https://datatracker.ietf.org/doc/draft-farley-acta-signed-receipts/), အစီအစဉ် 02) တွင် သီးခြား ဖော်ပြသည်။ ဤသင်ခန်းစာ၏ ပုံတူသော receipt သည် draft ၏ `{payload, signature}` အထုပ်နှင့် ကွာခြားပြီး သဘောတူအကောင်အထည်ဖေါ်မှု မဟုတ်ပါ။ Draft သည် shared conformance suite ([agent-governance-testvectors](https://github.com/ScopeBlind/agent-governance-testvectors)) ကို ထုတ်ဝေသည်။
   - Microsoft Agent Governance Toolkit သည် Cedar- အခြေပြု မူဝါဒ ဆုံးဖြတ်ချက်များနှင့် receipt များ ပေါင်းစပ်ထားပြီး အပြီးအတိုင် နမူနာများကို ထို repository ၏ Tutorial 33 တွင် ကြည့်ရှုနိုင်သည်။
   - `protect-mcp` (npm) နှင့် `@veritasacta/verify` (npm) package များသည် MCP server များကို tamper-evident audit trail ဖြင့် ထုပ်ပိုးရန် အတွက် Receipt လက်မှတ်ရေးထိုးခြင်းနှင့် offline စစ်ဆေးမှု Node-based implementation ဖြစ်သည်၊ ဖိအားထားသည့် လုပ်ဆောင်ချက်များအတွက် approval receipt ထုတ်ပေးမည့် held-for-co-sign flow ပါဝင်သည် (desktop flow တွင် WebAuthn- ကူညီသည်)။
   - **[nobulex](https://github.com/arian-gogani/nobulex)** Python SDK (`pip install nobulex`) သည် LangChain နှင့် CrewAI ပေါင်းစပ်ရန် Ed25519 + JCS signing ကို တူညီစွာ ပေးဆောင်ပြီး published cross-validation test vectors နှင့် compliance mapping ကို [OWASP PR #2210](https://github.com/OWASP/CheatSheetSeries/pull/2210) မှ ထည့်သွင်းထားသည်။

ကိုယ်တိုင်ရေးသားခြင်းနဲ့ library အသုံးပြုခြင်းသည် JWT library ရေးသားမှုနှင့် တူညီသည် - နှစ်ဖက်လုံး သင့်တော်ပြီး၊ library သည် အချိန်တိုင်းဆန်သိမ်းပြီး audit အခွာကို လျှော့နည်းစေသည်။ Scratch မှာရေးခြင်းသည် primitive တစ်ခုချင်းစီကို နားလည်ရန်လိုအပ်သည်။ ဤသင်ခန်းစာသည် Scratch စနစ်ကို သင်ကြားပါသည့်အတွက် နှစ်မျိုးလုံးအတွက်အခြေခံဖြစ်သည်။

## အသိပညာ စစ်ဆေးမေးခွန်းများ

လေ့ကျင့်ခန်းသို့ ရောက်မတိုင်မီ သင်၏ နားလည်မှုကို စစ်ဆေးပါ။

**၁။ Receipt ကို ကိုယ်စားလှယ်၏ လျှို့ဝှက် Ed25519 key ဖြင့် လက်မှတ်ရေးထိုးသည်။ စစ်ဆေးသူတွင် အများပြည်သူ key ပဲ ရှိသည်။ စစ်ဆေးသူသည် receipt ကို offline မှာ စစ်ဆေးနိုင်ပါသလား?**

<details>
<summary>အဖြေ</summary>

ဟုတ်ကဲ့။ Ed25519 verification သည် public key နှင့် signed bytes ဖလှယ်ရန် လိုအပ်သည်။ Network call မလို၊ service ကိုမီမီမလိုအပ်။ ဤအင်္ဂါရပ်သည် receipt များအား air-gapped, မျိုးစုံအဖွဲ့အစည်း၊ သို့မဟုတ် ယုံကြည်မှု နည်းပါးသော audit အခြေအနေများတွင် အသုံးဝင်စေရန်ဖြစ်သည်။
</details>

**၂။ တိုက်ခိုက်သူတစ်ဦးသည် receipt ၏ `policy_id` field ကို ပြုံငယ်သော မူဝါဒငြင်း ဆန့်ကျင်မှု ဖြစ်ပေါ်သည်ဟု သိမ်းဆည်းရန် ပြင်ဆင်သည်။ လက်မှတ်သည် မူလ payload ပေါ်တွင် ရေးထိုးထားသည်။ စစ်ဆေးမှုအတွင် ဖြစ်ပေါ်တယ့် အခြေအနေကို ဘယ်လိုဖြစ်မလဲ?**

<details>
<summary>အဖြေ</summary>


လက်မှတ်အတည်ပြုမှု မအောင်မြင်ပါ။ လက်မှတ်ကို မူလ payload ၏ canonical bytes များအပေါ် တွက်ချက်ထားသည်။ မည်သည့် ကွက်လပ်ကိုမဆို ပြင်ဆင်ခြင်းသည် bytes များကိုပြောင်းလဲပြီး လက်မှတ်ကို မရည်ရွယ်သင့်ဘဲ ပြုလုပ်ခြင်း ဖြစ်လာသည်။ တိုက်ခိုက်သူသည် အသစ်၊ မှန်ကန်သော လက်မှတ်ကို ထုတ်ပေးရန် အထူးသီးသန့် key ထိုတ်ကို လိုအပ်မည်ဖြစ်ပြီး ၎င်းမှာ မပိုင်ဆိုင်ပါ။
</details>

**3. ရှေ့ပြကွက်နှင့် ရလဒ်ကို ရိုးရိုးအနေဖြင့် ထည့်သွင်းရန်အစား `tool_args_hash` နှင့် `result_hash` ကို ဘာလို့ receipt ထဲတွင် ထည့်သွင်းသလဲ?**

<details>
<summary>အဖြေ</summary>

မူလတန်းအနက်နှစ်ခု ကြောင့်ဖြစ်သည်။ ပထမတစ်ခု - receipt ကို တည်ထောင်ထားရသည့်နေရာများ၊ ကူးပြောင်းနေရာများ၌ မူရင်းအကြောင်းအရာ (ပုဂ္ဂိုလ်ရေးအချက်အလက်၊ စီးပွားရေးဒေတာ) ပြဿနာတစ်ရပ်ဖြစ်တတ်ပေသည်။ Hashing က receipt ကို သေးငယ်ပြီး အကြောင်းအရာကို ကိုယ်ပိုင်ထားစေသည်။ စစ်ဆေးသူသည် hash တွက်ချက်ချက်သည် တစ်ခြားသိမ်းဆည်းထားသော အကြောင်းအရာ နှင့် ကိုက်ညီသည်ဟု စစ်ဆေးနိုင်သည်။ ဒုတိယ - hash များသည် အရွယ်အစား သတ်မှတ်ထားပြီး receipts တစ်ခုသည် စံအတိုင်း အရွယ်အစား ပမာဏကို ထိန်းသိမ်းထားနိုင်သည်။
</details>

**4. `previous_receipt_hash` ကွက်လပ်သည် receipt တစ်ခုချင်းစီကို ၎င်း၏ အရင် receipt နှင့် ချိတ်ဆက်ထားသည်။ တိုက်ခိုက်သူက  ဂျောင်းထဲရှိ receipt တစ်ခုကို တိတ်ဆိတ်ဖျက်လိုက်လျှင် ဘာတွေ မမှန်ဖို့ ဖြစ်မလဲ?**

<details>
<summary>အဖြေ</summary>

ဖျက်လိုက်သော receipt အောက်ပိုင်းရှိ receipt အားလုံး။ ၎င်းတို့၏ `previous_receipt_hash` ကွက်လပ်များသည် အမှန်တကယ်ရှိသော ဂျောင်းနှင့် ကိုက်ညီခြင်း မရှိတော့ပါ (ဖြစ်နေရခြင်းကြောင့် ဖျက်ထားသော receipt မရှိတော့ပဲ၊ သို့မဟုတ် ဂျောင်းသည် အခြား ညီမျှသောအသီးသီး အရင် receipt ကို တွဲသွားခြင်း ဖြစ်သည်)။ ဖျက်ခြင်းကို ဖုံးကွယ်ရန် တိုက်ခိုက်သူသည် နောက်ပိုင်း receipt အားလုံးကို ပြန်လက်မှတ်ရေးဆွဲရမည်၊ ထိုအတွက် အထူးသီးသန့် key လိုအပ်သည်။
</details>

**5. Receipt တစ်ခုသည် စစ်ဆေးခြင်းကို ပြီးမြောက်စွာ အတည်ပြုပြီ ဖြစ်ပါက အောက်ပါအချက်များထဲ၌ အတိုက်အခံလုပ်ဆောင်မှုသည် မှန်ကန်၊ တည်ငြိမ် သို့မဟုတ် မူဝါဒနှင့် လိုက်ဖက်သည်ဟုတ်၏ဟု အတည်ပြုပါသလား?**

<details>
<summary>အဖြေ</summary>

မဟုတ်ပါ။ မှန်ကန်သော receipt သည် အတိုင်းအတာသုံးခု ရှိပြသည်။ attribution (ဤ key သည် ဤအကြောင်းအရာကို လက်မှတ်ရေးထိုးသည်), integrity (အကြောင်းအရာမပြောင်းလဲပဲ ရှိသည်), ကြိမ်နှုန်း (ဤ receipt သည် အဲဒီ receipt နောက်ပိုင်းတစ်ခုဖြစ်သည်)။ ၎င်းသည် လုပ်ဆောင်မှုသည် မှန်ကန်မှု၊ `policy_id` တွင် ဖော်ပြထားသည့် မူဝါဒကို တိတိကျကျ အကဲဖြတ်ထားသည်၊ သို့မဟုတ် အေးဂျင့်သည် စည်းမျဥ်းကြောင်း အားလုံးလိုက်နာသည်ဟု အတည်ပြုခြင်း မပြုပါ။ Receipt များသည် အေးဂျင့်၏ လုပ်ဆောင်မှုကို စစ်ဆေးနိုင်စေသော်လည်း မှန်ကန်မှုကို မအာမခံပါ။ သင်ခန်းစာ၏ အရေးကြီးဆုံးကန့်သတ်ချက် ဖြစ်သည်။
</details>

## လေ့ကျင့်ခန်း

`code_samples/18-signed-receipts.ipynb` ဖိုင်ကိုဖွင့်ပြီး စာမူလေးခု ဝင်ပါ။

1. **အပိုဒ် ၁**: သင်၏ ပထမဆုံး receipt ကို လက်မှတ်ရေးထိုးပြီး အတည်ပြုပါ။
2. **အပိုဒ် ၂**: Receipt ကို ပြင်ဆင်ပြီး verification မအောင်မြင်မှုကို ကြည့်ရှုပါ။
3. **အပိုဒ် ၃**: ရှေ့ပြ receipt သုံးခုကို ဖန်တီးပြီး ဂျောင်းတည်ငြိမ်မှုကို အတည်ပြုပါ။
4. **အပိုဒ် ၄**: Microsoft Agent Framework ဖြင့် တည်ဆောက်ထားသော agent ကို အသုံးပြု၍ pattern ကို အသုံးပြုပါ - tool ခေါ်ဆိုမှုကို receipt-လက်မှတ်ရေးထိုးခြင်းဖြင့် ဝိုင်းပတ်ပြီး၊ receipt ကို အထူးသီးသန့် စစ်ဆေးပါ။

**အပြန်အလှန် စိန်ခေါ်မှု ၁:** receipt schema ကို သင်ရွေးချယ်သော အထူးကွက်လပ်တစ်ခုဖြင့် တိုးချဲ့ပါ (ဥပမာ tracing အတွက် request ID)၊ canonical signing logic ကို ပြင်၍ ထည့်သွင်းပြီး receipt ကို လက်မှတ်ရေးထိုးပြီး verification ပြုလုပ်ပါ။ ပြီးနောက် လက်မှတ်ရေးထိုးမှု ပြီးသော အချိန်တွင် ကိုယ့်ရွေးချယ်ထားသောကွက်လပ် ပြင်ဆင်ပြီး verification မအောင်မြင်မည်ကို အတည်ပြုပါ။ ၎င်းသည် canonical encoding ၏ ဘိုင်( byte ) တစ်ခုချင်းစီသည် လက်မှတ်အပေါ် ဘယ်လိုထိရောက်မှု ရှိကြောင်းနားလည်ရန် ပံ့ပိုးသည်။

**အပြန်အလှန် စိန်ခေါ်မှု ၂:** သင်၏ receipt နှစ်ခုကို SHA-256 ဖြင့် hash တည်းတစ်ခုပြုလုပ်သည်( canonical bytes များကို သတ်မှတ်ထားသော အစီအစဉ်ဖြင့် ပေါင်းစည်းခြင်း)၊ ထို့နောက် သုံးစွန်း receipt တွင် အဲဒီ hash ကို အသစ်ကွက်လပ်ကြားထည့်ပါ။ သုံးမူ receipt များကို တစ်ကိုယ်တည်း ပြန်လည်အတည်ပြုနိုင်သည်။ သင်သည် တစ်ဆင့်သော ထည့်သွင်းချုပ် အထောက်အထား တည်ဆောက်ပြီးဖြစ်သည်။ receipt တတိယ ကိုင်ဆောင်သော မည်သူမဆို ပထမနှစ်ခု ရှိခဲ့ကြောင်း သက်ဝင်လျှင် လက်မှတ်ရေးထိုးသည့်အချိန်တွင် သက်သေပြနိုင်သည်၊ ၎င်းများ၏ အကြောင်းအရာကို မဖော်ပြပဲ စစ်ဆေးနိုင်သည်။ ၎င်းသည် selective-disclosure receipt များ၏ ပုံစံ ဖြစ်သည် (Merkle commitments, RFC 6962)။

## အနှုတ်ချုံး

အက်စ်အိုင် အေးဂျင့်များအတွက် ကွန်ပြူတာ လက်မှတ်များသည် အောက်ပါ အချက်များကို အသွင်ပြောင်းပေးသည်။

- **ကိုယ်ပိုင်စစ်ဆေးနိုင်သော**: ဘာသာရပ်တိုင်း લက်မှတ်ကို ကြေညာသောသူသည် စစ်ဆေးနိုင်သည်; ဝန်ဆောင်မှုမလို။
- **ပြင်ဆင်မှုထင်ရှားသော**: မည်သည့်ပြင်ဆင်မှုမျှ လက်မှတ်ကို မမှန်ကန်စေပါ။
- **တဆက်တည်း သယ်ဆောင်နိုင်သော**: receipt သည် သေးငယ်သော JSON ဖိုင်; သိမ်းဆည်းပေးရ၊ လွှဲပြောင်းပေးရ၊ စစ်ဆေးနိုင်သည်။
- **စံချိန်စည်းမှုပေါ် တည်ဆောက်ထားသော**: Ed25519 (RFC 8032), JCS (RFC 8785), နှင့် SHA-256 များကို အသုံးပြု၍ ပြုလုပ်ထားသည်။

၎င်းတို့သည် input စစ်ဆေးခြင်း၊ မူဝါဒ လိုက်နာခြင်း သို့မဟုတ် ကိုယ်身份အထောက်အထားအဆောက်အအုံ မဟုတ်ပါ။ ၎င်းများသည် အဆိုပြုတိုင်းသော အဆင့်များအတွက် အခြေခံ တည်နေရာ ဖြစ်သည်။ သင်သည် ပြဋ္ဌာန်းထားသော လုပ်ငန်းစဉ်များ၊ ကုမ္ပဏီများအကြား အလုပ်လုပ်ငန်းများ သို့မဟုတ် နောက်တစ်ချိန် အစစ်အမှု ဆင်းရဲမှုရှိနိုင်သည်ဟု ယူဆရသော နေရာများသို့ agent များကို စက်ပစ္စည်းတင်သောအခါ receipt များက အမွန်တရား audit trail ဖြစ်စေသည်။

အရေးကြီးဆုံး သင်ယူရမည့်အချက်မှာ - receipt များက ဘယ်သူ အဘယ်အချိန် ဘာပြောခဲ့သည်ဟု သက်သေပြသည်။ ၎င်းမှာ ပြောဆိုထားသောအရာသည် မှန်ကန်မှန်း သို့မဟုတ် မှန်ကန်မှုကို မသက်သေ ပြုပါ။ အဲဒီကွာခြားချက်ကို သိမ်းထားသင့်သည်။ ၎င်းသည် ရိုးသားသော မူရင်းစာရင်းစနစ်နှင့် မမှန်ကန်သော စနစ်ကြား ခြားနားချက် ဖြစ်သည်။

## ထုတ်လုပ်မှု စစ်ဆေးစာရင်း

သင်သည် သင်ခန်းစာမှ တက်တန်းပြီး အမှန်တကယ် agent များကို receipt-lakမှတ်ရေးထိုးသော ပတ်ဝန်းကျင်တွင် တပ်ဆင်ရန် ပြင်ဆင်နေသည်မှာ -

- [ ] **လက်မှတ်ရေးဆွဲသော key ကို ဖန်ဆင်းသူလက်ပ်တော့မှ အပြောင်းအလဲပြုလုပ်ပါ။** Azure Key Vault, AWS KMS သို့ hardware security module ကို အသုံးပြုပါ။ receipt များကို လက်မှတ်ရေးထိုးသော အထူးသီးသန့် key သည် source control တွင် သို့မဟုတ် plaintext အနေဖြင့် အက်ပလီကေးရှင်း စက်ပစ္စည်းများတွင် မရှိသင့်ပါ။
- [ ] **verification public key ကို ထုတ်ပြန်ပါ။** စစ်ဆေးသူများသည် offline ပုံစံဖြင့် စစ်ဆေးရန် လိုအပ်သည်။ စံနမူနာမှာ well-known URL (RFC 7517) တစ်ခုတွင် JWK Set ဖြစ်သည်၊ ဥပမာ - `https://your-org.example.com/.well-known/agent-keys.json`။
- [ ] **ဂျောင်းကို ပြင်ပတွင် သံမဏိထားပါ။** အချိန်မျှတစွာ နောက်ဆုံး ဂျောင်းခေါင်း hash ကို transparency log (Sigstore Rekor, RFC 3161 timestamp authority သို့မဟုတ် နှစ်ခု째 အတွင်းရေးစနစ်) တွင် လွှဲရေး၍ ပြင်ပလူတစ်ဦးဖြင့် "ဤဂျောင်းသည် အချိန်ဤတွင် ရှိခဲ့သည်" ဟု အတည်ပြုနိုင်ရန်။
- [ ] **receipt များကို ပြောင်းလဲ မရသော အထောက်အထား ဖြစ်အောင် သိမ်းဆည်းပါ။** Append-only blob storage (Azure Storage with immutability policies, AWS S3 Object Lock) သည် အတွင်းရေးလုပ်သားတစ်ဦးက သိမ်းဆည်းရာတွင် သမိုင်းကို ပြန်လည်ရေးသားခြင်းကို တားဆီးသည်။
- [ ] **ထိန်းသိမ်းမှု အချိန်သတ်မှတ်ချက်ကို ဆုံးဖြတ်ပါ။** အများအဖြစ် ဉပဒေစည်းမျဥ်းများသည် နှစ်ပေါင်းများစွာ ထိန်းသိမ်းရန် လိုအပ်သည်။ receipt များတိုးတက်မှုအတွက် စတင်ပြင်ဆင်ပါ (~ receipt တစ်ခုသည် ~500 bytes; အေးဂျင့် တစ်နေ့လျှင် 10K ခေါ်ဆိုမှုလုပ်သည်ဆိုလျှင် ခုနှစ်စဉ် ~1.8 GB ဖြစ်သည်)။
- [ ] **receipt များ မပါဝင်သည့် အရာများကို စာရွက်သဖွယ် ပြုလုပ်ပါ။** receipt များသည် attribution, integrity နှင့် orderingကို သက်သေပြသည်။ သင်၏လုပ်ငန်းလမ်းညွှန်တွင် ထူးခြားသော ထိန်းချုပ်မှုများ (input validation, policy enforcement, rate limiting, identity infrastructure) မူလတည်ဆောက်မှုတွင် ဘာများ ရှိသည်ကို ဖော်ပြရန်။

### AI Agent များကို လုံခြုံရေးဆိုင်ရာ ထပ်မံမေးမြန်းချင်ပါသလား?

[Microsoft Foundry Discord](https://aka.ms/ai-agents/discord) တွင် ဝင်ရောက်ပါ။ အခြား တက်ကြွသူများနှင့်တွေ့ဆုံ၍ office hours တွင် တက်ရောက်ပြီး AI Agents မေးခွန်းများဖြေကြားပါ။

## ယခုသင်ခန်းစာ ကျော်လွန်ပြီး နောက်ပိုင်း

ဤသင်ခန်းစာသည် 单一 receipt သဘောတရားနှင့် hash-chained စီးရီး များကို ဖုံးကွယ်ထားသည်။ အခြားကျယ်ပြန့်သော အဆင့်မြင့် ပုံစံများကို governance လမ်းဘေးပိုင်းတိုးတက်လာသည့်အခါ တွေ့မြင်နိုင်သည်။

- **ရွေးချယ်ဖော်ပြခြင်း။** receipt ၏ကွက်လပ်များသည် အဆင့်လိုက် ဖော်ပြထားသည့် အခါ (RFC 6962 မျိုး Merkle tree)၊ သင့်အား သတ်မှတ်ထားသည့် ကွက်လပ်များကို အတည်ပြုစစ်ဆေးသူများအတွက် ဖော်ပြခြင်းနှင့် တစ်ခြားကွက်လပ်များကို မဖော်ပြပဲ မပြောင်းလဲကြောင်း သက်သေပြနိုင်သည်။ သဘာဝတွင် ဖြည့်ဆည်းဖို့ ပိုမိုလိုအပ်သည့် audit (ပြည့်စုံမှု လိုအပ်သော audit) နှင့် ပုဂ္ဂိုလ်ရေးကာကွယ်မှု စည်းမျဥ်းများဖြစ်သော GDPR အတွက် သုံးစွဲသူများကို သက်သာစေသည်။
- **receipt ပယ်ဖျက်ခြင်း။** လက်မှတ်ရေးထိုးသော key ပျက်စီးခဲ့ပါက ထို key ဖြင့် လက်မှတ်ရေးထိုးထားသော receipt များအားလုံးကို ယုံကြည်မှုမရှိရန် မှတ်ချက်တင်နိုင်ရန် လမ်းကြောင်းလိုအပ်သည်။ စံနမူနာများ - ယာယီ လက်မှတ်ရေးထိုး key များနှင့် ထုတ်ပြန်ထားသော ပယ်ဖျက်စာရင်း, သို့မဟုတ် transparency log များတွင် ပယ်ဖျက်ချက်များပါရှိစေရန်။
- **နှစ်ဖက်/ အပိုင်းခွဲ လက်မှတ်ရေးထိုးသော receipt များ။** အဖွဲ့ ရေးထိုး payload ကို တိုက်ဆိုင်မှုမတူဘဲ လက်မှတ်ရေးထိုးခြင်းခွဲခြားသည် (pre-execution authorization_* နှင့် post-execution result_* ခွဲခြားထားသည်)၊ ယင်းသည် authorization ဆုံးဖြတ်ချက်နှင့် ကိုင်တွယ်မှုကို ကွဲပြားသူများ သို့မဟုတ် ကာလအတွင်းကွဲပြားသည့် actor များ လုပ်သော အခါအသုံးဝင်သည်။ ဤသည်သည် သင်ခန်းစာတွင် သင်ကြားသော receipt ပုံစံအပေါ် ထပ်တိုးပေါင်းစပ်နိုင်သည်။
- **Payload ဖွဲ့စည်းမှု။** receipt သည် `result_hash` တွင် ထည့်သွင်းထားသော bytes များအားလုံးကို သီးသန့်အသိအမှတ်ပြုသည်။ အမှန်တကယ်သော payload များသည် တစ်ခါတည်း tool မှ ရလဒ်ထက် ပို၍ သုံးစွဲမှု အလွန် ပြည့်စုံသည်။ ပြုစုရေး ဆုံးဖြတ်ချက်မတိုင်မီ အကြောင်းအရာများ (model ခန့်မှန်းချက်, ရွေးချယ်ထားသော ရွေးချယ်မှုများ, သက်သေများနှင့် ၎င်း၏ ပြည့်စုံမှု, အန္တရာယ်၊ တာဝန်ခံမှု ချိတ်ဆက်မှု, gate အဖြေ) များကို payload အတွင်း သွင်းထားနိုင်ပြီး receipt တစ်ခုဖြင့် ပိတ်ဆို့ထားသည်။ ၎င်းသည် receipt ပုံစံကို အနည်းဆုံးထိန်းသိမ်းရန်ဖြစ်ပြီး payload schema များကို domain အလိုက် တိုးတက်စေသည်။
- **တစ်မျိုးတည်း မဟုတ်သည့် ပလက်ဖောင်းများအကြား သဟဇာတရှိမှု။** receipt ပုံစံတူသော အခြား အစီအစဉ်များ (Python, TypeScript, Rust, Go) သည် တူညီသော စမ်းသပ်မှု စံနှုန်းများအား အတည်ပြုကြသည်။ မိမိကိုယ်တိုင် ဖန်တီးပါက ဖွင့္လှစ်ထားသော စမ်းသပ်မှု ဗက်က်တာများနှင့် ထိတွေ့ပြီး ကွာဟမှုမရှိကြောင်း အတည်ပြုပါ။
- **Post-quantum သို့ ရွေ့လျားခြင်း။** Ed25519 သည် ယနေ့အခါ ကျယ်ပြန့်စွာ အသုံးပြုသော်လည်း quantum-resistant မဟုတ်ပါ။ receipt ပုံစံသည် algorithm-agile ဖြစ်သည်။ `signature.alg` ကွက်လပ်သည် မလိုအပ်သည့် ကာလတွင် post-quantum လက်မှတ်မှု စံသတ်မှတ်ချက် olan `ML-DSA-65` (NIST) ကိုပါ ထားနိုင်သည်။ ရွေ့လျားမှုကာလ တစ်ခုအတွင်း receipt များကို နှစ်ဖက်လက်မှတ်ရေးဆွဲထားရန် စီစဉ်ပါ။
