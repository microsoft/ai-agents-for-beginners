## 💻 Esecuzione del Codice

L'implementazione completa è disponibile in `03.dotnet-agent-framework-workflow-ghmodel-concurrent.cs`. Questo file dimostra un **flusso di lavoro concorrente Fan-Out/Fan-In** per la pianificazione di viaggi:

### 🏗️ **Architettura del Flusso di Lavoro**

```
User Request → ConcurrentStartExecutor → [Researcher Agent || Planner Agent] → ConcurrentAggregationExecutor → Final Output
```

**Componenti Chiave:**

1. **ConcurrentStartExecutor**: Trasmette la richiesta utente a tutti gli agenti simultaneamente
2. **Agente Ricercatore**: Analizza destinazioni e attrazioni in parallelo
3. **Agente Pianificatore**: Crea piani di viaggio dettagliati in parallelo
4. **ConcurrentAggregationExecutor**: Raccoglie e combina i risultati di entrambi gli agenti

### 🎯 **Pattern Fan-Out/Fan-In**

Questo flusso di lavoro dimostra il classico pattern **Fan-Out/Fan-In**:
- **Fan-Out**: Un messaggio di input viene trasmesso a più agenti simultaneamente
- **Elaborazione Concorrente**: Molti agenti lavorano in parallelo allo stesso compito
- **Fan-In**: I risultati di tutti gli agenti vengono raccolti e aggregati in un'unica uscita

### 🔍 Comprendere gli Esecutori Personalizzati

**ConcurrentStartExecutor:**
- Implementa `IMessageHandler<string>` per accettare input di tipo stringa
- Trasmette messaggi a tutti gli agenti connessi
- Invia un `TurnToken` per innescare l'elaborazione concorrente

**ConcurrentAggregationExecutor:**
- Implementa `IMessageHandler<ChatMessage>` per ricevere risposte degli agenti
- Raccoglie i messaggi in modo thread-safe
- Aggrega quando arrivano tutte le risposte attese
- Restituisce l'output finale con `context.YieldOutputAsync()`

### ⚡ Benefici sulle Prestazioni

**Concorrente vs Sequenziale:**
- Sequenziale: Agente1 (30s) → Agente2 (30s) = **60 secondi totali**
- Concorrente: Agente1 (30s) || Agente2 (30s) = **30 secondi totali**

**Miglioramento del throughput**: Fino a N volte più veloce per N agenti concorrenti (dipendente da carico e risorse)

### 🛡️ Gestione degli Errori

Il flusso di lavoro gestisce i guasti di singoli agenti con grazia:
- Se un agente fallisce, gli altri continuano l'elaborazione
- L'aggregatore può implementare logiche di timeout
- Risultati parziali possono essere restituiti se necessario
