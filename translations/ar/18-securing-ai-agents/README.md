# تأمين وكلاء الذكاء الاصطناعي باستخدام الإيصالات التشفيرية

## المقدمة

سيغطي هذا الدرس:

- لماذا تُعد سجلات التدقيق لوكلاء الذكاء الاصطناعي مهمة للامتثال، وتصحيح الأخطاء، والثقة.
- ما هو الإيصال التشفيري وكيف يختلف عن سجل بدون توقيع.
- كيفية إنتاج إيصال موقع لاستدعاء أداة الوكيل باستخدام بايثون بسيط.
- كيفية التحقق من الإيصال دون اتصال واكتشاف التلاعب.
- كيفية ربط الإيصالات بحيث يؤدي إزالة أو إعادة ترتيب إيصال إلى كسر السلسلة.
- ماذا تثبت الإيصالات وماذا لا تثبت صراحةً.

## أهداف التعلم

بعد إكمال هذا الدرس، ستعرف كيف:

- تحديد أوضاع الفشل التي تحفز إثبات الأصل التشفيري لإجراءات الوكيل.
- إنتاج إيصال موقع بـ Ed25519 على حمولة JSON معيارية.
- التحقق من الإيصال بشكل مستقل باستخدام المفتاح العام فقط.
- اكتشاف التلاعب عن طريق إعادة تشغيل التحقق على إيصال معدل.
- بناء سلسلة متسلسلة بالإيصالات وشرح أهمية السلسلة.
- التعرف على الحد الفاصل بين ما تثبته الإيصالات (النسبة، السلامة، الترتيب) وما لا تثبته (صحة الإجراء، صحة السياسة).

## المشكلة: سجل تدقيق وكيلك

تخيل أنك نشرت وكيلاً ذكياً لشركة Contoso Travel. يقرأ الوكيل طلبات العملاء، يستدعي واجهة برمجة تطبيقات الرحلات للبحث عن الخيارات، ويحجز مقاعد نيابة عن العميل. في الربع الماضي، عالج الوكيل 50,000 حجز.

اليوم يصل مدقق. يسأل سؤالاً بسيطاً: "أرني ماذا فعل وكيلك."

تسلمه ملفات السجل الخاصة بك. ينظر المدقق إليها ويسأل السؤال الأصعب: "كيف أعرف أن هذه السجلات لم تُحرر؟"

هذه هي مشكلة سجل التدقيق. معظم عمليات نشر الوكلاء اليوم تعتمد على:

- **سجلات التطبيقات**: يكتبها الوكيل نفسه، يمكن تعديلها من قبل أي شخص لديه وصول إلى نظام الملفات.
- **خدمات تسجيل السحابة**: تظهر التلاعب على مستوى المنصة ولكن فقط إذا وثق المدقق في مشغل المنصة.
- **سجلات معاملات قواعد البيانات**: مناسبة جيدًا لتغييرات قاعدة البيانات ولكن ليس لاستدعاءات الأدوات العشوائية.

لا يمكن لأي من هذه الإجابة على سؤال المدقق دون أن يضطر المدقق إلى الثقة في شخص ما (أنت، مزود السحابة، بائع قاعدة البيانات). للاستخدام الداخلي، عادة ما تكون هذه الثقة مقبولة. للحمولات المنظمة (المالية، الرعاية الصحية، أي شيء يخضع لقانون الذكاء الاصطناعي في الاتحاد الأوروبي)، ليست كذلك.

تحل الإيصالات التشفيرية هذه المشكلة بجعل كل إجراء وكيل قابل للتحقق بشكل مستقل. لا يحتاج المدقق إلى الوثوق بك. يحتاج فقط إلى مفتاحك العام والإيصال نفسه.

## ما هو الإيصال التشفيري؟

الإيصال هو كائن JSON يسجل ما فعله الوكيل، موقعاً بتوقيع رقمي.

```mermaid
flowchart LR
    A[الوكيل يستدعي أداة] --> B[بناء حمولة الإيصال]
    B --> C[تحويل JSON حسب RFC 8785 إلى الشكل القانوني]
    C --> E[توقيع Ed25519 للبايتات القانونية]
    E --> F[إيصال مع التوقيع]
    F --> G[المراجع يتحقق دون اتصال]
    G --> H{هل التوقيع صالح؟}
    H -- yes --> I[إثبات مقاوم للتلاعب]
    H -- no --> J[تم رفض الإيصال]
```

يبدو الإيصال البسيط هكذا:

```json
{
  "type": "agent.tool_call.v1",
  "agent_id": "contoso-travel-bot",
  "tool_name": "lookup_flights",
  "tool_args_hash": "sha256:a3f9c1...",
  "result_hash": "sha256:7b2e1d...",
  "policy_id": "contoso-travel-policy-v3",
  "timestamp": "2026-04-25T14:30:00Z",
  "sequence": 47,
  "previous_receipt_hash": "sha256:9d4e6a...",
  "signature": {
    "alg": "EdDSA",
    "sig": "c5af83...",
    "public_key": "8f3b2c..."
  }
}
```

ثلاث خصائص تقوم بالعمل:

1. **التوقيع**. يتم توقيع الإيصال بواسطة بوابة الوكيل باستخدام مفتاح خاص Ed25519. يمكن لأي شخص يملك المفتاح العام المقابل التحقق من التوقيع دون اتصال. التلاعب بأي حقل يلغي التوقيع.

2. **الترميز المعياري**. قبل التوقيع، يتم تسلسل الإيصال باستخدام مخطط معيار JSON (JCS، RFC 8785). هذا يضمن أن تنفيذين ينتجان نفس الإيصال المنطقي ينتجان نفس المحتوى البايت بالبايت. بدون التقييس، محولات JSON المختلفة ستنتج توقيعات مختلفة لنفس المحتوى.

3. **تسلسل الهاش**. يربط حقل `previous_receipt_hash` كل إيصال بالذي قبله. إزالة أو إعادة ترتيب إيصال يكسر كل الإيصالات التي تليه. يظهر التلاعب على مستوى السلسلة حتى لو تم تجاوز توقيعات فردية.

معًا تقدم هذه الخصائص ثلاث ضمانات:

- **النسبة**: هذا المفتاح وقع هذا المحتوى.
- **السلامة**: المحتوى لم يتغير منذ التوقيع.
- **الترتيب**: هذا الإيصال جاء بعد ذلك الإيصال ضمن السلسلة.

## إنتاج إيصال في بايثون

لا تحتاج إلى مكتبة خاصة لإنتاج إيصال. البدائيات التشفيرية متاحة على نطاق واسع والمنطق مجرد عشرات الأسطر من بايثون.

تمشي تمارين التطبيق العملي في `code_samples/18-signed-receipts.ipynb` عبر التدفق الكامل. النسخة المختصرة:

```python
import json
import hashlib
import base64
from nacl import signing
from jcs import canonicalize  # JSON المعياري RFC 8785

def b64url_nopad(data: bytes) -> str:
    return base64.urlsafe_b64encode(data).decode("ascii").rstrip("=")

def sha256_canonical(obj) -> str:
    """SHA-256 of a Python object's JCS-canonical JSON form."""
    return f"sha256:{hashlib.sha256(canonicalize(obj)).hexdigest()}"

# توليد أو تحميل مفتاح التوقيع (في الإنتاج، خزن في خزنة المفاتيح)
signing_key = signing.SigningKey.generate()
verify_key = signing_key.verify_key

# بناء حمولة الإيصال (بدون توقيع بعد)
tool_args = {"origin": "SYD", "destination": "LAX"}
tool_result = [{"flight": "QF11", "price": 1850, "stops": 0}]

payload = {
    "type": "agent.tool_call.v1",
    "agent_id": "contoso-travel-bot",
    "tool_name": "lookup_flights",
    "tool_args_hash": sha256_canonical(tool_args),
    "result_hash": sha256_canonical(tool_result),
    "policy_id": "contoso-travel-policy-v3",
    "timestamp": "2026-04-25T14:30:00Z",
    "sequence": 0,
    "previous_receipt_hash": None,
}

# توحيد الشكل والتوقيع على بايتات JCS مباشرة. PureEdDSA يقوم بالتجزئة داخلياً.
canonical_bytes = canonicalize(payload)
signature_bytes = signing_key.sign(canonical_bytes).signature

# إرفاق كائن توقيع منظم.
receipt = {
    **payload,
    "signature": {
        "alg": "EdDSA",
        "sig": b64url_nopad(signature_bytes),
        "public_key": b64url_nopad(bytes(verify_key)),
    },
}
```

هذه هي خط أنابيب التوقيع بالكامل. تمشي التمارين في الدفتر عبر كل خطوة.

## التحقق من الإيصال واكتشاف التلاعب

التحقق هو العملية العكسية:

```python
import base64
import hashlib
from nacl import signing
from nacl.exceptions import BadSignatureError
from jcs import canonicalize

def b64url_decode(s: str) -> bytes:
    padding = "=" * ((4 - len(s) % 4) % 4)
    return base64.urlsafe_b64decode(s + padding)

def verify_receipt(receipt: dict) -> bool:
    # التوقيع هو كائن منظم: {"alg", "sig", "public_key"}.
    sig_obj = receipt.get("signature")
    if not sig_obj or sig_obj.get("alg") != "EdDSA":
        return False

    # إعادة بناء الحمولة التي تم توقيعها فعليًا (كل شيء ما عدا التوقيع).
    payload = {k: v for k, v in receipt.items() if k != "signature"}

    canonical_bytes = canonicalize(payload)

    try:
        verify_key = signing.VerifyKey(b64url_decode(sig_obj["public_key"]))
        verify_key.verify(canonical_bytes, b64url_decode(sig_obj["sig"]))
        return True
    except BadSignatureError:
        return False
```

تأخذ هذه الدالة إيصالًا وترجع `True` إذا كان التوقيع صالحًا، و`False` خلاف ذلك. لا اتصال شبكة، لا اعتماد خدمة، لا حاجة للثقة بأي طرف ثالث.

لرؤية اكتشاف التلاعب عمليًا، يتناول الدفتر:

1. إنتاج إيصال صالح وتأكيد أنه يتحقق.
2. تعديل بايت واحد من حقل `tool_args_hash`.
3. إعادة التحقق ورؤية الفشل.

هذا هو العرض العملي لإثبات أن الإيصالات تظهر التلاعب: أي تعديل، مهما كان صغيراً، يكسر التوقيع.

## ربط الإيصالات لوكلاء متعددين الخطوات

يحمي إيصال واحد موقع إجراء واحد. سلسلة الإيصالات تحمي تسلسلاً.

```mermaid
flowchart LR
    R0[إيصال 0<br/>التكوين] --> R1[إيصال 1]
    R1 --> R2[إيصال 2]
    R2 --> R3[إيصال 3]
    R1 -. previous_receipt_hash .-> R0
    R2 -. previous_receipt_hash .-> R1
    R3 -. previous_receipt_hash .-> R2
```

يسجل كل إيصال هاش الإيصال قبله. لإزالة الإيصال 2 بهدوء، يحتاج المهاجم إلى إما:

- تعديل حقل `previous_receipt_hash` في الإيصال 3 (يكسر توقيع الإيصال 3)، أو
- تزوير توقيع جديد على الإيصال 3 المعدل (يتطلب المفتاح الخاص للوكيل).

إذا كان المفتاح الخاص في خزنة مفاتيح مادية وتنشر المفتاح العام مع كل إيصال، فلا يمكن لأي هجوم أن يتم دون اكتشاف.

يتناول الدفتر:

1. بناء سلسلة من ثلاثة إيصالات.
2. التحقق من أن `previous_receipt_hash` لكل إيصال يطابق هاش الإيصال السابق.
3. التلاعب في إيصال واحد بالمنتصف ورؤية السلسلة تكسر عند تلك النقطة بالضبط.

هذه هي الطريقة لإنتاج سجل تدقيق يمكن لمدقق خارجي التحقق منه دون الاعتماد عليك.

## ما تثبته الإيصالات (وما لا تثبته)

هذه هي أهم قسم في هذا الدرس. الإيصالات قوية لكن قوتها محدودة.

**الإيصالات تثبت ثلاثة أشياء:**

1. **النسبة**: قام مفتاح محدد بتوقيع حمولة محددة.
2. **السلامة**: الحمولة لم تتغير منذ التوقيع.
3. **الترتيب**: جاء هذا الإيصال بعد ذلك في سلسلة الهاش.

**الإيصالات لا تثبت:**

1. **الصحة**: أن كان إجراء الوكيل هو الإجراء الصحيح. يمكن توقيع إيصال بصورة نظيفة على إجابة خاطئة تمامًا كما هو الحال على إجابة صحيحة.
2. **الامتثال للسياسة**: أن السياسة المشار إليها في `policy_id` قد تم تقييمها فعليًا، أو أن تلك السياسة كانت ستسمح بهذا الإجراء إذا تمت مراجعتها. يسجل الإيصال ما تم الادعاء به، لا ما تم تنفيذه.
3. **الهوية بخلاف المفتاح**: يقول الإيصال "هذا المفتاح وقع هذا المحتوى." لا يقول "هذا الإنسان وافق على هذا." ربط المفتاح بشخص أو منظمة يتطلب بنية هوية منفصلة (دليل، سجل مفتاح عام، إلخ).
4. **صدق المدخلات**: إذا استلم الوكيل طلبًا معدلًا وتصرف بناءً عليه، يسجل الإيصال الإجراء بأمانة. الإيصالات تأتي بعد التحقق من المدخلات، وليست بديلاً عنه.

هذا الحد الفاصل مهم لسببين:

- يخبرك بما هي الاستخدامات المفيدة للإيصالات: جعل سلوك الوكيل قابلاً للتدقيق وموضح التلاعب، حتى عبر الحدود التنظيمية.
- يخبرك ما الطبقات الإضافية التي تحتاجها بعد: التحقق من المدخلات (الدرس 6)، تنفيذ السياسة (مذكور باختصار أدناه)، وبنية الهوية (خارج نطاق هذا الدرس).

خطأ شائع هو الاعتقاد بأن "لدينا إيصالات" يعني "نحن منظمون." الأمر ليس كذلك. الإيصالات هي الأساس. الحوكمة هي النظام الذي تبنيه فوق ذلك.

## إثبات أن الإنسان أقر الإجراء المحدد

النقطة 3 أعلاه تستحق قسمًا خاصًا: إيصال الإجراء يقول "هذا المفتاح وقع هذا المحتوى"، وليس أبدًا "إنسان أذن بهذا." للإجراءات عالية المخاطر (استرجاع الأموال، الحذف، التحويلات البنكية)، تتطلب أطر الحوكمة بشكل متزايد البيان المفقود ذاته، ويمكن إنتاجه بنفس البدائيات التي بنيتها في هذا الدرس.

يضيف الدفتر التابع `code_samples/human-authorization-receipts.ipynb` نوع إيصال ثاني، `human.approval.v1`، في نفس شكل الظرف مثل إيصالات الدرس (حمولة مكتوبة توقيع Ed25519 فوق بايتات JCS المعيارية، مع كائن `signature` خارج البايتات الموقعة). يقوم الموافق المسمى بتوقيع **الإجراء المعياري الكامل وهضمته** قبل التنفيذ؛ يحمل إيصال إجراء الوكيل **نفس هضم الإجراء** و`parent_approval_ref`، وهو `receipt_hash` للموافقة، نفس الاتفاقية في `previous_receipt_hash` في السلسلة التي بنيتها أعلاه. يمشي `verify_chain` المزدوج كلا القطعتين تحت **سجلات مفتاح مثبتة منفصلة** (مفاتيح الموافق مقابل مفاتيح الوكيل)، لذا يشارك مسار الكود لكن السلطات لا تتشارك أبدًا.

الخاصية التي توفرها، مع التعبير الدقيق: *الإنسان أقر هذا الإجراء تحديدًا، والوكيل نفذ ذلك الإجراء الموافق عليه بالضبط.* ترفض مركبات الدفتر الرافضة هذه الخاصية لتجعلها حقيقية وليست مجرد زعم:

- المجموعة الكلاسيكية: التلاعب، نائب مرتبك، إعادة التشغيل، مفاتيح مزورة على أي جهة، مدخلات مشوهة؛
- **السلطة القديمة**: توقيع ما يزال يتحقق منه، ولكنه رفض بأي حال لأن نسخة السياسة تغيرت، أو مفتاح الموافق تم استبداله من السجل المثبت، أو الموافقة انتهت صلاحيتها قبل التنفيذ؛
- **استبدال الهضم**: إيصال إجراء موقع بشكل صحيح يشير إلى *موافقة حقيقية* تربط *إجراء معياري مختلف*.

كل فشل يرفض لسبب مميز، لذلك يمكن للمدقق قراءة الرفض ومعرفة ما إذا كانت السلطة قديمة أو تغير الإجراء المنفذ. القاعدة التي يعلمها الدفتر: الموافقة الموقعة ليست السلطة بحد ذاتها. السلطة توجد فقط إذا ربط كلا الإيصالين بنفس الإجراء المعياري عند التنفيذ. إيصال الموافقة البشرية هو تركيب تعليمي محدد من هذا الدرس، وليس نوع إيصال معرف بـ `draft-farley-acta-signed-receipts`.

## مراجع الإنتاج

كود بايثون في هذا الدرس بسيط عن قصد لتتمكن من قراءة كل سطر وفهم ما يحدث بالضبط. في الإنتاج، لديك خياران:

1. **البناء مباشرة على البدائيات التشفيرية.** الخمسون سطرًا التي شاهدتها أعلاه كافية للعديد من حالات الاستخدام. مكتبات PyNaCl (Ed25519) وحزمة `jcs` (JSON المعياري) مكتبات صيانة ومراجعة جيدة.

2. **استخدام مكتبة إيصالات للإنتاج.** تنفذ عدة مشاريع مفتوحة المصدر نفس النموذج مع ميزات إضافية (تدوير المفاتيح، التحقق الجماعي، توزيع مجموعة JWK، التكامل مع محركات السياسة):
   - تستخدم خط أنابيب التوقيع اتفاقيات JCS ونطاق التوقيع في مسودة إنترنت IETF مستقلة ([`draft-farley-acta-signed-receipts`](https://datatracker.ietf.org/doc/draft-farley-acta-signed-receipts/)، المراجعة 02). إيصال الدرس التعليمي المسطح يختلف عن الظرف `{payload, signature}` في المسودة وليس مقدماً كتنفيذ متوافق. تنشر المسودة مجموعة توافق مشتركة ([agent-governance-testvectors](https://github.com/ScopeBlind/agent-governance-testvectors)) للتطبيقات التي تستهدف تنسيقها السلكي.
   - تجمع مجموعة أدوات حوكمة الوكيل من مايكروسوفت الإيصالات مع القرارات السياسية المبنية على Cedar؛ انظر الدرس 33 في ذلك المستودع لمثال شامل.
   - توفر حزم `protect-mcp` (npm) و `@veritasacta/verify` (npm) تنفيذًا بنيودج مخصصًا لتوقيع الإيصالات والتحقق دون اتصال، مخصصة لتغليف أي خادم MCP بسجل تدقيق موضح التلاعب، بما في ذلك تدفق "انتظار التوقيع المشترك" حيث يصدر إجراء مُعلق إيصال موافقة مرتبط بهضم الإجراء (مدعوم بـ WebAuthn في تدفق سطح المكتب)، وهو نفس نمط إيصال الموافقة المستخدمة في دفتر الموافقة البشرية أعلاه.
   - يوفر **[nobulex](https://github.com/arian-gogani/nobulex)** SDK بايثون (`pip install nobulex`) نفس نموذج التوقيع Ed25519 + JCS في بايثون مع تكاملات LangChain وCrewAI، بما في ذلك نشر ناقلات اختبار التحقق المتبادل ورسم خرائط الالتزام المساهمة عبر [OWASP PR #2210](https://github.com/OWASP/CheatSheetSeries/pull/2210).

القرار بين بناء مكتبتك الخاصة أو استخدام مكتبة يعكس القرار بين كتابة مكتبة JWT بنفسك أو استخدام مكتبة مجربة: كلاهما معقول؛ توفر المكتبة الوقت وتقلل من سطح التدقيق؛ النهج من الصفر يجبرك على فهم كل بدائي. يعلمك هذا الدرس الطريقة من الصفر حتى يكون لديك الأساس لأي اختيار.

## اختبار المعرفة

اختبر فهمك قبل الانتقال إلى تمرين الممارسة.

**1. يتم توقيع الإيصال باستخدام مفتاح Ed25519 الخاص بالوكيل. يمتلك المدقق المفتاح العام فقط. هل يمكن للمدقق التحقق من الإيصال دون اتصال؟**

<details>
<summary>الإجابة</summary>

نعم. يتطلب التحقق باستخدام Ed25519 المفتاح العام والبايتات الموقعة فقط. لا اتصال شبكة، ولا اعتماد خدمة. هذه الخاصية تجعل الإيصالات مفيدة في البيئات المعزولة، متعددة المنظمات، أو المنخفضة الثقة.
</details>

**2. يغير مهاجم حقل `policy_id` في إيصال ادعاءً بأنه تم الحكم عليه بسياسة أكثر تساهلاً. كان التوقيع على الحمولة الأصلية. ماذا يحدث أثناء التحقق؟**

<details>
<summary>الإجابة</summary>


فشل التحقق. تم حساب التوقيع على البايتات المعيارية للحمل الأصلي؛ تعديل أي حقل يغير تلك البايتات، مما يجعل التوقيع غير صالح. يجب على المهاجم أن يمتلك المفتاح الخاص لإنتاج توقيع جديد صالح، وهو ما لا يملكه.
</details>

**3. لماذا تتضمن الإيصال `tool_args_hash` و `result_hash` بدلاً من الوسائط والنتيجة الخام؟**

<details>
<summary>الجواب</summary>

لسببين. أولاً، قد يحتاج الإيصال إلى الأرشفة أو الإرسال في بيئات يكون فيها تسرب المحتوى الخام (المعلومات الشخصية، بيانات الأعمال) بمثابة مشكلة. التشفير يحافظ على صغر حجم الإيصال وسرية المحتوى؛ يتحقق المدقق من ملاءمة الهاش مع نسخة مخزنة منفصلة من المحتوى الفعلي. ثانيًا، الحجم الثابت للهاش؛ فإن الإيصال الذي يحتوي على هاشات له حد لحجمه بغض النظر عن حجم المدخلات والمخرجات.
</details>

**4. يرتبط حقل `previous_receipt_hash` بكل إيصال بسابقه. إذا حذف مهاجم إيصالًا من وسط السلسلة بهدوء، ما الذي يصبح غير صالح؟**

<details>
<summary>الجواب</summary>

كل إيصال جاء بعد المحذوف. لم تعد حقول `previous_receipt_hash` الخاصة بهم تطابق السلسلة الحقيقية (لأن الإيصال الذي أشاروا إليه لم يعد موجودًا، أو أن السلسلة الآن تشير إلى سابقة مختلفة). لإخفاء الحذف، يجب على المهاجم إعادة توقيع كل إيصال لاحق، وهذا يتطلب المفتاح الخاص.
</details>

**5. إذا تم التحقق من صحة الإيصال بشكل نظيف، هل هذا يثبت أن عمل الوكيل كان صحيحًا أو منطقيًا أو متوافقًا مع السياسة؟**

<details>
<summary>الجواب</summary>

لا. يثبت الإيصال الصحيح ثلاثة أشياء: العزو (أن هذا المفتاح وقع هذا المحتوى)، النزاهة (المحتوى لم يتغير)، والترتيب (أن هذا الإيصال جاء بعد ذاك). لكنه لا يثبت أن العمل كان صحيحًا، أو أن السياسة المسماة في `policy_id` تم تقييمها فعلاً، أو أن الوكيل اتبع كل قاعدة. تجعل الإيصالات سلوك الوكيل قابلاً للتدقيق، وليس بالضرورة صحيحًا. هذه هي الحدود الأهم في الدرس.
</details>

## تمرين عملي

افتح `code_samples/18-signed-receipts.ipynb` وأكمل الأقسام الأربعة كلها:

1. **القسم 1**: قم بتوقيع إيصالك الأول وتحقق منه.
2. **القسم 2**: قم بالتلاعب بالإيصال وراقب فشل التحقق.
3. **القسم 3**: ابنِ سلسلة من ثلاثة إيصالات وتحقق من سلامة السلسلة.
4. **القسم 4**: طبق النمط على وكيل مبني بإطار عمل Microsoft Agent: لف استدعاء أداة بتوقيع الإيصال، ثم تحقق من الإيصال بشكل مستقل.

**التحدي الإضافي 1:** وسع مخطط الإيصال بحقل إضافي من اختيارك (مثل معرف طلب للتتبع)، حدّث منطق التوقيع المعياري ليشمله، وتأكد من أن الإيصال يعبر دورة التحقق بنجاح. ثم عدل الحقل بعد التوقيع وتأكد من فشل التحقق. هذا يجبرك على فهم كيف يساهم كل بايت من الترميز المعياري في التوقيع.

**التحدي الإضافي 2:** هشِّن اثنين من إيصالاتك معًا (اربط البايتات المعيارية الخاصة بهم بترتيب حتمي) ودمج الناتج كحقل جديد في إيصال ثالث قبل توقيعه. تحقق من أن الثلاثة إيصالات لا تزال تمر بدورة التحقق. لقد صنعت للتو إثبات تضمين ذو خطوة واحدة: يمكن لأي شخص يحمل الإيصال الثالث إثبات وجود الأول والثاني وقت التوقيع، دون الحاجة لكشف محتواهما. هذا هو النمط الذي تستخدمه إيصالات الإفصاح الانتقائي على نطاق واسع (التزامات ميركل، RFC 6962).

## خاتمة

تعطي الإيصالات التشفيرية لوكلاء الذكاء الاصطناعي سجل تدقيق:

- **قابل للتحقق بشكل مستقل**: يمكن لأي طرف مع المفتاح العمومي التحقق، دون اعتماد على خدمة.
- **مثبتة التلاعب**: أي تعديل يبطل التوقيع.
- **محمولة**: الإيصال ملف JSON صغير؛ يمكن أرشفته وإرساله والتحقق منه في أي مكان.
- **متوافقة مع المعايير**: مبنية على Ed25519 (RFC 8032)، JCS (RFC 8785)، و SHA-256، كلها بدائيات مستخدمة على نطاق واسع.

ليست بديلاً عن التحقق من المدخلات، تطبيق السياسات، أو بنية الهوية. إنها أساس لتلك الطبقات. عندما تنشر وكلاء في أحمال العمل المنظمة، أو العمليات متعددة المؤسسات، أو أي بيئة لا يمكن تحمل أن يثق المدقق المستقبلي بك، فإن الإيصالات هي كيف تجعل سجل التدقيق أمينًا.

أهم خلاصة: تثبت الإيصالات من قال ماذا ومتى. لا تثبت أن ما قيل كان صحيحًا أو صائبًا. تمسك بهذا التمييز بشدة. هو الفرق بين نظام نسب أمين ونظام مضلل.

## قائمة فحص الإنتاج

عندما تكون مستعدًا للانتقال من هذا الدرس إلى نشر وكلاء موقعين بالإيصالات في بيئة حقيقية:

- [ ] **انقل مفتاح التوقيع من جهاز المطور المحمول.** استخدم Azure Key Vault، AWS KMS، أو وحدة أمان أجهزة. المفتاح الخاص الذي يوقع إيصالاتك لا يجب أبداً أن يكون في تحكم المصدر أو نص واضح على أجهزة التطبيق.
- [ ] **انشر مفتاح التحقق العام.** يحتاج المدققون إليه للتحقق دون اتصال. النمط القياسي هو مجموعة JWK على عنوان URL معروف (RFC 7517)، مثلاً `https://your-org.example.com/.well-known/agent-keys.json`.
- [ ] **رسخ السلسلة خارجيًا.** اكتب دوريًا هاش رأس السلسلة الأخير إلى سجل شفافية (Sigstore Rekor، سلطة الطابع الزمني RFC 3161، أو نظام داخلي ثاني) ليؤكد طرف خارجي "وجود هذه السلسلة في هذا الوقت."
- [ ] **خزن الإيصالات بلا تغيير.** التخزين الذي يسمح بالإضافة فقط (تخزين Azure مع سياسات عدم التغيير، قفل AWS S3) يمنع موظف داخلي من إعادة كتابة التاريخ على طبقة التخزين.
- [ ] **قرر بشأن الاحتفاظ.** تتطلب أنظمة الامتثال تفريغًا متعدد السنوات. خطط لنمو الإيصالات (كل إيصال ~500 بايت؛ وكيل يقوم بـ 10 آلاف استدعاء يوميًا ينتج ~1.8 جيجابايت سنويًا).
- [ ] **وثق ما لا تغطيه الإيصالات.** تثبت الإيصالات العزو والنزاهة والترتيب. يجب أن يذكر كتاب التشغيل الخاص بك صراحةً ما الضوابط الإضافية (التحقق من المدخلات، تنفيذ السياسة، تحديد المعدل، بنية الهوية) التي تقف إلى جانب الإيصالات في موقف الحوكمة لديك.

## ما بعد هذا الدرس

يغطي هذا الدرس توقيع إيصال واحد وتسلسلات متسلسلة هاشيًا. تتركب نفس البدائيات لأشكال أكثر تقدمًا قد تواجهها مع تطور موقف الحوكمة الخاص بك:

- **الإفصاح الانتقائي.** عندما يتم الالتزام بحقول الإيصال بشكل مستقل (شجرة ميركل بنمط RFC 6962)، يمكنك الكشف عن حقول محددة لمدققين معينين وإثبات أن الباقي لم يتغير دون كشفها. مفيد عندما يجب أن يلبي نفس الإيصال تدقيقًا شاملاً (يطلب الاكتمال) وتنظيمات تقليل البيانات مثل GDPR (تريد أن يرى المدقق أقل قدر ممكن).
- **إلغاء الإيصال.** إذا تم اختراق مفتاح التوقيع، تحتاج لطريقة لوضع علامة على كل الإيصالات التي وقعها المفتاح كغير موثوقة من نقطة زمنية فصاعدًا. الأنماط القياسية: مفاتيح توقيع قصيرة الأجل مع قائمة إلغاء منشورة، أو سجل شفافية مع إدخالات الإلغاء.
- **الإيصالات الثنائية الجانب / ذات التوقيع المقسوم.** بعض التطبيقات تقسم الحمولة الموقعة إلى نصف ما قبل التنفيذ (`authorization_*`) ونصف ما بعد التنفيذ (`result_*`) بتوقيعات مستقلة، مفيد عندما ينتج قرار التفويض والنتيجة الملاحظة جهات مختلفة أو في أوقات مختلفة. يضاف هذا فوق تنسيق الإيصال المعلم في هذا الدرس.
- **تركيب الحمولة.** يختم الإيصال أياً كان البايتات التي تضعها في `result_hash`. عادة ما تكون الحمولة الحقيقية أكثر ثراءً من نتيجة استدعاء أداة واحدة: يمكن أن يعيش داخل الحمولة التفكير ما قبل القرار (تنبؤ النموذج، الخيارات المتبعة، الأدلة واكتمالها، موقف المخاطر، سلسلة المساءلة، نتيجة البوابة)، كلها مختومة بإيصال واحد. هذا يحافظ على تنسيق الإيصال بسيطًا بينما يسمح لتطور مخططات الحمولة مجالاً مجالًا.
- **الامتثال بين التنفيذات.** عدة تطبيقات مستقلة لنفس تنسيق الإيصال (Python، TypeScript، Rust، Go) تتحقق عبرًا ضد متجهات اختبار مشتركة. إذا صنعت تطبيقك الخاص، التحقق مقابل المتجهات المنشورة يؤكد التوافق في الاتصال.
- **الهجرة لما بعد الكم.** Ed25519 مستخدم على نطاق واسع اليوم لكنه ليس مقاومًا لكم الكمومي. تنسيق الإيصال مرن خوارزميًا: الحقل `signature.alg` يمكن أن يحمل `ML-DSA-65` (معيار التوقيع لما بعد الكم من NIST) عندما تحتاج للهجرة. خطط لفترة انتقالية حيث تكون الإيصالات موقعة توقيعًا مزدوجًا.
