# ಕ್ರಿಪ್ಟೋಗ್ರಾಫಿಕ್ ರಸೀದಿಗಳೊಂದಿಗೆ AI ಏಜೆಂಟ್ಗಳನ್ನು ಸುರಕ್ಷಿತಗೊಳಿಸುವುದು

## ಪರಿಚಯ

ಈ ಪಾಠವು ಇವುಗಳನ್ನು ಒಳಗೊಂಡಿರುತ್ತದೆ:

- ಅನುಕೂಲತೆ, ಡೀಬಗ್, ಮತ್ತು ನಂಬಿಕೆಗೆ AI ಏಜೆಂಟ್ಗಳಿಗೆ ಆಡಿಯಟ್ ಟ್ರೇಲ್‌ಗಳು چرا ಮುಖ್ಯ.
- ಕ್ರಿಪ್ಟೋಗ್ರಾಫಿಕ್ ರಸೀದಿ ಎಂದರೇನು ಮತ್ತು ಅದು ಅಸೈನ್ ಮಾಡದ ಲಾಗ್ ಲೈನಿನಿಂದ ಹೇಗೆ ಭಿನ್ನ.
- ಪ್ಲೇನ್ ಪೈಥಾನ್‌ನಲ್ಲಿ ಏಜೆಂಟ್ ಸಾಧನ ಕರೆಗಾಗಿ ಸಹಿ ಮಾಡಲಾದ ರಸೀದಿ ಹೇಗೆ ಉತ್ಪಾದಿಸುವುದು.
- ರಸೀದಿಯನ್ನು ಆಫ್‌ಲೈನ್‌ನಲ್ಲಿ ಪರಿಶೀಲಿಸುವುದು ಮತ್ತು ತತ್ತರಿಸಲಾಗುವಿಕೆಯನ್ನು ಪತ್ತೆಹಚ್ಚುವುದು.
- ರಸೀದಿಗಳನ್ನು ಸರಪಳಿ ಮಾಡಲು ಹೇಗೆ, ಇದರಿಂದ ಒಂದು ರಸೀದಿಯನ್ನು ತೆಗೆದುಹಾಕುವುದು ಅಥವಾ ಮರು ಆದೇಶಿಸುವುದು ಸರಪಳಿಯನ್ನು ಮುರಿದುಹಾಕುತ್ತದೆ.
- ರಸೀದಿಗಳು 무엇을 ಸಾಬೀತುಮಾಡುತ್ತವೆ ಮತ್ತು ಅವು ಸ್ಪಷ್ಟವಾಗಿ 무엇ನ್ನು ಸಾಬೀತುಮಾಡುವುದಿಲ್ಲ.

## ಅಧ್ಯಯನ ಗುರಿಗಳು

ಈ ಪಾಠವನ್ನು ಮುಗಿಸಿದ ನಂತರ ನೀವು ತಿಳಿಯಬಹುದು:

- ಏಜೆಂಟ್ ಕ್ರಿಯೆಗಳಿಗೆ ಕ್ರಿಪ್ಟೋಗ್ರಾಫಿಕ್ ಮೂಲಭೂತತೆಯನ್ನು ಹುಣಿಸಿ ಉತ್ತೇಜಿಸುವ ವಿಫಲತೆ ಮodoಗಳು ಅರ್ಥಮಾಡಿಕೊಂಡು.
- ಮಾನ್ಯವಾದ JSON ಪೇಲೋಡ್‌ ಮೇಲೆ Ed25519 ಸಹಿ ಮಾಡಲಾದ ರಸೀದಿ ಉತ್ಪಾದಿಸುವುದು.
- ಸಹಿದಾರರ ಸಾರ್ವಜನಿಕ ಕೀಮాత్రದ ಬಳಸಿಕೊಂಡು ರಸೀದಿಯನ್ನು ಸ್ವತಂತ್ರವಾಗಿ ಪರಿಶೀಲಿಸುವುದು.
- ತಯಾರಿಸಿದ ರಸೀದಿಯನ್ನು ಬದಲಾಯಿಸಿ ಪರಿಶೀಲನೆಯನ್ನು ಮತ್ತೆ ನಡೆಸಿ ತತ್ತರಿಸುವಿಕೆಯನ್ನು ಪತ್ತೆಹಚ್ಚುವುದು.
- ರಸೀದಿಗಳ ಹ್ಯಾಶ್-ಚೈನ್ ಸರಣಿಯನ್ನು ಸಂಯೋಜಿಸಿ ಮತ್ತು ಆ ಸರಣಿ ಪ್ರಮುಖವಾದ್ದನ್ನು ವಿವರಣೆ ಮಾಡುವುದು.
- ರಸೀದಿಗಳು 무엇ನ್ನು ಸಾಬೀತುಮಾಡುತ್ತವೆ (ಹೆಸರು ಸೂಚನೆ, ಅಖಂಡತೆ, ಕ್ರಮ) ಮತ್ತು 무엇ನ್ನು ಸಾಬೀತುಮಾಡುವುದಿಲ್ಲ (ಕ್ರಿಯೆಯ ಸರಿಯಾದತೆ, ನಿತಿಚಟುವಟಿಕೆಯ ಶ್ರೇಷ್ಠತೆ) ಎಂಬ ಭೇದ.

## ಸಮಸ್ಯೆ: ನಿಮ್ಮ ಏಜೆಂಟ್ನ ಆಡಿಯಟ್ ಟ್ರೇಲ್

ನೀವು Contoso ಟ್ರಾವೆಲ್‌ಗೆ ಒಂದು AI ಏಜೆಂಟ್ ಅನ್ನು ನಿಯೋಜಿಸಿದ್ದೀರಂತೆ. ಏಜೆಂಟ್ ಗ್ರಾಹಕರ ವಿನಂತಿಗಳನ್ನು ಓದಿ, ಫ್ಲೈಟ್‌ಗಳ API ಅನ್ನು ಕರೆ ಮಾಡಿ ಆಯ್ಕೆಗಳನ್ನು ಹುಡುಕಿ, ಮತ್ತು ಗ್ರಾಹಕರ ಪರವಾಗಿ ಸೀಟುಗಳನ್ನು ಬುಕ್ ಮಾಡುತ್ತದೆ. ಕಳೆದ ತ್ರೈಮಾಸಿಕದಲ್ಲಿ, ಏಜೆಂಟ್ 50,000 ಬುಕ್ಕಿಂಗ್‌ಗಳನ್ನು ಪ್ರಕ್ರಿಯೆಮಾಡಿತು.

ಇಂದು ಒಂದು ಆಡಿಯಟರ್ ಬರುವರು. ಅವರು ಸರಳ ಪ್ರಶ್ನೆಯನ್ನು ಕೇಳುತ್ತಾರೆ: "ನಿಮ್ಮ ಏಜೆಂಟ್ ಏನು ಮಾಡಿದೆಯೋ ತೋರಿಸಿ."

ನೀವು ನಿಮ್ಮ ಲಾಗ್ ಕಡತಗಳನ್ನು ನೀಡುತ್ತೀರಿ. ಆಡಿಯಟರ್ ಅವುಗಳನ್ನು ನೋಡುತ್ತಾನೆ ಮತ್ತು ಗಟ್ಟಿಯಾದ ಪ್ರಶ್ನೆ ಕೇಳುತ್ತಾನೆ: "ನಾನು ಹೇಗೆ ತಿಳಿದುಕೊಳ್ಳಬೇಕೆಂದು ಈ ಲಾಗ್‌ಗಳನ್ನು ಸಂಪಾದಿಸಲಾಗಿದೆ ಎಂದು?"

ಇದು ಆಡಿಯಟ್-ಟ್ರೇಲ್ ಸಮಸ್ಯೆ. ಇಂದಿನ ಬಹುತೇಕ ಏಜೆಂಟ್ ನಿಯೋಜನೆಗಳು ಇವುಗಳನ್ನು ಅವಲಂಬಿಸುತ್ತವೆ:

- **ಅಪ್ಲಿಕೇಶನ್ ಲಾಗ್‌ಗಳು**: ಏಜೆಂಟ್ ಸ್ವತಃ ಬರೆದು, ಯಾವುದೇ ಫೈಲ್-ಸಿಸ್ಟಮ್ ಪ್ರವೇಶವಿರುವವರು ಸಂಪಾದಿಸಬಹುದಾದವು.
- **ಮೇಘ ಲಾಗಿಂಗ್ ಸೇವೆಗಳು**: ವೇದಿಕೆ ಮಟ್ಟದಲ್ಲಿ ತತ್ತರೋಪಾಧಿ ಸ್ಫಟಿಕ ಆದರೆ ಆಡಿಯಟರ್ ವೇದಿಕೆ ಸಂಚಾಲಕನ ಮೇಲೆ ನಂಬಿಕೆ ಇಡುವಾಗ ಮಾತ್ರ.
- **ಡೇಟಾಬೇಸ್ ಟ್ರಾನ್ಸಾಕ್ಷನ್ ಲಾಗ್‌ಗಳು**: ಡೇಟಾಬೇಸ್ ಬದಲಾವಣೆಗಳಿಗೆ ಸೂಕ್ತವಾಗಿವೆ ಆದರೆ ಎಲ arbitrary ಸಾಧನ ಕರೆಗಳಿಗೆ ಅಲ್ಲ.

ಆಡಿಯಟರ್ ಯಾರನ್ನು ನಂಬಬೇಕೆಂಬುದಿಲ್ಲದೆ ಆಡಿಯಟರ್ ಪ್ರಶ್ನೆಗೆ ಉತ್ತರಿಸುವುದಿಲ್ಲ. ಆಂತರಿಕ ಬಳಕೆಗೆ ಆ ನಂಬಿಕೆ ಸಾಮಾನ್ಯವಾಗಿ ಸ್ವೀಕಾರಾರ್ಹ. ನಿಯಂತ್ರಿತ ಕಾರ್ಯಗಳಿಗೆ (ಹಣಕಾಸು, ಆರೋಗ್ಯ ಸೇವೆ, EU AI ಅಧಿನಿಯಮಕ್ಕೆ ಒಳಪಟ್ಟ ಯಾವುದೇ ಕಾರ್ಯ), ಅದು ಸಾಧ್ಯವಿಲ್ಲ.

ಕ್ರಿಪ್ಟೋಗ್ರಾಫಿಕ್ ರಿಸೀಟ್‌ಗಳು ಸಹಿ ಮಾಡಲಾದ ಹೇಳಿಕೆಯನ್ನು ಸ್ವತಂತ್ರವಾಗಿ
ಪರಿಶೀಲಿಸಬಹುದಾಗಿಸುವ ಮೂಲಕ ಈ ಸಮಸ್ಯೆಯನ್ನು ಸೀಮಿತಗೊಳಿಸುತ್ತವೆ. ಆದಾಗ್ಯೂ, ಆಡಿಟರ್‌ಗೆ ಸಹಿ ಕೀಯನ್ನು ಮತ್ತು
ಹೇಳಿಕೆಯನ್ನು ಉತ್ಪಾದಿಸಿದ ಘಟಕವನ್ನು ವಿಶ್ವಾಸಿಸಲು ಹೊರಗಿನ ಕಾರಣ ಇನ್ನೂ ಬೇಕಾಗುತ್ತದೆ. ಒಳಸೇರಿದ ಕೀ ಸ್ವಯಂ-ಸಂಗತತೆಯನ್ನು ದೃಢಪಡಿಸುತ್ತದೆ,
ಅದು ಪ್ರಕಟಕರ ಗುರುತು ಅಥವಾ ಜಾರಿಗೆ ಬರುವ ಸ್ಥಳವಲ್ಲ.

## ಕ್ರಿಪ್ಟೋಗ್ರಾಫಿಕ್ ರಸೀದಿ ಎಂದರೇನು?

ರಸೀದಿ ಅಂದರೆ ಏಜೆಂಟ್ ಏನ್ ಮಾಡಿದೆಯೋ ದಾಖಲಿಸುವ JSON ವಸ್ತು, ಡಿಜಿಟಲ್ ಸಹಿಯಿಂದ ಸಹಿ ಮಾಡಲಾಗುತ್ತದೆ.

```mermaid
flowchart LR
    A[Agent invokes a tool] --> B[Build receipt payload]
    B --> C[Canonicalize JSON RFC 8785]
    C --> E[Ed25519 sign canonical bytes]
    E --> F[Receipt with signature]
    F --> G[Auditor verifies offline]
    G --> H{Signature valid?}
    H -- yes --> I[Signed statement is intact]
    H -- no --> J[Receipt rejected]
```

ಸಾಂಪ್ರದಾಯಿಕ ರಸೀದಿ ಹೀಗೆ ಕಾಣಬಹುದು:

```json
{
  "type": "agent.tool_call.v1",
  "agent_id": "contoso-travel-bot",
  "tool_name": "lookup_flights",
  "tool_args_hash": "sha256:a3f9c1...",
  "result_hash": "sha256:7b2e1d...",
  "policy_id": "contoso-travel-policy-v3",
  "timestamp": "2026-04-25T14:30:00Z",
  "sequence": 47,
  "previous_receipt_hash": "sha256:9d4e6a...",
  "signature": {
    "alg": "EdDSA",
    "sig": "c5af83...",
    "public_key": "8f3b2c..."
  }
}
```

ಮೂರು ಗುಣಲಕ್ಷಣಗಳು ಕೆಲಸ ಮಾಡುತ್ತವೆ:

1. **ಸಹಿ**. ರಸೀದಿಗೆ ಏಜೆಂಟ್‌ನ ಗೇಟ್ವೇ Ed25519 ಖಾಸಗಿ ಕೀ ಬಳಸಿಕೊಂಡು ಸಹಿ ಹಾಕಲಾಗಿದೆ. ಹೊಂದಿದ್ದ ಸಾರ್ವಜನಿಕ ಕೀ ಇರುವ ಯಾರಾದರೂ ಆ ಸಹಿಯನ್ನು ಆಫ್‌ಲೈನ್‌ನಲ್ಲಿ ಪರಿಶೀಲಿಸಬಹುದು. ನಂಬಿಕೆಯಿರುವ ಪಕ್ಷವು ಆ ಕೀ ಅನ್ನು ಪಿನ್ ಮಾಡಬೇಕು ಅಥವಾ ರಸೀದಿಯ ಹೊರಗಿನ ವಿಶ್ವಾಸಾರ್ಹ ನೋಂದಣಿಯಿಂದ ಅದನ್ನು ಪರಿಹರಿಸಬೇಕು. ಯಾವುದೇ ಸಹಿ-ಹೊಂದಿದ ಕ್ಷೇತ್ರದಲ್ಲಿ ತವರಿಗೆದ್ ಮಾಡಿದರೆ ಸಹಿ ಅಮಾನ್ಯವಾಗುತ್ತದೆ.

2. **ಕ್ಯಾನೋನಿಕಲ್ ಎನ್ಕೋಡಿಂಗ್**. ಸಹಿ ಮಾಡುವ ಮೊದಲು, ರಸೀದಿಯನ್ನು JSON ಕ್ಯಾನೋನಿಕಲೈಜೆಷನ್ ಸ್ಕೀಮ್ (JCS, RFC 8785) ಉಪಯೋಗಿಸಿ ಸರಣಿ ಗೊಳಿಸಲಾಗುತ್ತದೆ. ಇದರಿಂದ ಎರಡು ಅನುಷ್ಠಾನಗಳು ಒಂದೇ ಲಾಜಿಕಲ್ ರಸೀದಿಯನ್ನು ಬೈಟ್-ಒಂದುಸರಿಯಾದ ಔಟ್‌ಪುಟ್ ಉತ್ಪಾದಿಸುತ್ತವೆ. ಕ್ಯಾನೋನಿಕಲೈಸೇಶನ್ ಇಲ್ಲದೆ, ವಿಭಿನ್ನ JSON ಸರಿಯಾದಿಕೆಗಳು ಒಂದೇ ವಿಷಯಕ್ಕೆ ವಿಭಿನ್ನ ಸಹಿಗಳನ್ನು ಒದಗಿಸುತ್ತವೆ.

3. **ಹ್ಯಾಶ್ ಚೈನಿಂಗ್**. `previous_receipt_hash` ಕ್ಷೇತ್ರವು ಪ್ರತಿಯೊಂದು ರಸೀದಿಯನ್ನು ಅದರ ಹಿಂದಿನದಕ್ಕೆ ಸಂಪರ್ಕಿಸುತ್ತದೆ. ರಸೀದಿಯನ್ನು ತೆಗೆದುಹಾಕುವುದು ಅಥವಾ ಅದನ್ನು ಮರುಕ್ರಮಗೊಳಿಸುವುದು ಪ್ರದರ್ಶಿಸಲಾದ ಕ್ರಮವನ್ನು ಭಂಗಮಾಡುತ್ತದೆ. ಕತ್ತರಿಸುವಿಕೆ ಅಥವಾ ಸಹಿ-ನಿಯಂತ್ರಿತ ಮರುಬರಹವನ್ನು ಪತ್ತೆಹಚ್ಚಲು ಸ್ಥಿರಪಡಿಸಿದ ಪ್ರಸ್ತುತ ಚೈನ್ ಹೆಡ್, ಸ್ವತಂತ್ರವಾಗಿ ಸಾಕ್ಷ್ಯಗೊಂಡ ಚೆಕ್ಪಾಯಿಂಟ್, ಅಥವಾ ಪ್ರಮಾಣೀಕೃತ ಮುಚ್ಚಿದ-ಜನಸಂಖ್ಯೆ ಬದ್ಧತೆ ಅಗತ್ಯವಿದೆ.

ಈ ಗುಣಲಕ್ಷಣಗಳು ಒಟ್ಟಿಗೆ ಮೂರು ಭರವಸೆಗಳನ್ನು ನೀಡುತ್ತವೆ:

- **Attribution to a key**: ಈ ಕೀ ಈ ವಿಷಯವನ್ನು ಸಹಿ ಮಾಡಿದೆ. ಸಂಸ್ಥೆಯ ಅಥವಾ ವ್ಯಕ್ತಿ ಗುರುತಿಗಾಗಿ ನಂಬಬಹುದಾದ ಕೀ ಬಂಧನ ಅಗತ್ಯ.
- **ಅಖಂಡತೆ**: ಸಹಿ ಮಾಡಿದರೆಂದಿನಿಂದ ವಿಷಯ ಬದಲಾಗಿಲ್ಲ.
- **ಪರಿಶೀಲಿಸಿದ ಸರಣಿಯ ಒಳಗಿನ ಕ್ರಮ**: ಈ ರಸೀದಿ ಆ ಪೂರ್ವಿಕೆಗೆ ಕೊಂಡಿ ಹೊಂದಿದೆ.

## ಪೈಥಾನ್‌ನಲ್ಲಿ ರಸೀದಿ ಉತ್ಪಾದಿಸುವುದು

ರಸೀದಿ ಉತ್ಪಾದಿಸಲು ವಿಶೇಷ ಗ್ರಂಥಾಲಯ ಅಗತ್ಯವಿಲ್ಲ. ಕ್ರಿಪ್ಟೋಗ್ರಾಫಿಕ್ ಮೂಲಭೂತಗಳು ವೇಗವಾಗಿ ಲಭ್ಯವಿದ್ದು ಲಾಜಿಕ್ ಕೆಲ ಡಜನ್ ಪೈಥಾನ್ ಸಾಲುಗಳಷ್ಟೇ.

`code_samples/18-signed-receipts.ipynb` ನಲ್ಲಿನ ಪ್ರಾಯೋಗಿಕ ಅಭ್ಯಾಸಗಳು ಸಂಪೂರ್ಣ ಹರಿವನ್ನು ಹಾದುಹೋಗುತ್ತವೆ. ಮೂಲ-ನಿಯಂತ್ರಿತ `code_samples/18-signed-receipts.execution-receipt.json` ಇತ್ತೀಚಿನ ಸ್ವಚ್ಛ ಕಾರ್ಯಾಚರಣೆಯಿಂದ ನಿಖರವಾದ ನೋಟ್‌ಬುಕ್ ಹ್ಯಾಶ್, Python ಪರಿಸರ, ಸೆಲ್ ಎಣಿಕೆ ಮತ್ತು ತಪಾಸಣೆಗಳನ್ನೂ ದಾಖಲಿಸುತ್ತದೆ ಮತ್ತು ಪಾಠದ ಉಳಿಸಿರುವ ಔಟ್‌ಪುಟ್‌ಗಳನ್ನು ಬದಲಾಯಿಸದೆ ಇಡುತ್ತದೆ. ಸಾರಾಂಶ ಆವೃತ್ತಿ:

```python
import json
import hashlib
import base64
from nacl import signing
from jcs import canonicalize  # RFC 8785 canonical JSON

def b64url_nopad(data: bytes) -> str:
    return base64.urlsafe_b64encode(data).decode("ascii").rstrip("=")

def sha256_canonical(obj) -> str:
    """SHA-256 of a Python object's JCS-canonical JSON form."""
    return f"sha256:{hashlib.sha256(canonicalize(obj)).hexdigest()}"

# Generate or load a signing key (in production, store in a key vault)
signing_key = signing.SigningKey.generate()
verify_key = signing_key.verify_key
TRUSTED_PUBLIC_KEYS = {b64url_nopad(bytes(verify_key))}  # pinned out of band by the verifier

# Build the receipt payload (no signature yet)
tool_args = {"origin": "SYD", "destination": "LAX"}
tool_result = [{"flight": "QF11", "price": 1850, "stops": 0}]

payload = {
    "type": "agent.tool_call.v1",
    "agent_id": "contoso-travel-bot",
    "tool_name": "lookup_flights",
    "tool_args_hash": sha256_canonical(tool_args),
    "result_hash": sha256_canonical(tool_result),
    "policy_id": "contoso-travel-policy-v3",
    "timestamp": "2026-04-25T14:30:00Z",
    "sequence": 0,
    "previous_receipt_hash": None,
}

# Canonicalize and sign the JCS bytes directly. PureEdDSA hashes internally.
canonical_bytes = canonicalize(payload)
signature_bytes = signing_key.sign(canonical_bytes).signature

# Attach a structured signature object.
receipt = {
    **payload,
    "signature": {
        "alg": "EdDSA",
        "sig": b64url_nopad(signature_bytes),
        "public_key": b64url_nopad(bytes(verify_key)),
    },
}
```

ಇದು ಸಂಪೂರ್ಣ ಸಹಿ ಮಾಡುವ ಪೈಪ್ಲೈನ್. ನೋಟ್ಬುಕ್‌ನ ವ್ಯಾಯಾಮಗಳು ಪ್ರತಿ ಹೆಜ್ಜೆಯನ್ನು ವಿವರಿಸುತ್ತವೆ.

## ರಸೀದಿಯನ್ನು ಪರಿಶೀಲಿಸುವುದು ಮತ್ತು ತತ್ತರಿಸುವಿಕೆಯನ್ನು ಪತ್ತೆಹಚ್ಚುವುದು

ಪರಿಶೀಲನೆಹುನ್ನೆರುವಿಕೆ ಕ್ರಿಯೆಯ ವಿರುದ್ಧ.

```python
import base64
import hashlib
from nacl import signing
from nacl.exceptions import CryptoError
from jcs import canonicalize

def b64url_decode(s: str) -> bytes:
    padding = "=" * ((4 - len(s) % 4) % 4)
    return base64.b64decode(s + padding, altchars=b"-_", validate=True)

def verify_receipt(receipt: dict, trusted_public_keys: set[str]) -> bool:
    # The signature is a structured object: {"alg", "sig", "public_key"}.
    if not isinstance(receipt, dict):
        return False
    sig_obj = receipt.get("signature")
    if not isinstance(sig_obj, dict) or sig_obj.get("alg") != "EdDSA":
        return False
    try:
        # An inline key proves only self-consistency. Trust is configured out of band.
        public_key = sig_obj.get("public_key")
        signature = sig_obj.get("sig")
        if not isinstance(public_key, str) or not isinstance(signature, str):
            return False
        if public_key not in trusted_public_keys:
            return False
        payload = {k: v for k, v in receipt.items() if k != "signature"}
        canonical_bytes = canonicalize(payload)
        verify_key = signing.VerifyKey(b64url_decode(public_key))
        verify_key.verify(canonical_bytes, b64url_decode(signature))
        return True
    except (CryptoError, TypeError, ValueError, KeyError, OverflowError):
        return False
```

ಈ ಕಾರ್ಯವು ಒಂದು ರಸೀದಿಯನ್ನು ಮತ್ತು ಅವಲಂಬಿಸುವ ಪಕ್ಷದ ಪಿನ್ ಮಾಡಲಾದ ಕೀ ಸೆಟ್ ಅನ್ನು ತೆಗೆದು ಮತ್ತು ಹಿಂತಿರುಗಿಸುತ್ತದೆ
`True` ಮಾತ್ರ ಸಹಿ ಸ್ವೀಕೃತ ಕೀ ಅಡಿಯಲ್ಲಿ ಮಾನ್ಯವಾಗಿದ್ದರೆ. ಪರಿಶೀಲನೆಗೆ ಯಾವುದೇ
നെಟ್ವರ್ಕ್ ಕರೆ ಅಗತ್ಯವಿಲ್ಲ, ಆದರೆ ಕೀ ಮೇಲಿನ ನಂಬಿಕೆ ಇನ್ನೂ ಬಾಹ್ಯ ಸಂರಚನಾ ನಿರ್ಧಾರವಾಗಿದೆ.

ತತ್ತರಿಸುವಿಕೆ ಪತ್ತೆಚೆಗೆ ನೋಟ್ಬುಕ್‌ನಲ್ಲಿ ಇವುಗಳು ನಡೆಯುತ್ತವೆ:

1. ಮಾನ್ಯವಾದ ರಸೀದಿಯನ್ನು ಉತ್ಪಾದಿಸಿ ಅದು ಪರಿಶೀಲನೆ ಸಮ್ಮತಿಸುತ್ತದೆ ಎಂದು ದೃಢಪಡಿಸುವುದು.
2. `tool_args_hash` ಕ್ಷೇತ್ರದ ಒಂದೊಂದು ಬೈಟ್ ಅನ್ನು ಬದಲಾಯಿಸುವುದು.
3. ಪರಿಶೀಲನೆಯನ್ನು ಪುನಃ ನಡೆಸಿ ಅದು ವಿಫಲವಾಗುವುದನ್ನು ನೋಡುವುದು.

ಇದು ರಸೀದಿಗಳು ತತ್ತರಿಸುವಿಕೆ-ಸೂಚಿತವಾಗಿದ್ದಾರೆಯೆಂದು ವೈಯಕ್ತಿಕವಾಗಿ ಪ್ರದರ್ಶಿಸುವುದು: ಯಾವುದೇ ಬದಲಾವಣೆ ಸಹಿ ಮುರಿಯುತ್ತದೆ.

## ಬಹು-ಹೆಜ್ಜೆಗಳ ಏಜೆಂಟ್ಗಾಗಿ ರಸೀದಿಗಳ ಸರಪಳಿ

ಒಂದು ಸಹಿ ಮಾಡಿದ ರಸೀದಿ ಒಂದು ಕ್ರಿಯೆಯನ್ನು ರಕ್ಷಿಸುತ್ತದೆ. ರಸೀದಿಗಳ ಸರಪಳಿ ಕ್ರಮವನ್ನು ರಕ್ಷಿಸುತ್ತದೆ.

```mermaid
flowchart LR
    R0[Receipt 0<br/>genesis] --> R1[Receipt 1]
    R1 --> R2[Receipt 2]
    R2 --> R3[Receipt 3]
    R1 -. previous_receipt_hash .-> R0
    R2 -. previous_receipt_hash .-> R1
    R3 -. previous_receipt_hash .-> R2
```

ಪ್ರತಿ ರಸೀದಿ ಹಿಂದಿನ ರಸೀದಿಯ ಹ್ಯಾಶ್ ಅನ್ನು ದಾಖಲಿಸುತ್ತದೆ. ರಸೀದಿ 2 ಅನ್ನು ಮೌನವಾಗಿ ತೆಗೆದು ಹಾಕಲು, ದಾಳಿ ಮಾಡುತ್ತಿರುವವರು:

- ರಸೀದಿ 3‌ನ `previous_receipt_hash` ಕ್ಷೇತ್ರವನ್ನು ಬದಲಾಯಿಸುವುದು (ರಸೀದಿ 3‌ನ ಸಹಿಯನ್ನು ಮುರಿಯುತ್ತದೆ), ಅಥವಾ
- ಬದಲಾಯಿಸಿದ ರಸೀದಿ 3 ಮೇಲೆ ಹೊಸ ಸಹಿಯನ್ನು ನಕಲಿ ಮಾಡುವುದು (ಏಜೆಂಟ್ ಖಾಸಗಿ ಕೀ ಅಗತ್ಯ).

ಗೌಪ್ಯ ಕೀ ರಕ್ಷಿತವಾಗಿದ್ದರೆ ಮತ್ತು ಪರಿಶೀಲಕನು ಸ್ವತಂತ್ರವಾಗಿ ಸಾಕ್ಷ್ಯ ಹೊಂದಿರುವ ಸರಣಿಯ
ತುದಿಯನ್ನು ಲಗತ್ತಿಸಿದರೆ, ಈ ದಾಳಿಗಳನ್ನು ಪತ್ತೆಹಚ್ಚಬಹುದು. ಪ್ರತಿ ರಸೀದಿಯ ಒಳಗೆ ಕಿಯನ್ನು ಪ್ರಕಟಿಸುವುದು
ಸಾಕಾಗುವುದಿಲ್ಲ: ಸಹಿ ಮಾಡುವವನು ಅಥವಾ ದಾಳಿ ನಡೆಸುವವನು ಬೇರೆ ಕೀಯನ್ನು ನೀಡಬಹುದು, ಉಪಸರಣಿಯನ್ನು ಮರುಬರೆದಬಹುದು, ಅಥವಾ
ಸರಣಿಯನ್ನು ಕಡಿತಗೊಳಿಸಬಹುದು, ಅವಲಂಬಿಸುವ ಪಕ್ಷಕ್ಕೆ ಬಾಹ್ಯ ನಂಬಿಕೆ ಮತ್ತು ಪೂರ್ಣತೆಯ ಆಂಕರ್ ಇಲ್ಲದಿದ್ದರೆ.

ನೋಟ್ಬುಕ್ ಮುಂದುವರಿದಿದೆ:

1. ಮೂರು ರಸೀದಿಗಳ ಸರಪಳಿ ನಿರ್ಮಿಸುವುದು.
2. ಪ್ರತಿ ರಸೀದಿಯ `previous_receipt_hash` ಹಿಂದಿನ ರಸೀದಿಯ ನಿಜವಾದ ಹ್ಯಾಶ್‌ಗೂ ಹೊಂದಿಕೆಯನ್ನು ಪರಿಶೀಲಿಸುವುದು.
3. ಮಧ್ಯದಲ್ಲಿ ಒಂದೊಂದು ರಸೀದಿಯನ್ನು ತತ್ತರಿಸುವುದು ಮತ್ತು ಸರಣಿ ಮುರಿಯುತ್ತಿರುವುದು ನೋಡುವುದು.

ಇದು ನೀವು ಆಡಿಟ್ ಟ್ರೇಲ್ ಅನ್ನು ಹೇಗೆ ರಚಿಸುವಿರಿ ಎಂಬುದು, ಹೊರಗಿನ ಪರಿಶೋಧಕವು ತನ್ನ ಅಡಿಯಲ್ಲಿ
ಸ್ವಂತ ನಿಗದಿಪಡಿಸಿದ ಜಾರಿ ಮಾಡುವವರ ಕೀಲಿಗಳು ಮತ್ತು ಸರಪಳಿ ಚೆಕ್ಪಾಯಿಂಟ್‌ಗಳು, ನಿಮ್ಮ ಬದಲಾಯಿಸಬಹುದಾದ ಲಾಗ್ ಸಂಗ್ರಹವನ್ನು ನಂಬದೆ.

## ರಸೀದಿಗಳು 무엇ನ್ನು ಸಾಬೀತುಮಾಡುತ್ತವೆ (ಮತ್ತು 무엇ನ್ನು ಮಾಡುವುದಿಲ್ಲ)

ಈ ಪಾಠದ ಅತ್ಯಂತ ಮುಖ್ಯ ವಿಭಾಗ. ರಸೀದಿಗಳು ಶಕ್ತಿಶಾಲಿ ಆದರೆ ಆ ಶಕ್ತಿ ಮಿತವಾಗಿದೆ.

**ರಸೀದಿಗಳು ಮೂರು ವಿಷಯಗಳನ್ನು ಸಾಬೀತು ಮಾಡುತ್ತವೆ:**

1. **ಹೆಸರು ಸೂಚನೆ**: ನಿರ್ದಿಷ್ಟ ಕೀ ನಿರ್ದಿಷ್ಟ ಪೇಲೋಡ್ ಅನ್ನು ಸಹಿ ಮಾಡಿತ್ತು.
2. **ಅಖಂಡತೆ**: ಪೇಲೋಡ್ ಸಹಿ ಮಾಡಿದಾಗಿನಿಂದ ಬದಲಾಯಿಲ್ಲ.
3. **ಪ್ರಸ್ತುತಪಡಿಸಿದ, ಪರಿಶೀಲಿಸಿದ ಕ್ರಮದಲ್ಲಿ ಕ್ರಮಬದ್ಧತೆ**: ಈ ರಸೀದಿ ಆ ಹಿಂದಿನದಕ್ಕೆ ಲಿಂಕ್ ಮಾಡುತ್ತದೆ.

**ರಸೀದಿಗಳು ಸಾಬೀತು ಮಾಡದೆ ಇರುತ್ತವೆ:**

1. **ಸರಿಯಾದತೆ**: ಏಜೆಂಟ್ ಕ್ರಿಯೆ ಸರಿಯಾದ ಕ್ರಮವೋ ಎಂಬುದು. ತಪ್ಪಾದ ಉತ್ತರಕ್ಕೂ ಸಹಿ ಮಾಡಬಹುದು ಅದೇ ರೀತಿಯಲ್ಲಿ.
2. **ನೀತಿ ಅನುಕೂಲತೆ**: `policy_id` ನಲ್ಲಿ ಸೂಚಿಸಲ್ಪಟ್ಟ ನಿಯತಿಯನ್ನು ಸತ್ಯವಾಗಿಯೇ ಮೌಲ್ಯಾಂಕನ ಮಾಡಲಾಯಿತು ಅಥವಾ ಯಾವುದಾದರೂ ಕ್ರಿಯೆಯನ್ನು ಅನುಮತಿಸಿತೇ ಎಂಬುದನ್ನು. ರಸೀದಿ ಹೇಳುವುದು ಪ್ರವೇಶ ವಾದವು, ಅಳವಡಿಸಿಕೊಂಡಿಲ್ಲ.
3. **ಕೀಯಿಗಿಂತ ಹೊರಗಿನ ಐಡಂಟಿಟಿ**: ರಸೀದಿ "ಈ ಕೀ ಈ ವಿಷಯವನ್ನು ಸಹಿ ಮಾಡಿದೆ" ಎಂದು ಹೇಳುತ್ತದೆ. "ಈ ವ್ಯಕ್ತಿಯು ಅನುಮೋದಿಸಿದ" ಎಂದು ಹೇಳುವುದಿಲ್ಲ. ವ್ಯಕ್ತಿ ಅಥವಾ ಸಂಸ್ಥೆಗಾಗಿ ಕೀ ಸಂಪರ್ಕಿಸಬೇಕಾದರೆ ಪ್ರತ್ಯೇಕ ಐಡಂಟಿಟಿ ಮೂಲಸೌಕರ್ಯ ಬೇಕು (ಡೈರೆಕ್ಟರಿ, ಸಾರ್ವಜನಿಕ ಕೀ ನೊಂದಣಿ, ಇತ್ಯಾದಿ).
4. **ಇನ್ಪುಟ್‌ಗಳ ಸತ್ಯತ್ವ**: ಏಜೆಂಟ್ ತಂತ್ರಸೂಚನೆಯನ್ನು ತಿರುವುಮಾಡಿದಂತೆ ಮತಿಗಳನ್ನು ಸ್ವೀಕರಿಸಿ ಅದನ್ನು ಅನುಷ್ಠಾನ ಮಾಡಿದರೆ, ರಸೀದಿ ಆ ಕ್ರಿಯೆಯನ್ನು ನಂಬಬಹುದಾಗಿದೆ. ರಸೀದಿಗಳು ಇನ್ಪುಟ್ ಪ್ರಮಾಣೀಕರಣದ ಹಿಂದೆ ಇರುತ್ತವೆ, ಅದರ ಬದಲಿಗೆ ಅಲ್ಲ.
5. **ಕಾರ್ಯನಿರ್ವಹಣೆ ಅಥವಾ ವಾಸ್ತವಿಕ ಪರಿಣಾಮ**: ಕರೆ ನಂತರದ ರಸೀದಿ ಅದನ್ನು ಜಾರಿ ಮಾಡಿದವರು ಏನಾಯಿತು ಎಂದು ಹೇಳಿರುವುದನ್ನು ದಾಖಲಿಸುತ್ತದೆ. ಸ್ವೀಕಾರವನ್ನು ಸಾಬೀತುಮಾಡುವುದು ಅಥವಾ ಹೊರಗಿನ ಪರಿಣಾಮವನ್ನು ಸಮನ್ವಯಗೊಳಿಸುವುದು ನಿಜವಾದ ಕಾರ್ಯನಿರ್ವಹಣೆ ಅಥವಾ ಪೂರೈಕೆದಾರರ ಗಡಿಯಿಂದ ಬಂದ ಸಾಕ್ಷ್ಯವನ್ನು талапಿಸುತ್ತದೆ.
6. **ಪೂರ್ಣತೆ**: ರಸೀದಿ ಕಾಣದೆ ಇರುವುದು ಅಡ್ಡಿಯಾಗಿರುವುದು, ಬಿಟ್ಟುಬಿಡಲಾಗಿದೆ, ಕಳೆದುಹೋಗಿದೆ, ಅಥವಾ ಸಾಧನಗೊಳಿಸದಿರುವುದಾಗಿರಬಹುದು. ರಸೀದಿ ಇಲ್ಲದಿರುವುದು ಸಾಕ್ಷ್ಯವಾಗುವುದು ಕೇವಲ ಪ್ರಮಾಣೀಕೃತ ಮುಚ್ಚಿದ ಜನಸಂಖ್ಯೆಯೊಳಗೇ ಸಂಭವಿಸುತ್ತದೆ.
7. **ನಂಬಿಗಸ್ತ ಸಮಯ**: ಸಹಿ ಹಾಕಾದ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಸಹಿಯನ್ನು ಹಾಕಿದವನು ಆ ಮೌಲ್ಯವನ್ನು ಹೊಂದಿದ್ದನೆಂಬುದನ್ನು ಸಾಬೀತುಪಡಿಸುತ್ತದೆ, ಆ ಮೌಲ್ಯವು ಸರಿಯಾಗಿತ್ತು ಎಂಬುದನ್ನು ಅಲ್ಲ. ನಂಬಿಗಸ್ತ ಸಮಯಕ್ಕೆ ಪ್ರತ್ಯೇಕ ಕಾಲ ಪ್ರಾಧಿಕಾರ ಅಥವಾ ಸಾಕ್ಷಿಯಾದ ಚೆಕ್‌ಪಾಯಿಂಟ್ ಅಗತ್ಯವಿದೆ.

ಈ ಅಗ್ಗುಲು ಎರಡು ಕಾರಣಗಳಿಂದ ಮುಖ್ಯ:

- ಪ್ರಸಕ್ತಗೊಳಿಸುವುದು ರಸೀದಿಗಳು ಏಜೆಂಟ್ ಆಚಾರವನ್ನು ಪರಿಶೀಲನೀಯವಾಗಿಸಿ ತತ್ತರಿಸಲು ಸಹಕಾರಿ ಎಂಬುದು, ಸಂಸ್ಥೆಗಳ ಗಡಿಗಳನ್ನು ದಾಟಿದರೂ ಸಹ.
- ನೀವು ಇನ್ನೂ ಬೇಕಾಗುವ ಹೆಚ್ಚುವರಿ ಪದರಗಳನ್ನು ತಿಳಿಸುತ್ತದೆ: ಇನ್ಪುಟ್ ದೃಢೀಕರಣ (ಪಾಠ 6), ನೀತಿ ಜಾರಿಗೆ (ಕೆಳಗೆ ಸಣ್ಣ ವಿವರಣೆ), ಮತ್ತು ಐಡಂಟಿಟಿ ಮೂಲಸೌಕರ್ಯ (ಈ ಪಾಠಕ್ಕೆ ಹೊರಗಿದ್ದು).

ಸಾಮಾನ್ಯ ತಪ್ಪು "ನಾವು ರಸೀದಿಗಳನ್ನು ಹೊಂದಿದ್ದೇವೆ" ಎಂದರೆ "ನಾವು ಆಡಳಿತাধীন" ಎಂದು ಭಾವಿಸುವುದು. ಅಲ್ಲ. ರಸೀದಿಗಳು അടിസ്ഥാനಚೌಕಟ್ಟು. ಆಡಳಿತ ವ್ಯವಸ್ಥೆಯು ನೀವು ನಿರ್ಮಿಸುವ ವ್ಯವಸ್ಥೆಯಾಗಿದೆ.

## ಅನುಮೋದಕರ ಸಹಿಯನ್ನು ನಿಖರವಾದ ಕಾರ್ಯಕ್ಕೆ ಬಾಂಧಿಸುವುದು

ಮೇಲಿನ ಐಟಂ 3 ತನ್ನದೇ ವಿಭಾಗಕ್ಕೆ ಯೋಗ್ಯವಾಗಿದೆ: ಕ್ರಿಯೆಯ ರಶೀದಿ "ಈ ಕೀ ಈ ವಿಷಯವನ್ನು ಸಹಿ ಮಾಡಿದೆ," ಎಂದಿಗೂ "ಮಾನವನು ಇದಕ್ಕೆ ಅನುಮೋದನೆ ನೀಡಿದನು." ಎಂದು ಹೇಳುವುದಿಲ್ಲ. ಉನ್ನತ-ಅಪಾಯ ಕ್ರಿಯೆಗಳಿಗೆ (ಹಣ ಮರಳಿಸುವಿಕೆಗಳು, ಅಳಿಕೆಗಳು, ವೈರ್ ವರ್ಗಾವಣೆಗಳು), ಪ್ರತ್ಯೇಕ ಅನುಮೋದಕನ ಸಹಿ ನಿಖರ ಕ್ರಿಯೆಯನ್ನು ಬದ್ಧಗೊಳಿಸಬಹುದು. ಆ ಕೀಲಿಯನ್ನು ಮಾನವನೊಂದಿಗೆ ಕೊಂಡಿಡುವುದು ಮತ್ತು ಮಾನವ ಹಾಜರಾತಿಯನ್ನು ಪರಿಶೀಲಿಸುವುದು ಪ್ರತ್ಯೇಕ ಜವಾಬ್ದಾರಿಗಳಾಗಿಯೇ ಉಳಿಯುತ್ತವೆ.

ಮುಂದುವರಿದ ನೋಟ್‌ಬುಕ್ `code_samples/human-authorization-receipts.ipynb` ಪಾಠದ ರಸೀದಿಗಳೇ ಆಗಿರುವ ಅದೇ ಎನ್ವಲಪ್ ಆಕಾರದಲ್ಲಿ ಎರಡನೇ ರಸೀದಿ ವಿಧವಾದ `human.approval.v1` ಅನ್ನು ಸೇರಿಸುತ್ತದೆ (ಕ್ಯಾನೋನಿಕಲ್ JCS ಬೈಟ್‌ಗಳ ಮೇಲಿನ Ed25519 ಸಹಿ ಮಾಡಲಾದ ಟೈಪ್ಡ್ ಪೇಲೋಡ್, ಜೊತೆಗೆ `signature` ವಸ್ತುವು ಸಹಿ ಮಾಡಿದ ಬೈಟ್‌ಗಳ ಹೊರಗೆ ಇರುತ್ತದೆ). ಒಂದು ಅನುಮೋದಕ ಕೀವು **ಪೂರ್ಣ ಕ್ಯಾನನಿಕಲ್ ಕ್ರಿಯೆಯನ್ನು ಮತ್ತು ಅದರ ಡೈಜೆಸ್ಟ್** ಅನ್ನು ಸಹಿ ಮಾಡುತ್ತದೆ; ಒಂದು ಏಜೆಂಟ್ ಕೀವು **ಅದೇ ಕ್ರಿಯೆಯ ಡೈಜೆಸ್ಟ್** ಮತ್ತು `parent_approval_ref` ಅನ್ನು ಹೊತ್ತಿರುವ ಒಂದು ಕ್ಲೈಮ್ ಅನ್ನು ಸಹಿ ಮಾಡುತ್ತದೆ, ಅನುಮೋದನೆಯ `receipt_hash`, ಮೇಲೇ ನೀವು ನಿರ್ಮಿಸಿದ ಸರಣಿಯಲ್ಲಿನ `previous_receipt_hash` ಜತೆ ಇರುವ ಅದೇ ಸಂಪ್ರದಾಯ. ಒಂದು `verify_chain` ಎರಡು ಆರ್ಕಿಫ್ಯಾಕ್ಟ್‌ಗಳನ್ನು **ಪ್ರತ್ಯೇಕವಾಗಿ ಪಿನ್ ಮಾಡಲಾದ ಕೀ ರೆಜಿಸ್ಟ್ರಿಗಳಲ್ಲಿ** (ಅನುಮೋದಕರ ಕಿಗಳು ವಿರುದ್ಧ ಏಜೆಂಟ್ ಕಿಗಳು) ಪ್ರಕ್ರಿಯೆಗೊಳಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಕೋಡ್ ಪಥ ಹಂಚಿಕೊಳ್ಳಲಾಗುತ್ತದೆ ಆದರೆ ಅಧಿಕಾರಿಗಳು ಎಂದಿಗೂ ಹಂಚಿಕೊಳ್ಳುವುದಿಲ್ಲ.

ಈ ಮೂಲಕ ಸಿಗುವ ಗುಣಲಕ್ಷಣವನ್ನು ಜಾಗರೂಕವಾಗಿ ಹೇಳುವುದಾದರೆ: *ಪಟ್ಟಿಗೊಂಡ ಅನುಮೋದಕರ ಕೀ ಈ ನಿಖರವಾದ
ಕ್ರಿಯೆಗೆ ಸಹಿ ಮಾಡಿದೆ, ಮತ್ತು ಏಜೆಂಟ್ ಕೀ ನಂತರ ಅದೇ ಕ್ರಿಯಾ ಡೈಜೆಸ್ಟ್ ಹೊಂದಿರುವ ಒಂದು ಹೇಳಿಕೆಗೆ ಸಹಿ ಮಾಡಿತು.*
ಅದು ಉಪಯುಕ್ತ ಸಾಕ್ಷ್ಯವಾಗಿದೆ, ಆದರೆ ಅದು ತಾನೇ ಆ ಕ್ರಿಯೆ ಕಾರ್ಯಗತವಾಗಿದೆ ಎಂಬುದಕ್ಕೆ ಸಾಕ್ಷಿ ಅಲ್ಲ. ನಿಯಂತ್ರಣಕ್ಕಾಗಿ
ಕಾರ್ಯನಿರ್ವಹಣೆಯನ್ನು ನಿಯಂತ್ರಿಸಲು, ನಿಖರ ಅನುಮೋದನೆಯನ್ನು ಕೂಡ ವಾಸ್ತವ ನಿರ್ವಾಹಕ ಗಡಿಯಲ್ಲಿಯಲ್ಲಿ ಒಂದು ಬಾರಿ ಕಾಯ್ದಿರಿಸಿ ಮತ್ತು ಬಳಸಿಕೊಂಡು ಮುಗಿಸಬೇಕು
ವಾಸ್ತವ ನಿರ್ವಾಹಕ ಗಡಿಯಲ್ಲಿದ್ದು; ಅಜ್ಞಾತ ಪ್ರದಾತಾ ಫಲಿತಾಂಶಗಳು ತಿಳಿಯದೆಯೇ ಉಳಿಯಬೇಕು, ಬದಲಿಗೆ
ಅಂಧವಾಗಿಯೇ ಮರುಪ್ರಯತ್ನಿಸಬಾರದು. ನೋಟ್ಬುಕ್‌ನ ನಿರಾಕರಣೆ ಫಿಕ್ಸ್ಚರ್‌ಗಳು ರಸೀದಿ-ಶೃಂಖಲೆ ಪದರವನ್ನು ಪರೀಕ್ಷಿಸುತ್ತವೆ:

- ಹಸ್ತಕ್ಷೇಪ, ಗೊಂದಲಗೊಂಡ ಪ್ರಾಧಿಕಾರಿ, ಎರಡೂ ಕಡೆಗಳಲ್ಲಿನ ನಕಲಿ ಕೀಲಿಗಳು, ಮತ್ತು ಅಸಂರಚಿತ ಇನ್‌ಪುಟ್;
- **ಹಳೆಯ ಪ್ರಾಧಿಕಾರ**: ಇನ್ನೂ ಪರಿಶೀಲಿಸಬಹುದಾದ ಸಹಿ, ಆದರೂ ನಿರಾಕರಿಸಲಾಯಿತು ಏಕೆಂದರೆ ನೀತಿ ಆವೃತ್ತಿ ಬದಲಾಗಿತ್ತು, ಅನುಮೋದಕ ಕೀ ಪಿನ್ ಮಾಡಲಾದ ರೆಜಿಸ್ಟ್ರಿಯಿಂದ ತಿರುಗಿಸಲಾಯಿತು, ಅಥವಾ ನೀಡಲಾದ ಪರಿಶೀಲನಾ ಸಮಯಕ್ಕಿಂತ ಮುಂಚೆಗೆ ಅನುಮೋದನೆಯ ಅವಧಿ ಮುಗಿದಿತ್ತು;
- **ದಿಜೆಸ್ಟ್ ಬದಲಾವಣೆ**: ನಿಜವಾದ ಅನುಮೋದನೆಯನ್ನು ಸೂಚಿಸುವ ಮಾನ್ಯ ಸಹಿ ಹೊಂದಿದ ಕ್ರಿಯೆ ರಸೀದಿ, ಆದರೆ ವಿಭಿನ್ನ ಕ್ಯಾನೋನಿಕಲ್ ಕ್ರಿಯೆಗೆ ಬಿಡುತ್ತದೆಯೆಂದು ಸೂಚಿಸುವುದು.

ಪ್ರತಿ ವಿಫಲತೆ ವಿಭಿನ್ನ ಕಾರಣದೊಂದಿಗೆ ನಿರಾಕರಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ನಿರಾಕರಣೆಯನ್ನು ಓದುವ ಆಡಿಟರ್ ಅಧಿಕೃತತೆ ಅವಧಿ ಮುಗಿದಿದೆಯೇ ಅಥವಾ ಹೇಳಿಕೆಯಾದ ಕ್ರಿಯೆಯಲ್ಲಿ ಬದಲಾವುಂಟಾದದೆಯೇ ಎಂದು ಗುರುತಿಸಬಹುದು. ಪರಿಶೀಲನೆ ಓದಿಗೆ ಮಾತ್ರ ಮತ್ತು ಪುನರವર્તನೀಯವಾಗಿದೆ: ಇದು ಅನುಮೋದನೆಯನ್ನು ಬಳಸದೆಯೇ ಮತ್ತು ಪೂರೈಕೆದಾರರನ್ನು ಕರೆ ಮಾಡುವುದಿಲ್ಲ. ವಿಭಿನ್ನ ನಿರ್ವಹಕನಿಗೆ ದೀರ್ಘಕಾಲಿಕ, ಆಟಾಮಿಕ್ ಪುನರಾವರ್ತನೆ ರಕ್ಷಣೆ ಮತ್ತು ಸ್ಪಷ್ಟ ಯಶಸ್ಸು, ವಿಫಲತೆ ಮತ್ತು ನಿರ್ಧಾರಹೀನ ಫಲಿತಾಂಶಗಳ ಅಗತ್ಯವಿದೆ. ಮಾನವ-ಅನುಮೋದನೆ ರಸೀದಿ ಈ ಪಾಠದಲ್ಲಿ ವ್ಯಾಖ್ಯಾನಿಸಲಾದ ಶೈಕ್ಷಣಿಕ ಸಂಯೋಜನೆ ಆಗಿದ್ದು, `draft-farley-acta-signed-receipts` ನಲ್ಲಿ ವ್ಯಾಖ್ಯಾನಿಸಲಾದ ರಸೀದಿ ಪ್ರಕಾರವಲ್ಲ.

## ಉತ್ಪಾದನೆ ಉಲ್ಲೇಖಗಳು

ಈ ಪಾಠದ ಪೈಥನ್ ಕೋಡ್ ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಕನಿಷ್ಠವಾಗಿದೆ, ಆದ್ದರಿಂದ ಪ್ರತಿಯೊಂದು ಸಾಲನ್ನು ಓದಿ ಏನಾಗುತ್ತಿದ್ದುದು ತಿಳಿಯಬಹುದು. ಉತ್ಪಾದನೆಯಲ್ಲಿ, ನಿಮಗೆ ಎರಡು ಆಯ್ಕೆಗಳು ಇವೆ:

1. **ನೇರವಾಗಿ ಕ್ರಿಪ್ಟೋಗ್ರಾಫಿಕ್ ಮೂಲಭೂತಗಳ ಮೇಲೆ ನಿರ್ಮಿಸಿ.** ಮೇಲಿನ 50 ಸಾಲುಗಳು ಹಲವಾರು ಬಳಕೆಗಳಿಗೆ ಸಾಕಷ್ಟಿವೆ. PyNaCl (Ed25519) ಮತ್ತು `jcs` ಪ್ಯಾಕೇಜ್ (ಕ್ಯಾನೋನಿಕಲ್ JSON) ಉತ್ತಮ ನಿರ್ವಹಣೆ ಮತ್ತು ಪರಿಶೀಲನೆಯ ಗ್ರಂಥಾಲಯಗಳು.

2. **ಉತ್ಪನ್ನ ರಸೀದಿ ಗ್ರಂಥಾಲಯ ಬಳಸಿ.** ಹಲವು ಮುಕ್ತ-ಮೂಲ ಯೋಜನೆಗಳು ಸಹಿ ಮಾಡುವುದು, ಬ್ಯಾಚ್ ಪರಿಶೀಲನೆ, JWK ಸೆಟ್ ವಿತರಣೆ, ನೀತಿ ಎಂಜಿನ್‍ಗಳ ನೆರವು ಸೇರಿದಂತೆ ಅದೇ ಮಾದರಿಯನ್ನು ಜಾರಿಗೆ ತಂದಿವೆ:
   - ಸಹಿ ಪೈಪ್ಲೈನ್ JCS ಮತ್ತು ಸಹಿ-ವಿಸ್ತಾರ ನಿಯಮಗಳನ್ನು ಸ್ವತಂತ್ರ IETF ಇಂಟರ್ನೆಟ್-ಡ್ರಾಫ್ಟ್ ([`draft-farley-acta-signed-receipts`](https://datatracker.ietf.org/doc/draft-farley-acta-signed-receipts/), ಮರುಪಾರದರ್ಶಕತೆ 02) ಬಳಕೆ ಮಾಡುತ್ತದೆ. ಈ ಪಾಠದ ಸರಳ ಶೈಕ್ಷಣಿಕ ರಸೀದಿ ಡ್ರಾಫ್ಟ್‌ನ `{payload, signature}` ಎನ್ವಲಪ್‌ನಿಂದ ಭಿನ್ನವಾಗಿದೆ ಮತ್ತು ಅನುಷ್ಠಾನವಲ್ಲ. ಡ್ರಾಫ್ಟ್ ತನ್ನ ವೈರ್ ಫಾರ್ಮಾಟ್ ಗುರಿಯಲ್ಲಿ ಅನುಷ್ಠಾನಗಳಿಗೆ ಸಹಕಾರದ ಕಿಕ್ಕುಗಳನ್ನು ಪ್ರಕಟಿಸಿದೆ ([agent-governance-testvectors](https://github.com/ScopeBlind/agent-governance-testvectors)).
   - ಮೈಕ್ರೋಸಾಫ್ಟ್ ಏಜೆಂಟ್ ಆಡಳಿತ ಪರಿಕರ ಕಿಟ್ ರಸೀದಿಗಳನ್ನು ಸೀಡರ್ ಆಧಾರಿತ ನೀತಿ ನಿರ್ಧಾರಗಳಿಂದ ರಚಿಸುತ್ತದೆ; ಅದರಲ್ಲಿ ಟ್ಯುಟೋರಿಯಲ್ 33 ಪೂರ್ಣ ಉದಾಹರಣೆಗಾಗಿ ನೋಡಿ.
   - `protect-mcp` (npm) ಮತ್ತು `@veritasacta/verify` (npm) ಪ್ಯಾಕೇಜುಗಳು ನೋಡ್ ಆಧಾರಿತ ರಸೀದಿ ಸಹಿ ಮತ್ತು ಆಫ್‌ಲೈನ್ ಪರಿಶೀಲನೆ ಕಾರ್ಯಾನುಷ್ಠಾನವನ್ನು ಒದಗಿಸುತ್ತವೆ, ಎಲ್ಲ MCP ಸರ್ವರ್‌ಗಳನ್ನು ತತ್ತರಸೂಚಕ ಆಡಿಯಟ್ ಟ್ರೇಲ್‌ನೊಂದಿಗೆ ಸಾಧಿಸಲು, ರದ್ದು ಮಾಡಿ ಕಾಯ್ದಿರಿಸುವ ಕಾರ್ಯದಲ್ಲಿ ವೀಕ್ಷಣೆ ಅನುಮೋದನಾ ರಸೀದಿಯನ್ನು ಹೊರಡಿಸುವ ವ್ಯವಸ್ಥೆಯನ್ನು ಒಳಗೊಂಡಿದೆ (ಡೆಸ್ಕ್‌ಟಾಪ್ ಹರಿವುಗಳಲ್ಲಿ ವೆಬ್ ಆಥ್‍ನ್ ಬೆಂಬಲಿತ), ಮೇಲಿನ ಮಾನವ-ಅನುಮೋದನೆ ನೋಟ್ಬುಕ್‌ನಂತೆ.
   - **[nobulex](https://github.com/arian-gogani/nobulex)** ಪೈಥಾನ್ SDK (`pip install nobulex`) Ed25519 + JCS ಸಹಿ ಮಾದರಿಯನ್ನು ಪೈಥಾನ್‌ನಲ್ಲಿ LangChain ಮತ್ತು CrewAI ಸಂಯೋಜನೆಗಳೊಂದಿಗೆ ಒದಗಿಸುತ್ತದೆ, ಪ್ರಕಟಿತ ಪರಸ್ಪರ-ಪರಿಶೀಲನೆ ಪರೀಕ್ಷಾ ಕಿಕ್ಕುಗಳು ಮತ್ತು [OWASP PR #2210](https://github.com/OWASP/CheatSheetSeries/pull/2210) ಮೂಲಕ ಕೊಡುಗೆ ಹೊಂದಿದೆ.
- **[EMILIA ಪ್ರೋಟೋಕಾಲ್](https://github.com/emiliaprotocol/emilia-protocol)** ಪೂರಕ ನಿಖರ-ಕ್ರಿಯೆ ಜಾರಿಗೊಳಿಸುವ ಪದರವನ್ನು ಒದಗಿಸುತ್ತದೆ: ಆಫ್‌ಲೈನ್-ಪರಿಶೀಲಿಸಬಹುದಾದ ಅನುಮೋದನಾ ರಸೀದಿಗಳು, ನಿಗದಿಗೊಳಿಸಿದ WebAuthn ಅಥವಾ ಕ್ವೋರಮ್ ಪ್ರಾಧಿಕಾರ, ನಿರ್ವಾಹಕ ಗಡಿಯಲ್ಲಿನ ಒಮ್ಮೆ ಮಾತ್ರ ಬಳಕೆ, ಮತ್ತು ಸ್ಪಷ್ಟ ಅನಿಶ್ಚಿತ ಫಲಿತಾಂಶ ಮಾರ್ಗ. ಅದರ ಫ್ರೇಮ್ವರ್ಕ್ ಅಡಾಪ್ಟರ್‌ಗಳು ರಸೀದಿಯನ್ನು ಬಾಹ್ಯ ಪರಿಣಾಮ ಸಂಭವಿಸಿತೇ ಎಂಬುದನ್ನು ಸಾಬೀತುಪಡಿಸುವುದರ ಬದಲು ಅಗತ್ಯವಾದ ಸಾಕ್ಷ್ಯವಾಗಿ ಪರಿಗಣಿಸುತ್ತವೆ.

ನಿಮ್ಮದೇ JWT ಗ್ರಂಥಾಲಯವನ್ನು ಬರೆಯುವುದು ಅಥವಾ ಪರೀಕ್ಷಿತ ಗ್ರಂಥಾಲಯವನ್ನು ಬಳಸದಿರುವುದರೊಳಗಿನ ಭೇದದಲ್ಲಿಯೇ, ನಿಮ್ಮದೇ ರಸೀದಿ ಗ್ರಂಥಾಲಯವನ್ನು ರಚಿಸುವ ಅಥವಾ ಬಳಸದಿರುವ ನಿರ್ಧಾರ. ಎರಡೂ ಸಮಂಜಸ; ಗ್ರಂಥಾಲಯ ಸಮಯ ಉಳಿಸುತ್ತದೆ ಮತ್ತು ಪರಿಶೀಲನೆ ಸೌಕರ್ಯ ಕಡಿಮೆ ಮಾಡುತ್ತದೆ; ಆರಂಭದಿಂದ ಬರೆಸುವುದು ಪ್ರತಿಯೊಂದು ಮೂಲಭೂತವನ್ನು ಅರ್ಥಮಾಡಿಕೊಳ್ಳಲು ಕೈಪಿಡಿ. ಈ ಪಾಠ ಆರಂಭದಿಂದಲೂ ಮಾರ್ಗವನ್ನು ಕಲಿಸುವುದರಿಂದ ಯಾವುದೇ ಆಯ್ಕೆಗೆ ಮೂಲಸೌಕರ್ಯ ಸಿಗುತ್ತದೆ.

## ಜ್ಞಾನ ಪರಿಶೀಲನೆ

ಅಭ್ಯಾಸ ವ್ಯಾಯಾಮಕ್ಕೆ ಮುಂದುವರಿಯುವ ಮುನ್ನ ನಿಮ್ಮ ಅರ್ಥಮಾಡಿಕೊಳ್ಳುವಿಕೆಯನ್ನು ಪರೀಕ್ಷಿಸಿ.

**1. ರಸೀದಿಯನ್ನು ಏಜೆಂಟ್ ಖಾಸಗಿ Ed25519 ಕೀಲಿನೊಂದಿಗೆ ಸಹಿ ಮಾಡಲಾಗಿದೆ. ಆಡಿಯಟರ್‌ಗೆ ಸಾರ್ವಜನಿಕ ಕೀ ಮಾತ್ರ ಇದೆ. ಆಡಿಯಟರ್ ಆಫ್‌ಲೈನ್‌ನಲ್ಲಿ ರಸೀದಿಯನ್ನು ಪರಿಶೀಲಿಸಬಹುದೇ?**

<details>
<summary>ಉತ್ತರ</summary>

ಹೌದು, ಕ್ರಿಪ್ಟೋಗ್ರಾಫಿಕ್ ದೃಢೀಕರಣಕ್ಕೆ ಕೇವಲ ಸಾರ್ವಜನಿಕ ಕೀ ಮತ್ತು ಸಹಿ ಲಗತ್ತಿಸಲಾದ ಬೈಟ್ಗಳೇ ಬೇಕಾಗುತ್ತವೆ. ಆ
ಆ ಆಡಿಟರ್ ಇನ್ನೂ ಸ್ವೀಕೃತ ಸಾರ್ವಜನಿಕ ಕೀವನ್ನು ರಸೀದಿಯಿಂದ ಸ್ವತಂತ್ರವಾಗಿ ಪಡೆದು ಅದನ್ನು ಪಿನ್ ಮಾಡಬೇಕು.
ಆ ವಿಶ್ವಾಸ ಸಂರಚನೆ ಸ್ಥಾಪಿತವಾದ ನಂತರ ಯಾವುದೇ ನೆಟ್‌ವರ್ಕ್ ಕರೆ ಅಗತ್ಯವಿಲ್ಲ.
</details>

**2. ದಾಳಿ ಮಾಡುವವರು ರಸೀದಿ `policy_id` ಕ್ಷೇತ್ರವನ್ನು ಬದಲಾಯಿಸಿ ಅದেকেಗಿಂತ ಹೆಚ್ಚು ಅನುಮತಿಸುವ ನೀತಿಯಿಂದ ಸಂಚಾಲಿತವಂತೆ ಹೇಳುತ್ತಾರೆ. ಸಹಿ ಆ ಮೂಲ ಪೇಲೋಡ್ ಮೇಲೆ ಆಗಿತ್ತು. ಪರಿಶೀಲನೆ ಸಮಯದಲ್ಲಿ ಏನಾಗುತ್ತದೆ?**

<details>
<summary>ಉತ್ತರ</summary>


ಪರಿಶೀಲನೆ ವಿಫಲವಾಗಿದೆ. ಸಹಿ ಮೂಲ ಪೇಲೋಡ್‌ನ ಮಾನಕ ಬೈಟುಗಳ ಮೇಲೆ ಲೆಕ್ಕಿಸಲಾಯಿತು; ಯಾವುದೇ ಕ್ಷೇತ್ರವನ್ನು ಬದಲಾಯಿಸುವುದು ಆ ಬೈಟುಗಳನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ, ಇದು ಸಹಿಯನ್ನು ಅಮಾನ್ಯಗೊಳಿಸುತ್ತದೆ. ದಾಳಿ ನಡೆಸುವವರು ಹೊಸ ಸರಿಯಾದ ಸಹಿಯನ್ನು ರಚಿಸಲು ಖಾಸಗಿ ಕೀ ಅಗತ್ಯವಿದೆ, ಅದು ಅವರ ಬಳಿ ಇಲ್ಲ.
</details>

**3. ರಸೀದಿ ಕಚ್ಚಾ ಆರ್ಗುಮೆಂಟ್ಗಳ ಮತ್ತು ಫಲಿತಾಂಶದ ಬದಲು `tool_args_hash` ಮತ್ತು `result_hash` ಅನ್ನು ಏಕೆ ಒಳಗೊಂಡಿದೆ?**

<details>
<summary>ಉತ್ತರ</summary>

ಎರಡು ಕಾರಣಗಳು. ಮೊದಲನೆಯದಾಗಿ, ರಸೀದಿ ಸಂಗ್ರಹಿಸಲು ಅಥವಾ ಪ್ರಸಾರ ಮಾಡಲು ಅಗತ್ಯವಿರಬಹುದು, ಅಲ್ಲಿ ಕಚ್ಚಾ ವಿಷಯ (ವೈಯಕ್ತಿಕ ಗುರುತಿಸುವ ಮಾಹಿತಿ, ವ್ಯಾಪಾರದ ದತ್ತಾಂಶ) ಲೀಕ್ ಆಗುವುದು ಸಮಸ್ಯೆಯಾಗಿರಬಹುದು. ಹ್ಯಾಷಿಂಗ್ ರಸೀದಿಯನ್ನು ಸಣ್ಣದಾಗಿಸು ಹಾಗೂ ವಿಷಯವನ್ನು ಖಾಸಗಿ ಇಡುತ್ತದೆ; ಪರಿಶೀಲಕವು ಹ್ಯಾಷ್ ಪ್ರಾರಂಭದಲ್ಲಿ ಇಡಲಾದ ನಕಲಿನೊಂದಿಗೆ ಹೊಂದಿಕೆಯಾಗುತ್ತದೆ ಎಂದು ಪರಿಶೀಲಿಸುತ್ತಾನೆ. ಎರಡನೆಯದಾಗಿ, ಹ್ಯಾಷ್‌ಗಳು ಸ್ಥಿರ ಗಾತ್ರವನ್ನು ಹೊಂದಿರುತ್ತವೆ; ಹ್ಯಾಷ್‌ಗಳುಳ್ಳ ರಸೀದಿ ಗಾತ್ರದಲ್ಲಿ ನಿಯಂತ್ರಿತವಾಗಿರುತ್ತದೆ, ಇನ್ಪುಟ್‌ಗಳು ಮತ್ತು ಔಟ್‌ಪುಟ್‌ಗಳು ಎಷ್ಟು ದೊಡ್ಡವಿದ್ದರೂ ಸಹ.
</details>

**4. `previous_receipt_hash` ಕ್ಷೇತ್ರವು ಪ್ರತಿ ರಸೀದಿಯನ್ನು ಅದರ ಪೂರ್ವ ಅವರೊಂದಿಗೆ ಸಂಪರ್ಕಿಸುತ್ತದೆ. ದಾಳಿಕಾರನು ಸರಣಿಯ ಮಧ್ಯಭಾಗದಲ್ಲಿ ಒಂದು ರಸೀದಿ ಮೌನವಾಗಿ ಅಳಿಸಿದರೆ, ಯಾವುದು ಅಮಾನ್ಯವಾಗುತ್ತದೆ?**

<details>
<summary>ಉತ್ತರ</summary>

ಮುಂದೆ ಪ್ರಸ್ತುತಪಡಿಸಲಾದ ರಸೀದಿ ಈಗ ಅದರ ನಿರೀಕ್ಷಿತ ಪೂರ್ವಸ್ಥಿಗೆ ಸಂಪರ್ಕ ಹೊಂದಿಲ್ಲ, ಈ ಕಾರಣದಿಂದ ಪರಿಶೀಲನೆ
ಆ ಪ್ರಸ್ತುತ ಸರಣಿಯ ಪರಿಶೀಲನೆ ಗ್ಯಾಪ್‌ನಿಂದ ಮುಂದುವರಿದು ವಿಫಲವಾಗುತ್ತದೆ. ಸೈನ್ ಮಾಡುವವರು ಖಾಸಗಿ
ಕೀಲಿಯನ್ನು ನಿಯಂತ್ರಿಸಿದರೆ, ಅದು ಉಪಸರಣಿಯನ್ನು ಮರುಬರೆಯಬಹುದು ಅಥವಾ ಕತ್ತರಿಸಬಹುದು. ಅದನ್ನು ಪತ್ತೆಹಚ್ಚಲು ಪಿನ್ ಮಾಡಿದ ಪ್ರಸ್ತುತ ಹೆಡ್,
ಬಾಹ್ಯ ಚೆಕ್ಪಾಯಿಂಟ್, ಅಥವಾ ಪ್ರಾಮಾಣೀಕೃತ ಪಾಪ್ಯುಲೇಷನ್ ಬದ್ಧತೆ.
</details>

**5. ರಸೀದಿ ಸ್ಪಷ್ಟವಾಗಿ ಪರಿಶೀಲನೆಗೊಂಡಿದೆ. ಇದು ಏಜೆಂಟ್‌ನ ಕ್ರಿಯೆ ಸರಿಯಾದುದು, ಧ್ವನಿಪೂರ್ಣ ಅಥವಾ ನೀತಿ ಅನುಕೂಲವಾಗಿದೆ ಎಂದು ಸಾಬೀತಾಗುತ್ತದೆಯೇ?**

<details>
<summary>ಉತ್ತರ</summary>

ಇಲ್ಲ. ಪಿನ್ ಮಾಡಲಾದ ಕೀ ಮತ್ತು ಚೈನ್ ಸನ್ನಿವೇಶದಡಿ, ಮಾನ್ಯ ರಸೀದಿ ಸಹಿಯ ಕರ್ತೃತ್ವವನ್ನು ಸಾಬೀತುಪಡಿಸುತ್ತದೆ,
ವಿಷಯದ ಅಖಂಡತೆ ಮತ್ತು ಪ್ರದರ್ಶಿತ ಪೂರ್ವದೊಂದಿಗೆ ಇರುವ ಕೊಂಡಿಯೊಂದನ್ನು ಸಾಬೀತುಪಡಿಸುತ್ತದೆ. ಇದು ಸಾಬೀತುಪಡಿಸುವುದಿಲ್ಲ
ಕ್ರಿಯೆ ಸರಿಯಾದದು ಅಥವಾ ಅನುಷ್ಠಾನಗೊಂಡಿತು ಎಂದು, ನೀತಿ ಮೌಲ್ಯಮಾಪನಗೊಂಡಿತು ಎಂದು, ಟೈಮ್ಸ್ಟಾಂಪ್ ನಂಬಲಾಗುತ್ತದೆ ಎಂದು,
ಅಥವಾ ದಾಖಲೆ ಸೆಟ್ ಸಂಪೂರ್ಣವಾಗಿದೆ ಎಂದು. ಇದು ಪಾಠದ ಅತ್ಯಂತ ಪ್ರಮುಖ ಗಡಿ.
</details>

## ಅಭ್ಯಾಸ ವ್ಯಾಯಾಮ

 `code_samples/18-signed-receipts.ipynb` ಓದಿ ನಾಲ್ಕು ವಿಭಾಗಗಳನ್ನೂ ಪೂರ್ಣಗೊಳಿಸಿ:

1. **ವಿಭಾಗ 1**: ನಿಮ್ಮ ಮೊದಲ ರಸೀದಿಯನ್ನು ಸಹಿ ಮಾಡಿ ಮತ್ತು ಪರಿಶೀಲಿಸಿ.
2. **ವಿಭಾಗ 2**: ರಸೀದಿಯನ್ನು ಏಳುಮಾಡಿ ಮತ್ತು ಪರಿಶೀಲನೆ ವಿಫಲವಾಗುತ್ತದೆ ನೋಡಿ.
3. **ವಿಭಾಗ 3**: ಮೂರು ರಸೀದಿ ಸರಣಿಯನ್ನು ನಿರ್ಮಿಸಿ ಸರಣಿಯ ಅಖಂಡತೆ ಪರಿಶೀಲಿಸಿ.
4. **ವಿಭಾಗ 4**: ಮೈಕ್ರೋಸಾಫ್ಟ್ ಏಜೆಂಟ್ ಫ್ರೇಮ್ವರ್ಕ್ ಬಳಸಿ ನಿರ್ಮಿಸಿದ ಏಜೆಂಟ್‌ಗೆ ಮಾದರಿಯನ್ನು ಅನ್ವಯಿಸಿ: ಟೂಲ್ ಕರೆ ರಸೀದಿ-ಸಹಿ ಮೂಲಕ ಮುತ್ತಬೇಕು, ನಂತರ ರಸೀದಿಯನ್ನು ಸ್ವತಂತ್ರವಾಗಿ ಪರಿಶೀಲಿಸಬೇಕು.

**ಸ್ಟ್ರೆಚ್ ಸವಾಲು 1:** ಇಚ್ಛಿತ ಕ್ಷೇತ್ರ ಒಂದು ಹೆಚ್ಚಿಸಿ (ಉದಾಹರಣೆಗೆ ಟ್ರೇಸಿಂಗ್‌ಗಾಗಿ ವಿನಂತಿ ID), ಮಾನಕ ಸಹಿ ಲಾಜಿಕ್ ಅನ್ನು ಅದರಲ್ಲಿ ಸೇರಿಸಿ, ಮತ್ತು ರಸೀದಿ ಪರಿಶೀಲನೆಯ ಮೂಲಕ ಮತ್ತೆ ಸುತ್ತುಹೋಗುತ್ತದೆ ಎಂದು ಖಚಿತಪಡಿಸಿ. ನಂತರ ಸಹಿ ನಂತರ ಕ್ಷೇತ್ರವನ್ನು ಬದಲಿಸಿ ಮತ್ತು ಪರಿಶೀಲನೆ ವಿಫಲವಾಗುತ್ತದೆ ಎಂದು ದೃಢಪಡಿಸಿ. ಇದು ಮಾನಕ ಎನ್ಕೋಡಿಂಗ್‌ನ ಪ್ರತಿಯೊಂದು ಬೈಟ್ ಸಹಿಗೆ ಹೇಗೆ ಕೊಡುಗೆ ನೀಡುತ್ತದೆ ಎಂದು ತಿಳಿಯಲು ನಿಮಗೆ ಸಹಾಯ ಮಾಡುತ್ತದೆ.

**ಸ್ಟ್ರೆಚ್ ಸವಾಲು 2:** ನಿಮ್ಮ երկու ರಸೀದಿಗಳನ್ನು SHA-256 ಹ್ಯಾಷ್ ಮಾಡಿ (ಮೌಲ್ಯಮಾನ ನಿಯೋಜಿತ ಕ್ರಮದಲ್ಲಿ ಮಾನಕ ಬೈಟುಗಳನ್ನು Concatenate ಮಾಡಿ) ಮತ್ತು ಹಿನ್ನೀಲಿ ಒಂದು ಮೂರನೇ ರಸೀದಿಯಲ್ಲಿ ಹೊಸ ಕ್ಷೇತ್ರವಾಗಿ ಹೇರಿಸಿ. ಎಲ್ಲಾ ಮೂರು ರಸೀದಿಗಳು ಇನ್ನೂ ಸುತ್ತುಹೋಗುತ್ತವೆ ಎಂದು ಪರಿಶೀಲಿಸಿ. ನೀವು ಇತ್ತೀಚೆಗೆ ಒಂದು ಹಂತದ ಒಳಗೊಂಡಿರುವುದು ಸಾಬೀತು ಮಾಡುವುದನ್ನು ನಿರ್ಮಿಸಿದ್ದೀರಿ: ಮೂರನೇ ರಸೀದಿ ಹೊಂದಿರುವೆವರು ಮೊದಲ ಎರಡು ಸಹಿ ಆಗಿದ್ದಾಗ ಇದ್ದವು ಎಂದು ಸಾಬೀತು ಮಾಡುವುವು, ವಿಷಯಗಳನ್ನು ಬಹಿರಂಗಪಡಿಸದೆ. ಇದು ಆಯ್ಕೆಮಾಡಿದ ಬಹಿರಂಗ ಪಟ್ಟಿ ರಸೀದಿಗಳು ವ್ಯಾಪಕವಾಗಿ ಬಳಸುವ ಮಾದರಿ (Merkle ಬದ್ಧತೆಗಳು, RFC 6962).

## ಕೊನೆ

ಕ್ರಿಪ್ಟೋಗ್ರಾಫಿಕ್ ರಸೀದಿಗಳು AI ಏಜೆಂಟ್‌ಗಳಿಗೆ ಈ ರೀತಿಯ ಪರಿಶೀಲನಾ ಹಾದಿಯನ್ನು ನೀಡುತ್ತವೆ:

- **ನಿಗದಿಗೊಳಿಸಿದ ನಂಬಿಕೆಯ ಅಡಿಯಲ್ಲಿ ಸ್ವತಂತ್ರವಾಗಿ ದೃಢೀಕರಿಸಬಹುದಾಗಿದೆ**: ಸ್ವೀಕರಿಸಲಾದ ಸಾರ್ವಜನಿಕ ಕೀಲಿಗಳು ಮತ್ತು ಹಸ್ತಾಕ್ಷರಿತ ಬೈಟ್ಗಳಿರುವ ಒಂದು ಪಕ್ಷವು ಸೇವಾ ಅವಲಂಬನೆಯಿಲ್ಲದೆ ದೃಢೀಕರಿಸಬಹುದು.
- **ತಪ್ಪುಮಾಡಲು ದೃಷ್ಟಿಗೋಚರ**: ಯಾವುದೇ ಬದಲಾವಣೆ ಸಹಿಯನ್ನು ಅಮಾನ್ಯಗೊಳಿಸುತ್ತದೆ.
- **ಹರಿಸಲಾಗಬಹುದಾದದ್ದು**: ರಸೀದಿ ಸಣ್ಣ JSON ಕಡತ; ಅದನ್ನು ಸಂಗ್ರಹಿಸಬಹುದು, ಪ್ರಸಾರ ಮಾಡಬಹುದು ಮತ್ತು ಉಪಸ್ಥಿತಿಯಲ್ಲಿ ಪರಿಶೀಲಿಸಬಹುದು.
- **ಮಾಣ್ಯಗಳಗುಂಡಾದವು**: Ed25519 (RFC 8032), JCS (RFC 8785), ಮತ್ತು SHA-256 ಮೇಲೆ ನಿರ್ಮಿತ, ಎಲ್ಲವೂ ವ್ಯಾಪಕವಾಗಿ ಬಳಸುವ ಪ್ರಾಥಮಿಕಗಳು.

ಅವುಗಳು ಇನ್‌ಪುಟ್ ಮಾನ್ಯತೆ, ನೀತಿ ಅನುಷ್ಠಾನ, ಕಾರ್ಯನಿರ್ವಾಹಕರ ಪ್ರವೇಶಕ್ಕೆ ಪರ್ಯಾಯವಲ್ಲ,
ಫಲಿತಾಂಶದ ಸಾಬೀತುಗಳು, ಸಂಪೂರ್ಣತೆ ನಿಯಂತ್ರಣೆಗಳು, ಅಥವಾ ಗುರುತಿನ ಮೂಲಸೌಕರ್ಯ. ಅವುಗಳು ಆಧಾರವಾಗಿವೆ
ಆ ಪದರಗಳಿಗಾಗಿ. ನಿಯಂತ್ರಿತ ಅಥವಾ ಬಹು-ಸಂಸ್ಥಾ ಕಾರ್ಯಪ್ರವಾಹಗಳಲ್ಲಿ, ರಸೀದಿಗಳು ನಿರ್ದಿಷ್ಟ
ಇಶ್ಯೂಯರ್ ಹೇಳಿಕೆಗಳನ್ನು ಆಡಿಟರ್‌ನ ಸ್ವಂತ ನಂಬಿಕೆಯ ಸಂರಚನೆಯಡಿ ಸ್ವತಂತ್ರವಾಗಿ ಪರಿಶೀಲಿಸಬಹುದಾಗಿಸುತ್ತವೆ.

ಅತ್ಯಂತ ಪ್ರಮುಖ ಉಪಸಂಹಾರ: ರಸೀದುಗಳು ಸಾಬೀತುಪಡಿಸುತ್ತವೆ ಎಂದು ಒಂದು ನಿರ್ದಿಷ್ಟ ಕೀ ಒಂದು ನಿರ್ದಿಷ್ಟ
ವಿಷಯವನ್ನು. ಒಟ್ಟಿಗೆ ಸಾಗಿಸಲಾದ ಟೈಮ್‌ಸ್ಟ್ಯಾಂಪ್ ಪ್ರತ್ಯೇಕವಾಗಿ ಸಮಯದ ಮೂಲಕ ದೃಢೀಕರಿಸದಿದ್ದರೆ ಸಹಿ ಮಾಡುವವರ ಘೋಷಣೆಯಾಗಿದೆ. ಒಂದು
ರಸೀದು ಅದರ ವಿಷಯವು ಸತ್ಯವೆಂದು, ಯಾವುದೇ ಕ್ರಮವು ಕಾರ್ಯಗತವಾಯಿತು ಎಂದು, ಅಥವಾ ಆ
ದಾಖಲೆಗಳ ಸೆಟ್ ಸಂಪೂರ್ಣವಾಗಿದೆ ಎಂಬುದನ್ನು ಸಾಬೀತುಪಡಿಸುವುದಿಲ್ಲ. ಆ ವ್ಯತ್ಯಾಸಗಳನ್ನು ಕಟ್ಟುನಿಟ್ಟಾಗಿ ಹಿಡಿದುಕೊಳ್ಳಿ.

## ಉತ್ಪಾದನಾ ಪರಿಶೀಲನೆ ಪಟ್ಟಿ

ನೀವು ಈ ಪಾಠವನ್ನು ಮುಗಿಸಿ ತಾಂತ್ರಿಕ ವಾಸ್ತವಿಕ ಪರಿಸರದಲ್ಲಿ ರಸೀದಿ-ಸಹಿತ ಏಜೆಂಟ್ ಗಳನ್ನು ನಿಯೋಜಿಸಲು ಸಿದ್ಧರಾಗಿರುವಾಗ:

- [ ] **ದೇವಲಾಪಕಿ ಲ್ಯಾಪ್‌ಟಾಪ್‌ನಿಂದ ಸಹಿ ಕೀಯನ್ನು ಅಳಿಸಿ.** Azure Key Vault, AWS KMS, ಅಥವಾ ಹಾರ್ಡ್‌ವೇರ್ ಸುರಕ್ಷತಾ ಘಟಕವನ್ನು ಬಳಸಿರಿ. ನಿಮ್ಮ ರಸೀದಿ ಸಹಿ ಮಾಡುವ ಖಾಸಗಿ ಕೀ ಮೂಲ ನಿಯಂತ್ರಣ ಅಥವಾ ಸಾಗಣೆ ಯಂತ್ರಗಳಲ್ಲಿ ಪLAINಟೆಕ್ಸ್ಟ್ ಆಗಿರಬಾರದು.
- [ ] **ಪರಿಶೀಲಕ ಕೀ ವಿಶ್ವಾಸ ಸ್ಥಾಪಿಸಿ.** JWK Set ಅಥವಾ ರೆಜಿಸ್ಟ್ರಿ ಮೂಲಕ ಕೀಲಿಗಳನ್ನು ಪ್ರಕಟಿಸಿ, ನಂತರ ನಿರ್ಭರಿಸುವ ಪಕ್ಷಗಳು ಸ್ವೀಕೃತ ಜಾರಿಕರಿಸುವವರ ಗುರುತು, ಕೀ ಸೆಟ್ ಮತ್ತು ರೊಟೇಶನ್ ನೀತಿಯನ್ನು ವೈಯಕ್ತಿಕ ರಸೀದಿಗಳ ಹೊರಗೆ ನಿಗದಿಪಡಿಸಿಕೊಳ್ಳುವಂತೆ ಮಾಡಿ. ಒಂದು ಇನ್‌ಲೈನ್ ಕೀ ಮಾತ್ರ ನಂಬಿಕೆಯ ಆಧಾರವಲ್ಲ.
- [ ] **ಸರಣಿಯನ್ನು ಹೊರಗಿನ ನಿರ್ಧಾರಕ್ಕೆ ಆಂಕರ್ ಮಾಡಿ.** ಸಿಗಸ್ಟೋರ್ ರೆಕಾಪರ್, RFC 3161 ಸಮಯ ಮುದ್ರಿತ ಪ್ರಾಧಿಕಾರ, ಅಥವಾ ಎರಡನೇ ಆಂತರಿಕ ವ್ಯವಸ್ಥೆಗೆ ಇತ್ತೀಚಿನ ಸರಣಿ ತಲೆ ಹ್ಯಾಶ್ ನಿಯಮಿತವಾಗಿ ಬರೆಯಿರಿ, ಹಾಗಾಗಿ ಹೊರಗಿನ ಪಕ್ಷವು "ಈ ಸರಣಿ ಈ ಸಮಯದಲ್ಲಿ ಇತ್ತು" ಎಂದು ದೃಢಪಡಿಸಬಹುದು.
- [ ] **ರಸೀದಿಗಳನ್ನೂ ಅಚಲವಾಗಿ ಸಂಗ್ರಹಿಸಿ.** ಅತಿರಿಕ್ತ-ಮಾತ್ರ ಬ್ಲಾಬ್ ಸಂಗ್ರಹಣೆ (ಅಜೂರ್ ಸಂಗ್ರಹಣೆ ಅಚಲತೆ ನೀತಿಗಳೊಂದಿಗೆ, AWS S3 ವಸ್ತು ಲಾಕ್) ಆಂತರಿಕರಿಗೆ ಇತಿಹಾಸವನ್ನು ಮರುಬರೆಯುವುದಿಲ್ಲ.
- [ ] **ರಹಿತ ನಿರ್ಧಾರ ಮಾಡಿ.** ಹಲವಾರು ಅನುಭವ ನಿಯಮ ವರುಷ ಸಹಿತ ಸಂಗ್ರಹಣೆ ಬೇಕಾಗುತ್ತದೆ. ರಸೀದಿ ಬೃಹತ್ತಾಗುವಿಕೆಯನ್ನು ಯೋಜಿಸಿ (ಪ್ರತಿ ರಸೀದಿ ~500 ಬೈಟ್; ಏಜೆಂಟ್ ದಿನಕ್ಕೆ 10K ಕರೆ ಮಾಡುತ್ತಿದ್ದರೆ ವರ್ಷಕ್ಕೆ ~1.8 GB ಉತ್ಫತ್ತಾ).
- [ ] **ರಸೀದಿಗಳು ಯಾವಯಾವುದನ್ನು ಒಳಗೊಂಡಿಲ್ಲ ಎಂದು ದಾಖಲೆ ಮಾಡಿರಿ.** ರಸೀದಿಗಳು ಹಕ್ಕು, ಅಖಂಡತೆ, ಮತ್ತು ಕ್ರಮವನ್ನು ಸಾಬೀತುಪಡಿಸುತ್ತವೆ. ನಿಮ್ಮ ಕಾರ್ಯನಿರ್ದೇಶನದಲ್ಲಿ ಯಾವುದೇ ಹೆಚ್ಚುವರಿ ನಿಯಂತ್ರಣಗಳು (ಇನ್ಪುಟ್ ಪರಿಶೀಲನೆ, ನೀತಿ ಜಾರಿಗೊಳಿಸುವಿಕೆ, ದರ ಮಿತಿ, ಗುರುತು ವ್ಯವಸ್ಥೆ) ರಸೀದಿಗಳೊಡನೆ ನಿಮ್ಮ ಆಡಳಿತ ಕಸೂತಿ ಪಾಲಿನಲ್ಲಿ ಇರುವಂತೆ ಸ್ಪಷ್ಟವಾಗಿ ಪಟ್ಟಿಮಾಡಿರಿ.

### AI ಏಜೆಂಟ್‌ಗಳನ್ನು ಭದ್ರಪಡಿಸುವ ಕುರಿತು ಇನ್ನಷ್ಟು ಪ್ರಶ್ನೆಗಳಿದ್ದರೆ?

[Microsoft Foundry Discord](https://aka.ms/ai-agents/discord) ನಲ್ಲಿ ಸೇರಿ, ಇತರ ಕಲಿಯುವವರನ್ನು ಭೇಟಿ ಮಾಡಿ, ಕಾರ್ಯಾಲಯ ಸಮಯಗಳಲ್ಲಿ ಭಾಗವಹಿಸಿ ಮತ್ತು ನಿಮ್ಮ AI ಏಜೆಂಟ್ ಪ್ರಶ್ನೆಗಳಿಗೆ ಉತ್ತರಗಳನ್ನು ಪಡೆಯಿರಿ.

## ಈ ಪಾಠದ ಮೇಲೆ ಮುಂದುವರಿಯಿರಿ

ಈ ಪಾಠವು ಒಬ್ಬೊಬ್ಬ ರಸೀದಿ ಸಹಿ ಮತ್ತು ಹ್ಯಾಶ್ ಸರಣಿಗಳನ್ನು ಒಳಗೊಂಡಿದೆ. ಇದೇ ಮೂಲಭೂತಗಳು ನೀವು ಮುಂದುವರೆದ ನಿಯಂತ್ರಣ ವ್ಯವಸ್ಥೆಗೆ ಬರುತ್ತಿರುವಾಗ ಹಲವುಂತೆ ಉತ್ತುಂಗ ಮಾದರಿಗಳಲ್ಲಿ ನಾಡಿ ಬೀಳಬಹುದು:

- **ಆಯ್ಕೆಮಾಡಿದ ಬಹಿರಂಗಪಡಿಸುವಿಕೆ.** ಒಬ್ಬ ರಸೀದಿಯ ಕ್ಷೇತ್ರಗಳು ಸ್ವತಂತ್ರವಾಗಿ ಬದ್ಧವಾಗಿದ್ದರೆ (RFC 6962 ಶೈಲಿಯ ಮೆರ್ಕಲ್ ಮರ), ನೀವು ವಿಶೇಷ ಕ್ಷೇತ್ರಗಳನ್ನು ವಿಶೇಷ ಪರಿಶೀಲಕರಿಗೆ ಬಿಚ್ಚಿ ಇತರವು ಬದಲಾಗಿಲ್ಲ ಎಂದು ಸಾಬೀತು ಮಾಡಬಹುದು. ಒಂದು ಸಮಗ್ರ ಪರಿಶೀಲನೆ (ಪೂರ್ಣತೆಯನ್ನು ಬಯಸದವರು) ಮತ್ತು GDPR ಹೀಗೆ ಕಡಿಮೆ ದತ್ತಾಂಶ ನಿಯಮಗಳು (ಪರಿಶೀಲಕರು ಕಡಿಮೆ ತಿಳಿದುಕೊಳ್ಳಬೇಕು) ಈ ಎರಡನ್ನು ತೃಪ್ತಿಪಡಿಸಲು ಉಪಯುಕ್ತ.
- **ರಸೀದಿ ರದ್ದತಿಕರಣ.** ಸಹಿ ಕೀ ಭಂಗವಾಗಿದ್ದರೆ, ಆ ಕೀ ಸಹಿ ಮಾಡಿದ ಎಲ್ಲಾ ರಸೀದಿಗಳನ್ನು ನಂಬಿಕೆಗೆ ಒಳಪಡಿಸುವದಿಲ್ಲ ಎಂದು ಸೂಚಿಸಲು ವಿಧಾನ ಬೇಕಾಗುತ್ತದೆ. ಮಾನಕ ಮಾದರಿಗಳು: ಚಿಕ್ಕ ಅವಧಿಯ ಸಹಿ ಕೀಗಳು ಮತ್ತು ಪ್ರಕಟಿತ ರದ್ದತಿಮಾಡಿದ ಪಟ್ಟಿ, ಅಥವಾ ರದ್ದತಿಸೂಚನೆಗಳಿರುವ ಪಾರದರ್ಶಕತಾಪಟ್ಟಿ.
- **ದ್ವಿಪাক্ষೀಯ / ವಿಭಾಗ-ಸಹಿ ರಸೀದಿಗಳು.** ಕೆಲವು ಅನುಷ್ಠಾನಗಳು ಸಹಿತ ಪೇಲೋಡ್ ಅನ್ನು ಪೂರ್ವ-ನಿರ್ವಹಣೆ (`authorization_*`) ಮತ್ತು ನಂತರ-ನಿರ್ವಹಣೆ (`result_*`) ಭಾಗಗಳಲ್ಲಿ ವಿಭಜಿಸಿ ಸ್ವತಂತ್ರ ಸಹಿಗಳೊಂದಿಗೆ ಬಳಸುತ್ತವೆ, ಅಥಾರೈಸೇಶನ್ ನಿರ್ಧಾರ ಮತ್ತು ಕಂಡುಬಂದ ಫಲಿತಾಂಶ ವಿಭಿನ್ನ ಪಾತ್ರದವರು ಅಥವಾ ಸಮಯದಲ್ಲಿ ಸೃಷ್ಟಿಸಿದಾಗ ಉಪಯುಕ್ತ. ಇದು ಈ ಪಾಠದಲ್ಲಿ ಕಲಿಸುವ ರಸೀದಿ ರೂಪರೇಖೆಯ ಮೇಲೆ ಸೇರಿಸಲಾಗುತ್ತದೆ.
- **ಪೇಲೋಡ್ ಸಂಯೋಜನೆ.** ನಿಮಗೆ `result_hash` ಒಳಗೊಂಡ ಯಾವುದೇ ಬೈಟುಗಳನ್ನು ರಸೀದಿ ಮೊಟ್ಟುಮುದ್ರಣ ಮಾಡುತ್ತದೆ. ವಾಸ್ತವಿಕ ಪೇಲೋಡ್‌ಗಳು ಹಲವು ಆಯ್ಕೆ-ಅನುಕೂಲನೆಗಳ ಹಾಗೂ ಪೂರ್ವ-ನಿರ್ಧಾರ ನಿರ್ವಹಣೆಯೊಂದಿಗೆ ಸಮೃದ್ಧವಾಗಿರಬಹುದು: ಮೊದಲನೆಯ ಆಗಾಗ ಮತ್ತು ಅದರ ಪೂರ್ಣತೆ, ಅಪಾಯ ಸ್ಥಿತಿ, ಹೊಣೆಗಾರಿಕೆ ಸರಣಿ, ಗೇಟ್ ಫಲಿತಾಂಶ ಇत्यಾದಿ. ಇದರಿಂದ ರಸೀದಿ ಸ್ವರೂಪವನ್ನು ಕನಿಷ್ಠವಾಗಿಟ್ಟುಕೊಳ್ಳಬಹುದು ಮತ್ತು ಪೇಲೋಡ್ ವ್ಯಾಕ್ಯಸಗಳು ಕ್ಷೇತ್ರ-ಪ್ರಕಾರವಾಗಿ ಬೆಳೆಯಬಹುದು.
- **ದ್ವಿತೀಯ ಅನುಷ್ಠಾನ ಹೊಂದಾಣಿಕೆ.** ಒಂದೇ ರಸೀದಿ ಸ್ವರೂಪದ ಹಲವಾರು ಸ್ವತಂತ್ರ ಅನುಷ್ಠಾನಗಳು (Python, TypeScript, Rust, Go) ಹಂಚಿದ ಟೆಸ್ಟ್ ವ್ಯಾಕ್ಟರ್‌ಗಳ ವಿರುದ್ಧ ಪರಿಶೀಲಿಸುತ್ತವೆ. ನೀವು ನಿಮ್ಮದೇ ಅನುಷ್ಠಾನ ನಿರ್ಮಿಸಿದರೆ, ಪ್ರಕಟಿತ ವ್ಯಾಕ್ಟರ್‌ಗಳ ವಿರುದ್ಧ ಮಾನ್ಯತೆ ಪಡೆದು ವ್ಯತ್ಯಾಸರಹಿತ ಸಂಪರ್ಕವನ್ನು ಖಚಿತಪಡಿಸಬಹುದು.
- **ಪೋಸ್ಟ್-ಕ್ವಾಂಟಮ್ ಸ್ಥಳಾಂತರ.** Ed25519 ಇಂದು ವ್ಯಾಪಕವಾಗಿ ಹಮ್ಮಿಕೊಳ್ಳಲಾಗಿದೆ ಆದರೆ ಅದು ಕ್ವಾಂಟಮ್-ಪ್ರತಿರೋಧಕವಲ್ಲ. ಒಂದು `alg` ಲೇಬಲ್ ಮಾತ್ರವೇ ಸ್ಥಳಾಂತರವಲ್ಲ: ಒಂದು ಪ್ರೊಫೈಲ್ ML-DSA ಕೀ ಎನ್‌ಕೋಡಿಂಗ್, ಕ್ಯಾನೋನಿಕಲ್ ಸಹಿ ಮಾಡಲಾದ ಬೈಟ್ಸ್, ಪರಿಶೀಲನೆ, ಆಧಾರಿತ ಪಕ್ಷದ ನೀತಿ, ಡೌನ್ಗ್ರೇಡ್ ಪ್ರತಿರೋಧಕತೆ ಮತ್ತು ಪರಿವರ್ತನೆಯ ಅರ್ಥಶಾಸ್ತ್ರವನ್ನು ನಿರ್ಧರಿಸಬೇಕು. ಅನುಕೂಲತೆ ಸಂಬಂಧಿ ದಾವೆಗಳನ್ನು ಮಾಡುವ ಮೊದಲು ಹಂಚಿಕೊಂಡಿರುವ ವೆಕ್ಟರ್‌ಗಳ ವಿರುದ್ಧ ದ್ವಿ-ಸಹಿ ಪರಿವರ್ತನೆಯನ್ನು ಯೋಜಿಸಿ ಮತ್ತು ಪರೀಕ್ಷಿಸಿ.
